# 0001. SDD 用ツール(cc-sdd)を導入しない

- 日付:2026-10-08
- 状態:採用

## 背景

このプロジェクトは仕様駆動開発(SDD)で進める。最優先は、実装内容をオーナーが理解すること([principles.md](../principles.md))。

AI と SDD を進めるためのツールとして cc-sdd がある。npm パッケージで、Claude Code などにコマンド(スキル)を追加する。確認した時点の版は v3.0。

cc-sdd の流れは次のとおり。

1. `/kiro-spec-init`、`/kiro-spec-requirements`、`/kiro-spec-design`、`/kiro-spec-tasks` で、機能ごとに要件・設計・タスクを作る(`.kiro/specs/機能名/` に 3 ファイル)
2. 人が仕様を承認する
3. `/kiro-impl` で、AI が長時間にわたって自律的に実装する(サブエージェントによるレビューやデバッグ付き)

## 選択肢

1. cc-sdd を全面的に導入する
2. 仕様作成のコマンドだけ使い、実装は自分たちの流れで行う
3. 導入せず、自分で設計した流れ([development-flow.md](../development-flow.md))で進める

## 決定

3 を選ぶ。

## 理由

- **1 は方針と合わない**。cc-sdd v3 の中心は、仕様の承認後に AI が自律的に実装すること。このプロジェクトは、1ファイルずつ説明・承認・差分確認をしながら進める。人が関わる場所が根本的に違う。
- **2 は管理が二重になる**。仕様書が `.kiro/specs/` と `docs/specs/` に、タスクが `tasks.md` と GitHub Issue に分かれる。どちらが最新か分からなくなる。
- **3 は説明できる**。既存のツールを調べたうえで、目的に合わせて流れを自分で設計した。なぜこの流れなのかを、自分の言葉で説明できる。

## 影響

- cc-sdd の考え方のうち、次は取り入れる。
  - 受け入れ条件を EARS 形式(「〜のとき、システムは〜する」という型)で書く。仕様書の「完了条件」の書き方として、development-flow.md に追記する(別途)。
  - `.kiro/steering/` に相当する全体の前提は、principles.md と architecture.md が担う。
- 実装の速さが理解より重要になった場合(例:締め切りのある機能追加)は、この判断を見直す。
