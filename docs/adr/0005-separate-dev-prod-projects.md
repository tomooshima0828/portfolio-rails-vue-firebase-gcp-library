# 0005. 開発用と本番用で、Google Cloud のプロジェクトを分ける

- 日付:2026-11-10
- 状態:採用

## 背景

#29 で、フェーズ2の本番(Cloud Run、Cloud SQL、Firebase Hosting など)を置く Google Cloud のプロジェクトを用意する。プロジェクトは、部品と設定と料金をまとめる単位で、Firebase のプロジェクトも、その1つに Firebase の機能を足したものになっている。

[ADR 0004](0004-local-firebase-auth.md) で、ローカルの Google ログインには、本物の Firebase の開発用プロジェクトを使うことにした。このプロジェクトは無料の Spark プランで、請求先アカウント(料金を払うクレジットカード)を紐づけていない。ADR 0004 では、本番用のプロジェクトを開発用と分けるかどうかを、フェーズ2で決めることにしていた。

Cloud Run や Cloud SQL を使うには、プロジェクトに請求先アカウントを紐づける必要がある(Firebase では Blaze プランと呼ぶ)。

## 選択肢

1. 開発用と本番用の2つに分ける。開発用は Spark プランのままにし、請求先アカウントは本番用にだけ紐づける
2. 1つのプロジェクトで、開発と本番を兼ねる。今の開発用のプロジェクトに請求先アカウントを紐づけ、本番の部品もそこに置く
3. 開発用・検証用(ステージング)・本番用の3つに分ける。本番に出す前に、本番と同じ構成の検証用で確かめる

## 決定

1 を選ぶ。本番用のプロジェクトの ID は `knowledge-library-prod` にする。

## 理由

- **料金が生まれる場所を、本番用の1つに閉じ込められる**。2 では、ローカル開発のログインに使う箱にも請求先アカウントが紐づき、開発の試しで有料の部品を作ると、そのまま料金になる。1 では、開発用の箱は無料の範囲を超えて使えないので、料金は本番用からしか生まれない。予算アラートも、本番用の1つを見張れば足りる。
- **開発の試しが、本番に響かない**。2 では、Firebase Authentication の設定(ログイン方法、承認済みのドメインなど)が開発と本番で1組しかない。ローカルのために設定を変えると、本番のログインも変わる。データも混ざる。1 なら、設定もデータも別々になる。
- **3 は、この規模には重い**。検証用にも Cloud SQL が要るので、料金が倍近くになる。docs/principles.md の非目標「無料枠・低額枠を超える常時稼働の構成」に当たる。利用者がオーナー1人のポートフォリオでは、本番で問題が出ても影響が小さく、検証用で先に確かめる得が料金に見合わない。
- **分ける損は小さい**。プロジェクトが2つになると、Firebase の設定を2回することになる。ただ、開発用のプロジェクトで使っているのは Google ログインだけで、追加の料金もかからない。

2 は、プロジェクトが1つで設定が1回で済み、ローカルと本番が同じ Firebase の設定で動く。3 は、デプロイの手順や本番の設定を、本番に出す前に本番と同じ構成で確かめられる。1 を選ぶことで、これらの利点は捨てる。

## 影響

- 検証用がないので、デプロイの手順や本番だけの設定(Cloud Run、Cloud SQL、Secret Manager など)は、本番で初めて動かすことになる。その前に、CI のテストとローカル環境での確認を通す。本番で問題が出たら、直前の版に戻す。
- Firebase の設定値(`projectId`、`apiKey` など)が、開発用と本番用の2組になる。開発用はリポジトリ直下の `.env`(ADR 0004)、本番用は #32 で Vue をビルドするときに渡す。
- Rails が ID トークンを確かめるときの `FIREBASE_PROJECT_ID` も、開発用と本番用で値が変わる。本番用の値は #30 以降で Cloud Run に渡す。
- 開発用のプロジェクトは Spark プランのままにする。開発で有料の機能を試したくなったら、この判断を見直す。
- 本番用のプロジェクトの作り方は、`docs/production-setup.md` に書く。
