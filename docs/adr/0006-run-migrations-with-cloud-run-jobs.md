# 0006. 本番のマイグレーションは、Cloud Run のジョブで流す

- 日付:2026-11-11
- 状態:採用

## 背景

#31 で、本番の DB(Cloud SQL for PostgreSQL)を作り、Cloud Run の Rails から繋ぐ。DB に表を作ったり変えたりする作業(マイグレーション、`rails db:migrate`)を、本番では誰がどこで流すかを決める必要がある。

Rails が生成した `api/bin/docker-entrypoint` は、コンテナが起動するたびに `rails db:prepare` を流していた。#30 で、この処理を外した。Cloud Run は同時に複数のコンテナを起動することがあり、全部が一斉に流すとぶつかる恐れがあり、起動も遅くなるため(仕様書 030)。そのため、今は本番でマイグレーションを流す場所がない。

#33 では、`main` へのマージのたびに、マイグレーションを含めて自動でデプロイする。ここで決める流し方を、そのまま自動にできることが望ましい。

## 選択肢

1. Cloud Run のジョブで流す。サービス `api` と同じイメージ、同じ身分証(`api-runtime`)、同じ DB の設定で、`bin/rails db:migrate` を1回だけ実行して終わる。サービスをデプロイする前に流す
2. 手元の Mac から流す。Cloud SQL Auth Proxy を手元で動かして本番の DB に繋ぎ、`RAILS_ENV=production` で `rails db:migrate` を実行する
3. 起動時に流す方式に戻す。entrypoint で `rails db:migrate` を流し、同時に起動する台数を1に固定する

## 決定

1 を選ぶ。ジョブの名前は `migrate` にする。

## 理由

- **デプロイするコードと、流すマイグレーションが必ず一致する**。1 は、サービスと同じイメージを使うので、イメージに入っているマイグレーションが流れる。2 は、手元のコードから流すので、手元のブランチが、デプロイするイメージとずれていると、別のマイグレーションが流れる。
- **本番の鍵と権限を、手元に置かなくて済む**。2 は、手元に master.key と DB のパスワードを置き、オーナーのアカウントに本番の DB へ繋ぐ権限を持たせる必要がある。1 は、ジョブが `api-runtime` の身分で、Secret Manager から値を受け取るので、#30 と同じ仕組みで足りる。
- **#33 でそのまま自動にできる**。1 の手順は「ジョブのイメージを新しくして実行し、成功したらサービスをデプロイする」で、GitHub Actions からも同じ操作を呼べる。2 は、手元の Mac がないと流せない。
- **サービスの台数や起動の速さと切り離せる**。3 は、マイグレーションを安全に流すために台数を1に縛ることになり、#35 で台数を決めるときの制約になる。台数 0 からの起動のたびに、流すものがなくてもマイグレーションの確認が走り、最初のリクエストが遅くなる。マイグレーションが失敗すると、コンテナが起動せず、API 全体が止まる。1 なら、ジョブが失敗しても、サービスは前の版のまま動き続ける。

なお、#30 で挙げた「ぶつかる恐れ」は、調べ直すと、表が壊れる心配ではなかった。Rails は、マイグレーションを流す間、PostgreSQL のロック(アドバイザリーロック)を取る。複数のコンテナが同時に流そうとすると、ロックを取れた1台だけが流し、ほかのコンテナはロックを取れずにエラー(`ActiveRecord::ConcurrentMigrationError`)で止まる。表は壊れないが、起動時に流す方式では、エラーで止まったコンテナが起動に失敗する。これも、上の「失敗の巻き込み」の1つになる。

2 は、新しい部品を作らずに、すぐ流せる。3 は、デプロイの手順が1つで済み、流し忘れがない。1 を選ぶことで、これらの利点は捨てる。

## 影響

- デプロイの順番は「ジョブ `migrate` を流す → 成功したらサービス `api` をデプロイする」になる。ジョブが失敗したら、サービスはデプロイしない。
- 新しいイメージをデプロイするたびに、ジョブのイメージも同じものに変えてから実行する。変え忘れると、古いイメージのマイグレーションが流れる。#33 の自動化で、この手順をまとめる。
- ジョブが流れてからサービスが新しくなるまでの間、新しい表の形で、古いコードが動く。そのため、マイグレーションは、古いコードでも動く形で書く。たとえば、列を消すときは、まずコードがその列を使わないようにしてデプロイし、次のデプロイで列を消す。
- ジョブの料金は、実行している間だけかかる。数十秒で終わるので、無料枠に収まる見込み。
- ジョブの実行結果とログは、Cloud Run の「ジョブ」の画面と Cloud Logging で見る。
- 手順は `docs/production-setup.md` の「3. Cloud SQL」に書く。
