# 0007. Cloud SQL は、開発中は動かしたままにし、長く使わないときは削除する

- 日付:2026-11-11
- 状態:採用

## 背景

#31 で、本番の DB として Cloud SQL for PostgreSQL のインスタンス `db` を作る。Cloud SQL は、このプロジェクトで初めて、使っていなくても料金がかかる部品になる。

[docs/principles.md](../principles.md) の非目標に「Cloud SQL は予算アラートを設定し、使わない期間は停止または削除する」とあるが、止めるのか削除するのか、どのくらい使わなければそうするのかは決めていない。

料金を止める仕組みは、自動では働かない。

- #29 で設定した予算(月 3,000円)は、メールを送るだけで、課金は止めない
- 「予算と上限」の画面にある利用額上限(予算に達したら一部のサービスを一時停止する仕組み)は、対象が Gemini API、Vertex AI、Cloud Run、Cloud Run functions だけで、Cloud SQL は対象外(#29 で残した確認。2026-11-11 の Google の文書「Manage spend cap budgets」より)

そのため、費用を抑えるのは、オーナーが手で行う。

インスタンスは、公開 IP を付け、Cloud Run の Cloud SQL 接続で繋ぐ([仕様書 031](../specs/031-cloud-sql.md))。#31 では、まず Cloud SQL の30日間の無料お試しで作り、お試しが切れる前に、小さい DB(一番小さい共有コアの db-f1-micro、SSD 10GB)に作り直す。お試しの間は DB の料金がかからず、30日たつと、有料に切り替えない限り DB が止まる。

## 選択肢

月額は、お試しの後に作り直す小さい DB の、東京の価格の概算(1ドル150円)。公式の料金ページの値ではなく、第三者の記事と Google の文書からの見積もり。

| | 選択肢 | 月額の目安 | かかるもの |
|---|---|---|---|
| 1 | 動かしたままにする | 約1,900円 | 本体 約$10.2、ディスク 約$2.2 |
| 2 | 止める(インスタンスを停止し、使うときに開始する) | 約1,400円 | 公開 IP 約$7.3、ディスク 約$2.2 |
| 3 | 削除し、使うときに手順書で作り直す | 0円 | なし。データとバックアップも消える |

止めている間も、ディスクと IP アドレスの料金はかかる(Google の文書「Start, stop, and restart instances」)。公開 IP は、動いている間は料金がかからず、止めている間だけ1時間 $0.01 かかる。

## 決定

- 開発を続けている間は、1(動かしたまま)にする
- 1か月以上使わない見込みのときは、3(削除)にする
- 2(止める)は、普段は使わない。予算アラートのメールが来て、原因を調べる間に費用の増え方を抑えたいときの、応急処置にだけ使う

## 理由

- **止めても、ほとんど安くならない**。公開 IP で繋ぐので、止めている間は IP アドレスの料金がかかり、月500円ほどしか下がらない。止めるたびに、動かし直す手間と、止めている間 API がエラーを返すことを受け入れるには、見合わない。
- **動かしたままでも、予算に収まる**。月約1,900円で、予算の 3,000円に収まる。開発中は、記事の一覧などをいつでも本番で確かめられる方が、作業が止まらない。
- **データを失っても困らない**。本番の DB に入るのは、オーナーが動作確認で入れる記事だけ。削除して作り直せば、表はマイグレーションのジョブ([ADR 0006](0006-run-migrations-with-cloud-run-jobs.md))で元に戻る。
- **同じ名前ですぐ作り直せる**。削除したインスタンスの名前は、すぐに使い直せる(Google の文書「Delete instances」)。同じ `db` で作り直せば、接続名 `knowledge-library-prod:asia-northeast1:db` が変わらないので、Cloud Run のサービスとジョブの接続先を変えなくてよい。
- **作り直しの手順は、そのまま残る**。`docs/production-setup.md` の「3. Cloud SQL」が、作り直しの手順書になる。
- **境目を1か月にする**。作り直しには、インスタンスの作成を待つ時間を含めて、オーナーの手で1時間ほどかかる見込み。1か月使わなければ約1,900円の節約になり、手間に見合う。数日〜数週間の休みでは、作り直しの手間の方が大きい。

1 は、いつでも使えるが、使わない間も料金がかかる。2 は、データを残したまま費用を少し下げられる。3 は、料金が0円になるが、データとバックアップを失い、使い始めるまでに時間がかかる。

## 影響

- **お試しの間**:DB の料金がかからないので、使わない期間でも、止めたり削除したりしなくてよい。お試しを作った日に、作成から29日目の予定をカレンダーに入れる。29日目までに、お試しを削除し、小さい DB を作り直す(手順は下の「作り直すとき」と同じ)。応募が終わり、本番を見せる必要がなくなっていれば、作り直さずにお試しを削除するだけでもよい(その後は0円)。お試しは、有料に切り替えない(ストレージ 100GB を減らせず、月約3,300円かかるため。仕様書 031)。
- **削除するとき**:インスタンスの「削除からの保護」を外してから削除する。最終バックアップは取らない。シークレット `db-password` は消さずに残す(版を足して使い続ける)。
- **作り直すとき**:`docs/production-setup.md` の「3. Cloud SQL」に従い、同じ名前 `db` でインスタンス、データベース、利用者を作る。パスワードは新しく作り、`db-password` に新しい版として足す。Cloud Run のサービス `api` とジョブ `migrate` の、`DB_PASSWORD` の版の番号を変えてから、ジョブ → サービスの順に流す。
- **予算アラートが来たとき**:「お支払い」の「レポート」で、どのサービスの費用かを確かめる。Cloud SQL が想定より高ければ、まずインスタンスを止め(2)、原因が分かってから、動かし直すか削除するかを決める。止めている間、`GET /api/articles` は 500 を返す(仕様書 031 の AC-6)。
- **見直すとき**:
  - 小さい DB に作り直した後の最初の請求で、実際の月額を確かめる。上の見積もりと大きく違ったら、この判断を見直す
  - 本番に、失うと困るデータ(オーナー以外の人の記事など)が入るようになったら、削除の前に最終バックアップを取るか、削除をやめる
  - 内部 IP で繋ぐ方式に変えたら、止めている間の IP アドレスの料金がなくなるので、2(止める)を選び直す
