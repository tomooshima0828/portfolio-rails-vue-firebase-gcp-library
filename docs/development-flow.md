# 開発の流れ(SDD × GitHub)

仕様駆動開発(SDD)を、GitHub の Issue・Milestone・PR と組み合わせて進める。
前提となる方針は [principles.md](principles.md)、AI への作業ルールは [CLAUDE.md](../CLAUDE.md) にある。

## 役割分担

| 置き場所 | 書くこと | 寿命 |
|---|---|---|
| `docs/architecture.md` | **今の**全体像。機能一覧、画面と API の一覧、データモデル、インフラ構成 | 仕様が変わるたびに更新する |
| `docs/roadmap.md` | フェーズと、その順番・目標 | フェーズの見直し時に更新する |
| `docs/specs/` | タスクごとの仕様書。**実装前に必ず書く** | その時点の記録として残す。マージ後は書き換えない |
| Issue | タスク名、仕様書へのリンク、進み具合 | 作業が終われば Close |
| Milestone | フェーズ(Issue のまとまり)と進捗率 | フェーズが終われば Close |
| PR | 実際の変更と、その説明 | マージで完了 |

仕様の中身は仕様書にだけ書き、Issue には書かない(二重管理を避ける)。
タスクの一覧も roadmap.md には書かず、Issue だけで管理する。

## 流れ

```
① 全体を決める     → docs/architecture.md、docs/roadmap.md
② タスクに分解する → 1タスク = 1 Issue。フェーズごとに Milestone でまとめる
③ タスクを実装する → ブランチを作る
                     → 最初のコミットで仕様書(docs/specs/)を書く
                     → 1ファイルずつ実装してコミットする
                     → PR を作る(本文に「Closes #番号」)
④ 確認する         → CI が通り、動作確認の結果を PR に残してマージ
                     → 全体像が変わったら、同じ PR で architecture.md も更新する
```

例:

```
Milestone「フェーズ1:ログインして記事を投稿・一覧表示」
  ├ #11 Rails API プロジェクトを作る
  ├ #12 Firebase のトークン検証を作る
  ├ #13 記事モデルを作る
  └ #14 記事の作成・一覧 API を作る
          ↓
      ブランチ feature/14-articles-api
        1. docs/specs/014-articles-api.md   ← 仕様書(最初のコミット)
        2. config/routes.rb                 ← 1ファイルずつ実装
        3. app/controllers/...
        4. spec/requests/...
          ↓ Closes #14
      PR「記事の作成・一覧 API を作る」
```

## 単位のルール

| 単位 | 大きさ |
|---|---|
| Claude Code との対話 | 1回に書くのは 1ファイル(1実装箇所)。書く前に説明し、承認を得てから書く |
| コミット | 1ファイル(1実装箇所)ごと。理解した順に履歴を残す |
| タスク = Issue = ブランチ = PR | 単体で動作確認できる、意味のあるまとまり。目安は PR を一度に読み切れる量(数ファイル程度) |

例外:

- **生成コマンド**。`rails new`、`npm create vue` など、一度に複数ファイルを作るコマンドは「コマンド1回 = 1コミット」とする。PR では主要なファイルだけ説明する。
- **方針文書だけの変更**(`docs/` ブランチ)。実装を伴わないので、Issue と仕様書は作らなくてよい。

## 仕様書の書き方

`docs/specs/Issue番号-名前.md` に、次の欄を必ず書く。セットアップ作業など小さいタスクは短くてよい。

| 欄 | 書くこと |
|---|---|
| 目的 | なぜこのタスクが必要か |
| やること | 作るもの、振る舞い。API やデータを扱うタスクは入出力も書く |
| やらないこと | このタスクの範囲外 |
| 完了条件 | どうなれば終わりか。テストか手動確認で確かめられる形で書く |

## 仕様が変わったとき

- **作業中に変わったら**:同じ PR の中で、コードより先に仕様書を直す。
- **マージ後に変わったら**:新しいタスク(Issue)と仕様書を作る。過去の仕様書は書き換えず、architecture.md を更新する。

コードだけ先に変えて、仕様書が古いまま残る状態を作らない。

## 名前の付け方

| 対象 | 形式 | 例 |
|---|---|---|
| 仕様書 | `docs/specs/Issue番号(3桁)-名前.md` | `docs/specs/014-articles-api.md` |
| ADR | `docs/adr/NNNN-名前.md`(4桁連番) | `docs/adr/0001-database-hosting.md` |
| 機能のブランチ | `feature/Issue番号-名前` | `feature/14-articles-api` |
| セットアップ・設定のブランチ | `chore/Issue番号-名前` | `chore/11-rails-new` |
| 修正のブランチ | `fix/Issue番号-名前` | `fix/15-title-validation` |
| 方針文書のブランチ | `docs/名前` | `docs/development-flow` |

## PR に書くこと

[PR テンプレート](../.github/pull_request_template.md)の欄に従う。

- 対応する Issue と仕様書(`Closes #番号`)
- 何を変えたか
- なぜそう書いたか(代替案があれば、選んだ理由)
- 動作確認の方法と結果

## ブランチ保護

`main` に Ruleset を設定済み。一人開発では自分の PR を自分で承認できないため、次の設定にしている。

- `main` への直接 push、force push、ブランチ削除を禁止し、変更は PR 経由にする
- 承認数は 0
- CI の成功を必須にする(CI 導入後に追加する)
