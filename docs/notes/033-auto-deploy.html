自動デプロイと、サービスアカウントの権限借用

Issue #33 で、main にマージするたびに、GitHub Actions が本番へのデプロイを自動で行うようにします。このノートは、仕様書を決める前に、全体の流れと、GitHub Actions が Google Cloud に入るための「サービスアカウントの権限を借用する方法」を図にしたものです。Rails を本番に置いたときのノート「置き場と、動かす場所と、鍵の金庫」と、Issue #8 の「ID トークンの署名」を下敷きにしています。

サービスアカウントは、Google Cloud の中にある、人ではなくプログラムのためのアカウントです。権限(ロール)は、このアカウントに付けます。

権限借用は、別のプログラム(このノートでは GitHub Actions)が、サービスアカウントの権限を一時的に使うことです。

このページで分かること

  • なぜ権限借用の仕組みが必要なのか(1章)
  • 誰が登場し、それぞれ何者か。仕様書に出てくる名前の意味(2章)
  • マージしてから本番が新しくなるまでに、何が起きるか(3章)
  • GitHub の OIDC トークンが、誰の手を通って deployer のアクセストークンに替わるか。鍵ファイルを使わない理由(4章)
  • 仕様書で決める5つの事項と、その理由(5章)

1出発点:なぜ権限借用の仕組みが必要なのか

今は、オーナーが手元で、次の4つを順に行って、本番を新しくしています(production-setup.md の 3 章と 4 章)。

  1. Rails のイメージをビルドし、Artifact Registry に置く
  2. Cloud Run のジョブ migrate のイメージを替えて実行し、表を更新する
  3. Cloud Run のサービス api のイメージを替える
  4. Vue をビルドし、Firebase Hosting に置く

手で行うと、時間がかかるうえに、順番を間違えたり(表を更新する前に新しいコードを動かす)、コミットしていない変更を混ぜてビルドしたりする心配があります。そこで Issue #33 では、この4つを、main にマージするたびに GitHub Actions(GitHub が用意する、決めた手順を自動で行う仕組み)に行わせます。

困るのは、Google Cloud が「誰からの操作か」が分かるものしか受け付けないことです。オーナーが手で行うときは、オーナーの Google アカウントでログインしているので、Google Cloud はオーナーからの操作だと分かり、受け付けます。ところが、GitHub Actions には Google アカウントがありません。

昔からある方法は、Google Cloud でサービスアカウント(2章)の鍵ファイルを作り、GitHub に預けておくことです。ただ、この鍵ファイルは、消すまでずっと使えます。漏れると、誰でも本番を操作できてしまいます。

そこで Issue #33 では、鍵ファイルを預けずに、GitHub が発行する OIDC トークンを Google Cloud に提示し、デプロイ用のサービスアカウントの権限を、その場で1時間だけ借用する方法を使います。この仕組みを、Workload Identity 連携と呼びます。形は、Issue #8 で作った「Vue が提示する ID トークンを、Rails が検証する」とほぼ同じです(4章)。

2登場人物

GitHub の側に2人、Google Cloud の側に5人、両方を操作する オーナー が1人です。Artifact Registry、Cloud Run、Firebase Hosting は、どれも「デプロイで新しくするもの」なので、同じ赤で描きます。色は、このページの図と本文で共通です。

オーナー人 · GitHub と Google Cloud の両方の画面を操作する準備(Workload Identity 連携と deployer を作る)を1回だけ手で行います。その後は、PR を main にマージするだけです。

GitHubインターネットの先 · GitHub が運営するリポジトリを預かり、GitHub Actions を動かします。ジョブに、署名つきの OIDC トークン(「このジョブは、どのリポジトリの、どの Environment で動いているか」を書いたもの)を発行します。リポジトリの設定で作る Environment(下の「GitHub の Environment」)も、GitHub が持ちます。

deploy.yml のジョブGitHub Actions のランナー · 私たちが書くGitHub Actions への指示書を ワークフロー(.github/workflows/ の yml ファイル)と呼び、その中の「1台のランナーで順に実行する手順のまとまり」を ジョブ と呼びます。今あるワークフローは CI(ci.yml)だけです。Issue #33 では deploy.yml を追加し、デプロイの手順をジョブ1つに書きます。ジョブは、GitHub Actions が用意するランナー(ジョブごとに用意され、終了後に破棄される仮想マシン)で動きます。

Workload Identity 連携Google Cloud の中 · Google が用意し、オーナーが設定する外(GitHub)から来た OIDC トークンを検証し、条件に合えば、サービスアカウントの権限の借用を許可する仕組みです。「どこが発行した OIDC トークンを、どんな条件なら信じるか」は、オーナーが登録します。中では、Security Token Service と IAM Credentials API の2つが働きます(4章)。

deployerGoogle Cloud の中 · オーナーが作るデプロイ用に新しく作るサービスアカウント(冒頭の説明)です。Issue #30 で作った api-runtime(Rails が動作するときのサービスアカウント)も、サービスアカウントの1つです。何をしてよいかは、ロール(できることのまとまり。例:「Artifact Registry 書き込み」= イメージを保存できる)を付けて決めます。deployer には、デプロイに必要なロールだけを付与します。

Artifact Registry、Cloud Run、Firebase HostingGoogle Cloud の中 · Issue #30〜#32 で作ったArtifact Registry はイメージの保存先、Cloud Run は Rails を動かす場所(サービス api とジョブ migrate)、Firebase Hosting は Vue を配る場所です。操作のリクエストを受けると、リクエストを送ったサービスアカウントに、そのロールが付いているかを確認します。

GitHub の Environment

Environment は、GitHub のリポジトリの設定画面(Settings → Environments)で作る、デプロイ先の名前です。Issue #33 では production を1つ作ります。Environment はリポジトリごとに作るものなので、「このリポジトリの Environment production」は、このリポジトリの設定画面で作った production のことです。

deploy.yml のジョブ は、「自分は production へのデプロイだ」と宣言して動きます。Issue #33 では、Environment に3つの役目があります。

役目中身
値の保存先Vue の設定値(5章の B)を置く。production を宣言したジョブだけが読める
使えるブランチを絞るmain からしか使えないようにする
OIDC トークンに書かれるGitHub は、production を宣言したジョブの OIDC トークンに「Environment: production」と書く。Workload Identity 連携 はそれを見て、deployer の権限の借用を許可するかを決める(4章、5章の D)

「ジョブ」という言葉が2つ出てきます。deploy.yml のジョブ は GitHub Actions の手順のまとまりで、Cloud Run のジョブ migrate は「表を更新して終わる Rails」です。名前は同じですが、別のものです。このノートでは、前者を「deploy.yml のジョブ」、後者を「ジョブ migrate」と書き分けます。

3全体の流れ

全体を5つの場面に分けました。場面 0 は最初に1回だけ、場面 1〜4 はマージのたびに起きます。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。deployer は、自分からは動かないので、縦の線にはしていません(4章の図3 に描きます)。

場面 0:準備最初に1回だけ、手で

  1. オーナー が、Google Cloud のコンソールで、Workload Identity 連携 を設定し、「GitHub が発行した、このリポジトリの、Environment production のジョブの OIDC トークンだけを信じる」と登録する
  2. オーナー が、deployer を作り、デプロイに必要なロールだけを付与する。さらに、Workload Identity 連携 を通った相手に deployer の権限の借用を許可する、と deployer の権限に登録する
  3. オーナー が、GitHub で Environment production を作り、main からしか使えないようにする。Vue の設定値(Vue が本番の Firebase につなぐための4つの値。5章の B)を置く

今は、仕様書を決めている段階です。仕様書が決まったら、最初に手を動かすのが、この場面 0 です。Issue #33 で新しく作るのは、場面 0 の準備と、場面 2〜4 を行う deploy.yml です。場面 1 の CI は、今もあります。

場面 1:マージと CIマージのたび

  1. オーナー が、PR を main にマージする
  2. GitHub が、CI(ci.yml)を動かし、テストと静的解析で、マージした後のコードを確認する

場面 2:権限の借用CI が成功したら

  1. GitHub が、deploy.yml のジョブを起動する。deploy.yml のジョブ が要求すると、GitHub は OIDC トークンを渡す
  2. deploy.yml のジョブ が、Workload Identity 連携 に OIDC トークンを提示する
  3. Workload Identity 連携 が、OIDC トークンが本物か、条件に合うかを検証し、deploy.yml のジョブ に deployer のアクセストークンを渡す

CI が失敗したときは、場面 2 から先は起きません。テストを通過したコードだけが、本番に反映されます。

場面 3:デプロイ場面 2 のすぐ後

deploy.yml のジョブ が、deployer のアクセストークンを付けて、次の4つを順に依頼します。今オーナーが手で行っている4つと同じです(1章)。依頼を受けた側は、そのたびに、deployer にそのロールが付いているかを確認してから実行します。

  1. deploy.yml のジョブ が、Rails のイメージをビルドし、Artifact Registry に置く
  2. deploy.yml のジョブ が、Cloud Run のジョブ migrate のイメージを替えて実行し、表の更新が終わるまで待つ
  3. deploy.yml のジョブ が、Cloud Run のサービス api のイメージを替える
  4. deploy.yml のジョブ が、Vue をビルドし、Firebase Hosting に配る

途中のどれかが失敗したら、そこで止まり、その先は行いません。たとえば 2 が失敗したら、3 と 4 は行わないので、本番は前の版のまま動き続けます。

場面 4:結果場面 3 の後

  1. deploy.yml のジョブ が、GitHub に、成功したか失敗したかを記録する。ジョブが終了すると、ランナーは破棄される
  2. GitHub が、リポジトリの画面(Actions のタブと Environment の履歴)で、オーナー に結果を表示する

4OIDC トークンが、アクセストークンに替わるまで

3章の場面のうち、安全に関わるのは場面 2 です。この章では、場面 2 を拡大し、GitHub が発行した OIDC トークンが、誰の手を通って deployer のアクセストークンに替わり、どこで失効するかを追います。

deployer と、deployer のアクセストークン

先に、2つを分けておきます。deployer は、Google Cloud の中にずっとあるサービスアカウントで、外には出ません。deploy.yml のジョブ が受け取るのは、「deployer として、1時間だけ操作してよい」というアクセストークンです。このアクセストークンを付けたリクエストは、deployer からのリクエストとして扱われます。たとえると、次のようになります(たとえ話の言葉は、この表の中だけで使います)。

たとえ話このアプリでは
会社に登録された社員deployer(Google Cloud の中にあり、外に出ない)
その社員が入ってよい部屋deployer に付けたロール
外の会社が書いた紹介状GitHub の OIDC トークン
紹介状を確認し、入館証を出す受付Workload Identity 連携
その社員として、1時間だけ使える入館証deployer のアクセストークン
入館証を持って部屋に入る人deploy.yml のジョブ
部屋の入口で、入館証の社員に許可があるかを確認するArtifact Registry などが、deployer のロールを確認する

形は、Issue #8 で作った、Rails が ID トークンを検証する仕組みとほとんど同じです。発行する側、提示する側、検証する側が入れ替わっただけです。

違うのは、検証した後に、OIDC トークンをアクセストークンに交換するところです。Artifact Registry、Cloud Run、Firebase Hosting は、GitHub の OIDC トークンを直接は受け付けません。Google Cloud のサービスアカウントのアクセストークンを付けたリクエストだけを受け付けます。そのため、Workload Identity 連携 で、OIDC トークンを deployer のアクセストークンに交換します。

トークンは受け渡されるのではなく、2回交換される

図3 は、同じトークンが順に受け渡されていくように見えますが、実際には、同じトークンが渡っていくわけではありません。deploy.yml のジョブ が、Security Token Service と IAM Credentials API に順にトークンを提示し、そのたびに別のトークンと交換します。交換を行うのは、deploy.yml のジョブ だけです。

交換deploy.yml のジョブが提示するもの提示する先受け取るもの
1回目(②③)OIDC トークン(GitHub が発行)Security Token Service連携トークン
2回目(④⑤)連携トークンIAM Credentials APIdeployer のアクセストークン(deployer の権限で1時間使える)

その後、deploy.yml のジョブ は、このアクセストークンを付けて、Artifact Registry、Cloud Run、Firebase Hosting にリクエストを送ります(⑥)。

3つのトークンの一生

右の列は、その時点で、その順に出てくるトークン(OIDC トークン、連携トークン、アクセストークンのどれか)がどこにあるかです。

順誰が、何をするかある場所
①deploy.yml のジョブ が GitHub に OIDC トークンを要求する。GitHub は「リポジトリ ID 1409915528 の、Environment production のジョブ」などを書き、署名して渡すランナー
②deploy.yml のジョブ が、Security Token Service に OIDC トークンを提示する。Security Token Service は、GitHub の公開鍵で署名を検証し、中身が登録した条件(次の節)に合うかを確認する。合わなければ、ここで拒否するランナーSecurity Token Service
③Security Token Service が、deploy.yml のジョブ に連携トークン(Google の文書では federated token)を渡す。連携トークンは「Workload Identity 連携を通った」ことを示すだけで、まだ deployer としては何もできないランナー
④deploy.yml のジョブ が、IAM Credentials API に連携トークンを提示し、deployer のアクセストークンを要求するランナーIAM Credentials API
⑤IAM Credentials API が、「この相手には deployer の権限の借用を許可する」と登録されているかを確認し(場面 0 の 2)、deployer のアクセストークンを渡す。期限は、初めの値で1時間。deployer そのものは、Google Cloud の中に残るランナー
⑥deploy.yml のジョブ が、アクセストークンを付けて、Artifact Registry、Cloud Run、Firebase Hosting にリクエストを送る(場面 3)。それぞれが、deployer にそのロールがあるかを確認するランナー
⑦ジョブが終了し、GitHub がランナーを破棄する。アクセストークンも、期限が来れば使えなくなるどこにもない

簡略化したところ:図と表では、受け渡しを「deploy.yml のジョブ」がしているように書きました。実際には、ジョブの中で動く Google 製の道具(gcloud、Firebase CLI、Google が配る Action)が、①〜⑤ を自動で行い、期限が近づけば取り直します。私たちは、道具に「どの Workload Identity 連携で、どのサービスアカウントの権限を借用するか」を書くだけです。

Workload Identity 連携は、OIDC トークンのどこを見て借用を許可するか

② で、Security Token Service は、OIDC トークンに書かれた次の3つが、場面 0 で登録した値と合うかを見ます。1つでも違えば断ります。

見るところ登録する値何を断るためか
発行元GitHub ActionsGitHub 以外が作った OIDC トークン
リポジトリ ID1409915528(このリポジトリ)ほかの人のリポジトリのジョブ。名前ではなく数字の ID を見るのは、名前は付け替えたり、消した後に別の人が同じ名前で作ったりできるが、ID は変わらないから
Environmentproductionこのリポジトリの中でも、deploy.yml のジョブ以外(PR の CI のジョブなど)。CI のジョブは Environment を使わないので、OIDC トークンに production と書かれない

さらに、GitHub の側で、Environment production を main からしか使えないようにします。main 以外のブランチのジョブは、production と書かれた OIDC トークンを、そもそも受け取れません。Google Cloud の側と GitHub の側の、二重の絞り込みになります。

鍵ファイルを使わない理由

結論から言うと、長く使える鍵をどこにも置かないので、盗まれて困るものがないからです。比べる相手は、deployer の鍵ファイル(JSON)を作り、GitHub の Secrets(値を隠して置く場所)に入れておく方法です。

  1. 鍵ファイルは、消すまでずっと使える。ログに出てしまう、悪意のある Action に読まれる、などで漏れると、拾った人は、どこからでも、気づいて消すまで本番を操作できます。定期的に作り直す手間も、オーナーの仕事になります。
  2. 権限借用なら、盗まれ得るものが小さい。deploy.yml のジョブが持つのは、期限の短い OIDC トークンと、期限が1時間のアクセストークンだけで、どちらもランナーの中にしかありません。万一盗まれても、使えるのは期限が切れるまでです。また、ほかのリポジトリのジョブが、自分の OIDC トークンの中身(リポジトリ ID や Environment)を書き換えて権限を借用しようとしても、書き換えると署名が合わなくなるので、Security Token Service で断られます。
  3. 隠れた損は、準備の手間だけ。場面 0 で、Workload Identity 連携と条件を1回登録する手間が増えます。動き出した後の手間は、鍵ファイルの方法より少なくなります(作り直しがない)。Google の文書も、Workload Identity 連携は「サービスアカウントの鍵の管理と、安全の負担をなくす」と説明しています(Workload Identity Federation)。

つまり、準備の手間を1回払う代わりに、漏れたときの被害と、鍵ファイルを管理し続ける手間がなくなります。仕様書の「GitHub Actions から Google Cloud には、Workload Identity 連携で入る」と「権限の借用を許可する相手は、リポジトリ ID と Environment で絞る」は、このことです。詳しい判断は ADR 0009 に書きます。

受け持ち:私たちが決めるのは、条件とロールと、数行だけ

検証の仕組みそのものは、GitHub と Google Cloud が受け持ちます。私たちが間違えやすいのは、色を付けた2行です。条件を緩くしすぎると、ほかのリポジトリのジョブにも deployer の権限の借用を許可してしまいます。ロールを多く付けすぎると、アクセストークンが漏れたときに、できることが増えてしまいます。

5仕様書で決める5つのこと

仕様書で決めることは5つです。下の図は、マージから本番の更新までの処理を1列に並べ、5つの決定事項(A〜E)がどの処理に関わるかを示したものです。この章は、前の章の図に戻らなくても読めるように構成しています。

A. いつデプロイを開始するか

対象:オーナー が PR を main にマージすると、GitHub が CI(テストと静的解析)を実行します。その CI の終了後に、deploy.yml のジョブを開始するかどうかです。

決定事項:main へのマージで実行された CI が成功したときだけ開始します。CI は PR の作成時や更新時にも実行されますが、そのときは開始しません。

理由:テストを通過したコードだけを、本番に反映するためです。

B. Vue の設定値をどこに保存するか

対象:④ で、deploy.yml のジョブ が Vue をビルドする処理です。Vue の設定値は、Vue が本番の Firebase(Google ログイン)に接続するための4つの値(API キー、プロジェクト ID、認証ドメイン、アプリ ID)です。Issue #32 では、オーナー が自分の Mac の web/.env.production.local に書き、手元でビルドしました。自動デプロイでは GitHub Actions のランナーでビルドするため、このファイルは存在しません。そのため、値を GitHub に保存しておく必要があります。保存は、最初の準備(場面 0)で1回だけ行います。

決定事項:このリポジトリの Environment production(2章の「GitHub の Environment」)に、秘匿しない形で保存します。

理由:これらの値は、Firebase Hosting がすべての利用者のブラウザに配信する JavaScript に含まれる公開情報です。秘匿しても保護できるものはありません。秘匿しない形であれば、どの値でビルドしたかを GitHub の画面で確認できるため、誤った値に気づきやすくなります。

C. deployer に何を許可するか

対象:① 〜 ④ で、Artifact Registry、Cloud Run、Firebase Hosting は、リクエストを送ったのが deployer であることを確認すると、deployer にその操作の許可(ロール)があるかを確認します。その許可の範囲です。

決定事項:① 〜 ④ に必要な操作だけを許可します。範囲も、使用するリソースだけに限定します(リポジトリ knowledge-library、サービス api、ジョブ migrate)。Firebase Hosting はプロジェクト単位でしか許可を付与できないため、プロジェクトに付与します。

理由:アクセストークンが漏洩した場合でも、操作できる範囲を最小限にするためです。

D. 誰に deployer の権限の借用を許可するか

対象:deploy.yml のジョブ は、GitHub から受け取った OIDC トークンを Workload Identity 連携 に提示し、deployer の権限を借用します(4章)。Workload Identity 連携 が、どの OIDC トークンであれば借用を許可するかです。

決定事項:このリポジトリの、Environment production を宣言したジョブだけに許可します。Environment production は、main ブランチからのみ使用できるように設定します。

理由:他のリポジトリのジョブや、このリポジトリの PR の CI のジョブには、許可しないためです。PR の CI のジョブは Environment production を宣言しないため、OIDC トークンに production が記載されず、借用は拒否されます。

E. 古いイメージをどうするか

対象:① で、deploy.yml のジョブ は、Rails のイメージ(約 192MB)を Artifact Registry に保存します。自動デプロイでは、マージのたびにイメージが1つ増えます。

決定事項:最新の2つだけを残し、それ以外は Artifact Registry に自動で削除させます。

理由:Artifact Registry の無料枠(0.5GB)に収めるためです。2つ残すのは、現在動作しているイメージと、問題があったときに戻すための1つ前のイメージです。
