Google Cloud の全体図と用語

Issue #33 の準備の作業で操作したものが、Google Cloud の中のどこにあり、どういう関係かを、全体図と用語の表で示します。最後に、プログラムが Google Cloud にリクエストを送るときの関係を示します。

要点

  1. Google Cloud では、プロジェクトの中に製品(Cloud Run など)があり、製品の中に、オーナーが作ったリソース(サービス api など)があります。
  2. リソースは、それぞれ IAM ポリシー(許可の一覧)を持ちます。1行は「誰に(プリンシパル)、何を許可するか(ロール)」です。
  3. Rails や GitHub Actions のジョブは、サービスアカウントを使ってリクエストを送ります。リクエストを受けた側は、自分の IAM ポリシーで許可するかを決めます。

プロジェクトの IAM ポリシー

プロジェクト knowledge-library-prod も1つのリソースなので、自分の IAM ポリシーを持っています。ほかのリソースとの違いは、効く範囲です。リポジトリ knowledge-library の IAM ポリシーの行は、そのリポジトリにだけ効きます。プロジェクトの IAM ポリシーの行は、プロジェクトの中のすべてのリソースに効きます(継承)。

プロジェクトの IAM ポリシーの行(一部)意味
オーナーの Google アカウントに「オーナー」オーナーは、プロジェクトの中のすべてを操作できる。どの画面でも操作できるのは、この行があるから
deployer に「Firebase Hosting 管理者」2-1 で付けた行。Firebase Hosting は、リソースごとに許可を付けられないため
api-runtime に「Cloud SQL クライアント」Issue #31 で付けた行。Rails がデータベースに接続できる

コンソールの「IAM と管理」の「IAM」の画面は、このプロジェクトの IAM ポリシーを表示する画面です。サービスアカウントそのものの一覧は、別の「サービス アカウント」の画面にあります。

プロジェクトに付けた行は全体に効くので、許可はできるだけ個々のリソースに付け、プロジェクトに付けるのは必要なものだけにしています。

サービスアカウントが2つで足りる理由

サービスアカウントが必要になるのは、私たちのプログラムが、Google Cloud にリクエストを送るときだけです。このアプリで動くものを全部並べると、次のとおりです。

動くもの種類動く場所Google Cloud にリクエストを送るかサービスアカウント
Rails私たちのプログラムCloud Run送る(Secret Manager、Cloud SQL)api-runtime
deploy.yml のジョブ私たちのプログラムGitHub送る(Artifact Registry、Cloud Run、Firebase Hosting)deployer
Vue私たちのプログラム会員のブラウザ送らない。Firebase Authentication へのログインは会員の Google アカウントで行い、そのほかは Rails を呼ぶだけ不要
Firebase Hosting、Cloud Run などGoogle の製品Google Cloud私たちのプログラムではないので、対象外不要。製品の内部では、Google のサービス エージェントが動く

Firebase Hosting は Google が動かしている製品なので、サービスアカウントを作る必要はありません。ただし、Firebase Hosting にファイルを送る(デプロイする)のは私たちのデプロイのジョブなので、deployer に Firebase Hosting 管理者のロールが必要です。

1つのサービスアカウントで両方を行うこともできますが、その場合、Rails がデプロイの操作もでき、デプロイのジョブが秘密の値も読めてしまいます。サービスアカウントを分けておけば、それぞれが必要なことしかできません。

このプロジェクトには、ほかに Google が自動で作ったサービスアカウント(656607631341-compute@developer…、firebase-adminsdk-fbsvc@…)もあります。このアプリでは使っていませんが、Google の機能が使う可能性があるため、削除しません。

許可している行と、トークンの流れ

自動デプロイのトークンの流れ(033-auto-deploy.html の4章の図3)に、それぞれの操作を許可している行を書き足した図です。

2-6 の1行の読み方

決めること2-6 の1行
どれに対して(リソース)deployer(この IAM ポリシーを持つ側)
誰が(プリンシパル)deploy.yml のデプロイのジョブ(ロールを受け取る側)
何ができるか(ロール)Workload Identity ユーザー(権限の借用)

続けて読むと、「deploy.yml のデプロイのジョブは、deployer の権限を借用できる」です。借用したジョブは、deployer が 2-1〜2-5 で持った権限で操作できます。2-5(「deployer は api-runtime を使ってよい」)と同じ形の1行です。

  • 「どれに対して」は、1行の中には書かれない。どのリソースの IAM ポリシーに書いたかで決まります。Google ドライブで、ファイル A の共有の画面で追加した人が、ファイル A だけを編集できるのと同じです。
  • 「誰が」は、production を宣言したジョブ。ジョブに environment: production の1行を書くと、GitHub はそのジョブの OIDC トークンに "environment": "production" と書き込みます。この1行があるのは deploy.yml のデプロイのジョブだけで、ci.yml の4つのジョブにはありません。ジョブは Google Cloud の外にいてメールアドレスがないため、「プール github を通ってきた、リポジトリ ID 1409915528、Environment production のジョブ」という条件で書きます(下の値。覚える必要はありません)。
  • Workload Identity ユーザーという名前。Workload は人ではなく機械が動かすプログラム、Workload Identity は外のプログラムに身元を与える仕組み(Workload Identity 連携)、ユーザーはサービスアカウントを使う側、という意味です。GitHub 専用ではなく、AWS や Kubernetes などのプログラムにも使います。
principalSet://iam.googleapis.com/projects/656607631341/locations/global/workloadIdentityPools/github/attribute.repo_env/1409915528_production
