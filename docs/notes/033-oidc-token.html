OIDC と、GitHub Actions の OIDC トークン

GitHub Actions のジョブが、鍵ファイルを持たずに Google Cloud を操作できるのは、OIDC という標準の仕組みを使っているからです。このページでは、OIDC の基本を確認したうえで、今コンソールで作成している「プロバイダ github-actions」の各欄が、OIDC のどの部分にあたるかを説明します。

OIDC(OpenID Connect):「相手が誰か」を、発行元が署名したトークンで、別のサービスに伝えるための標準の仕組みです。「Google でログイン」もこの仕組みで作られています。

OIDC トークン:GitHub Actions が、ジョブのために発行する、署名つきのトークンです。「どのリポジトリの、どの Environment のジョブか」が書かれています。形式は JWT(署名の仕組みは、Issue #8 のノート ID トークンの署名)で、OIDC の標準では「ID トークン」と呼ぶものにあたります。

署名:発行元が、自分だけが持つ秘密鍵で、トークンの中身から作る値です。受け取る側は、発行元が公開している公開鍵で、トークンが発行元の作ったものか、書き換えられていないかを検証できます。

要点

  1. GitHub の OIDC プロバイダが、ジョブのたびに、「どのリポジトリの、どの Environment のジョブか」を書いた OIDC トークンを発行し、GitHub の秘密鍵で署名する。
  2. Security Token Service が、GitHub の公開鍵で署名を検証し、属性の条件でリポジトリ ID と Environment を確認する。合えば、deploy.yml のジョブに連携トークンを返す。署名は暗号化ではなく、OIDC トークンの中身は誰でも読める。
  3. deploy.yml のジョブは、連携トークンをさらに deployer のアクセストークンに交換し、そのアクセストークンで Cloud Run などを操作する。

  • 登場人物と、「プロバイダ」と呼ばれるものが2つあること(2章)
  • OIDC トークンが発行され、検証され、交換されるまでの流れ(3章)

1出発点:鍵ファイルを渡さずに、身元を伝える

Issue #33 では、main へのマージのたびに、GitHub Actions のジョブが本番の Google Cloud を操作します。Google Cloud は、リクエストを送ってきたのが誰かを確認できなければ、操作を許可しません。

もっとも単純な方法は、サービスアカウントの鍵ファイルを GitHub に保存し、ジョブがその鍵ファイルを提示することです。しかし鍵ファイルは、削除するまで有効なままで、漏洩すると誰でも使えます(ADR 0009 の【鍵ファイル方式】)。

そこで、すでにジョブのことを知っている GitHub に、身元を証明してもらいます。GitHub は、ジョブが実行されるたびに「このジョブは、リポジトリ ID 1409915528 の、Environment production のジョブである」と書いた OIDC トークンを発行し、GitHub の秘密鍵で署名します。Google Cloud の Security Token Service は、GitHub の公開鍵で署名を検証し、中身を読んで、受け付けるかどうかを決めます。GitHub と Google Cloud の間で、秘密の値を共有する必要はありません。

3全体の流れ

全体を3つの場面に分けました。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。今オーナーが行っている作業は、場面 0 です。

場面 0:準備1回だけ · 今ここ

  1. オーナー が、コンソールで、プール github と プロバイダ github-actions を作成する。プロバイダには、GitHub の OIDC プロバイダの URL、受け付ける対象、属性の対応づけ、属性の条件を書き込む(5章)

今オーナーが作成しているのは、この場面の プロバイダ github-actions です。作成した設定は、場面 2 の ④ で、Security Token Service が参照します。

場面 1:OIDC トークンの発行デプロイのたび

  1. deploy.yml のジョブ が、GitHub の OIDC プロバイダ に、OIDC トークンを要求する。このとき、OIDC トークンの「対象」(宛先)を指定する。ジョブにこの要求を許可するのは、deploy.yml に書く permissions の設定である
  2. GitHub の OIDC プロバイダ が、リポジトリ ID や Environment などを書いた OIDC トークンを作り、GitHub の秘密鍵で署名して、deploy.yml のジョブ に渡す

場面 2:検証と交換デプロイのたび

  1. deploy.yml のジョブ が、Security Token Service に、OIDC トークンと、使うプロバイダの名前(github-actions)を送る
  2. Security Token Service が、GitHub の OIDC プロバイダ に、公開鍵を要求する
  3. GitHub の OIDC プロバイダ が、Security Token Service に、公開鍵を渡す
  4. Security Token Service が、プロバイダ github-actions の設定(発行元の URL、対象、属性の対応づけ、属性の条件)を参照する
  5. Security Token Service が、署名、発行元、対象、期限を検証し、属性の対応づけで OIDC トークンの中身を写し、属性の条件を評価する
  6. すべてに合えば、Security Token Service が、deploy.yml のジョブ に、連携トークンを渡す。合わなければ、交換を拒否する

簡略化と、確認していないこと:② と ③ は、OIDC の標準の手順(受け取る側が、発行元の URL の /.well-known/openid-configuration から公開鍵の場所を知り、取得する)で描きました。GitHub はこの場所で公開鍵を公開しています(2026-11-18 に確認)。Security Token Service が公開鍵をいつ取得し、どれだけ使い回すかは、Google の文書では確認していません。

この後、ジョブは連携トークンを IAM Credentials API に送り、deployer のアクセストークンに交換します。この部分は、ノート 自動デプロイと、サービスアカウントの権限借用 の4章で説明しています。

署名つきのトークンで身元を伝える理由

結論から言うと、受け取る側が、発行元と秘密を共有せずに、中身が発行元の書いたとおりであることを検証できるからです。理由は3つあります。

  1. 共有する秘密(鍵ファイル)で伝える方式は、秘密が長く残る。鍵ファイルは GitHub に保存され、削除するまで有効です。漏洩すると、拾った人がどこからでも使えます。
  2. OIDC トークンは、ほかの人には作れない。署名に使う秘密鍵は GitHub の外に出ません。そのため、ほかの人が、リポジトリ ID や Environment を書き換えた OIDC トークンを作っても、署名の検証に通りません。Security Token Service は、公開されている公開鍵だけで検証できます。
  3. 損は小さい。OIDC トークンはジョブのたびに発行され、期限は短いので、漏洩しても使える時間はわずかです。保存や更新の作業もありません。代わりに、Google Cloud が GitHub の発行元を信頼する設定(プロバイダ github-actions)が1回だけ必要になります。

つまり、1回の設定の手間と引き換えに、長く残る秘密をなくせます。これは ADR 0009 の判断1(【借用方式】を選び、【鍵ファイル方式】を選ばない)の前提です。

署名の検証で分かることと、分からないこと

まず、署名は暗号化ではありません。OIDC トークンの中身は暗号化されておらず、base64 という形式に変換されているだけなので、誰でも読めます。公開鍵で行うのは「復号」ではなく、「この署名は、この中身から GitHub の秘密鍵で作られた」ことの検証です。OIDC トークンの安全性は、中身を隠すことではなく、ほかの人には作れないことから来ています。

署名の検証で分かるのは、「この OIDC トークンは GitHub が発行したもので、中身は書き換えられていない」ことまでです。「このリポジトリのジョブが発行させたものか」は、署名だけでは分かりません。

理由は、GitHub の OIDC プロバイダが1つだけで、世界中のすべてのリポジトリのジョブに、同じ秘密鍵で署名した OIDC トークンを発行しているからです。ほかの人が自分のリポジトリでジョブを動かしても、GitHub が正しく署名した OIDC トークンが手に入ります。

そこで、署名の検証に加えて、OIDC トークンに書かれたリポジトリ ID と Environment を、属性の条件で確認します。Google の文書が、GitHub のプロバイダには条件を「付けなければならない(must)」と書いているのは、このためです。ADR 0009 の判断2(【両方で絞る】)の、入口の側にあたります。

対象(宛先)を確認する理由

GitHub の OIDC トークンは、Google Cloud だけでなく、AWS や Azure などとの連携にも使われます。対象を確認しないと、ほかのサービス宛てに発行された OIDC トークンを、Google Cloud に送って使い回すことができてしまいます。対象が「プロバイダ github-actions」である OIDC トークンだけを受け付ければ、その OIDC トークンは Google Cloud のこのプロバイダのためだけに発行されたものだと言えます。

5名前:OIDC トークンの項目と、プロバイダ github-actions の欄

4章の「書かれていること」には、それぞれ正式な名前(クレーム名)があります。プロバイダ github-actions の欄は、このクレーム名で OIDC トークンの中身を指します。属性の対応づけや条件に出てくる assertion. は、「受け取った OIDC トークンの」という意味です(例:assertion.repository_id は、OIDC トークンの repository_id)。

aud について:プロバイダの「対象」を「デフォルトの対象」にすると、Security Token Service は、aud がプロバイダの完全な名前(//iam.googleapis.com/projects/656607631341/locations/global/workloadIdentityPools/github/providers/github-actions、先頭に https: が付いてもよい)と一致することを求めます(gcloud の文書)。google-github-actions/auth は、初めの値で、この名前を aud に入れるよう GitHub に要求します(Action の README)。実際に入る文字列は、確認していません。

sub について:GitHub の文書によると、2026-07-15 より後に作られたリポジトリでは、sub に所有者とリポジトリの ID が入る新しい書式になります。このリポジトリは 2026-10-08 に作られたので、新しい書式です。Environment を宣言したジョブで、後ろの部分(…)がどうなるかは、文書に書かれていないため確認していません。今回の条件は sub を使わず、repository_id と environment で判定するので、書式の違いは設定に影響しません。

iss と、入力した URL の末尾の /:OIDC トークンの iss の末尾には / がありません。発行元の欄には、Google の文書の例に合わせて、末尾に / を付けた URL を入力しました(google-github-actions/auth の README の例には / がありません)。どちらでも一致と見なされるかは、Google の文書では確認していません。最初の自動デプロイで、交換が成功するかで確認します。

6位置づけ:「Google でログイン」との比較

OIDC は、もともと人のログイン(「Google でログイン」など)のために作られた仕組みです。GitHub Actions は、そのうち「署名つきのトークンの形式」と「公開鍵を公開する方法」を、人ではなくジョブ(プログラム)の身元を伝えるために使っています。

OIDC の役割Google でログインGitHub Actions → Google Cloud(今回)
発行元(OpenID Provider)GoogleGitHub の OIDC プロバイダ
発行されるトークンID トークンOIDC トークン(形式は ID トークンと同じ JWT)
誰か(sub)Google のユーザー IDリポジトリとジョブの情報
受け取る側(Relying Party)Web サービスSecurity Token Service
対象(aud)Web サービスのクライアント IDプロバイダ github-actions の名前
ログイン画面とリダイレクトある(人がログインする)ない(ジョブが直接要求する)
検証の後に起きることWeb サービスが、会員をログイン状態にするSecurity Token Service が、連携トークンを発行する

ログイン画面がないのは、ジョブは人ではないので、パスワードを入力したり、同意の画面で許可したりできないからです。ジョブが GitHub のランナーの上で動いていること自体を、GitHub が知っています。そのため GitHub は、ジョブの要求だけで、OIDC トークンを発行できます。

Issue #8 では、Rails が、Google の公開鍵で Firebase の ID トークンの署名を検証しました(ID トークンの署名)。今回は、Security Token Service が、GitHub の公開鍵で OIDC トークンの署名を検証します。受け取る側が Rails から Security Token Service に、発行元が Google から GitHub に替わりますが、「発行元が署名したトークンを、受け取る側が公開鍵で検証し、中身で受け付けるかを決める」という形は同じです。
