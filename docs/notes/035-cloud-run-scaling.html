Cloud Run のスケール設定と、DB の接続数

アクセスが増えたときに、Cloud Run がインスタンスを増やしても、Cloud SQL の接続数が上限を超えないようにします。このページでは、リクエストが Cloud SQL に届くまでに通る段と、段ごとの上限の数を見渡し、Issue #35 で決める4つの値の関係を説明します。

  • インスタンス:Cloud Run が、Rails のイメージから起動したコンテナ1つ。Cloud Run が、アクセスに応じて台数を増減する。
  • 同時実行数:Cloud Run が、1つのインスタンスに同時に送るリクエストの上限。
  • worker:Puma が起動するプロセス。worker ごとに、自分のスレッドと接続プールを持つ。数は環境変数 WEB_CONCURRENCY で決まる(2章の「Puma、worker、スレッド」)。
  • スレッド:Puma の中で、リクエストを1件ずつ処理する作業の単位。3本あれば、3件を同時に処理できる(2章の「Puma、worker、スレッド」)。
  • 接続:Rails と Cloud SQL の間の通信路。一度作ると、閉じるまで何度でも SQL を送れる。Cloud SQL は、開いている接続を1本ずつ数える(2章の「接続プールと接続」)。
  • 接続プール:Rails の中にある、DB への接続の置き場。接続を使い回して速くし、接続の本数に上限をかける(2章の「接続プールと接続」)。
  • 最大接続数:Cloud SQL が、全体で同時に受け付ける接続の上限。

要点

  1. リクエストは、Cloud Run → インスタンス → Puma のスレッド → DB の接続 の順に進み、それぞれの段に上限の数がある。
  2. 同時実行数を Puma のスレッド数(3)にそろえると、インスタンスに入りきらないリクエストを、Cloud Run が別のインスタンスに送る。
  3. インスタンスが増えても DB の接続数の合計(最大 14)が Cloud SQL の最大接続数(25)に収まるように、最大インスタンス数を 2 にする。

このページで分かること

  • 数を計算して決める必要がある理由(1章)
  • 誰が登場し、それぞれの上限の数がいくつか。worker、スレッド、接続、接続プールとは何か(2章)
  • リクエストが届いてから、インスタンスが止まるまでの流れ(3章)
  • リクエストの数と、DB の接続の数を追う。値を選んだ理由(4章)
  • 設定の名前が、図のどこにあたるか(5章)
  • Issue #35 の作業と完了条件(6章)

1出発点:数を計算して決める理由

Cloud Run は、アクセスが増えると、インスタンスを自動で増やします。インスタンスの中の Rails は、それぞれ自分の接続プールを持ち、Cloud SQL に接続します。そのため、インスタンスが増えるほど、Cloud SQL への接続も増えます。Cloud SQL には最大接続数があり、上限を超えた接続は拒否されます。拒否されると、Rails はリクエストを処理できず、エラーを返します。

つまり、インスタンスの数、1台あたりの接続の数、Cloud SQL の上限は、互いに関係しています。どれか1つを決めると、ほかの値の範囲が決まります。Issue #35 では、この関係を計算して4つの値を決め、計算の過程を docs に残します。

今の設定には、もう1つ問題があります。Cloud Run は、1つのインスタンスに最大 80 件のリクエストを同時に送ります。一方、Puma が同時に処理できるのは 3 件です。4 件目以降は Puma の中で待ちますが、Cloud Run からは、インスタンスにまだ空きがあるように見えます(4章の図5)。

2登場人物と、それぞれの上限

登場人物は5つです。ブラウザ以外は、すべて本番のプロジェクト knowledge-library-prod の中にあります。色は、このページの図と本文で共通です。図1 の数は、Issue #35 で決める値です。

ブラウザ利用者の端末本番の URL を開き、/api/articles などのリクエストを Firebase Hosting に送る。

Firebase HostingFirebase · Issue #32 で設定したVue のファイルを配る。/api で始まるリクエストは、Cloud Run のサービス api に転送する。

Cloud RunGoogle Cloud · Issue #30 と #31 で作ったサービス api では、届いたリクエストをどのインスタンスに送るかを決め、必要ならインスタンスを起動・停止する。ジョブ migrate では、デプロイのたびに Rails を1回だけ動かす。

Puma と Railsインスタンスの中 · 私たちが書いて、設定するPuma は、Rails のアプリを動かす Web サーバー(gem)。スレッドを用意し、1本のスレッドに1件のリクエストを割り当てる。Rails は、DB が必要になると、接続プールから接続を1本借りる。

Cloud SQLGoogle Cloud · Issue #49 で作り直すPostgreSQL のサーバー(インスタンス db)。最大接続数を超える接続は拒否する。2026-12-11 までに、無料お試しから db-f1-micro に作り直す。

図2 は、図1 のインスタンス 1 の中を拡大したものです。この後の2つの節で、図2 の点線の枠(worker)と左の箱(Puma とスレッド)、右の箱(接続プールと接続)を順に説明します。

Puma、worker、スレッド

  • Puma:Rails のアプリを動かす Web サーバー(gem)。インスタンスの中で動き、届いたリクエストをスレッドに割り当てる。
  • worker:Puma が起動するプロセス。worker ごとに、自分のスレッドと接続プールを持つ。数は環境変数 WEB_CONCURRENCY で決まり、このプロジェクトでは初めの値の 1。
  • スレッド:Puma の中で、リクエストを1件ずつ処理する作業の単位。3本あれば、3件を同時に処理できる。

1つのインスタンスには、同時に複数のリクエストが届きます。Puma が1件ずつしか処理できなければ、2件目は1件目が終わるまで待ちます。そこで Puma は、1つの worker(プロセス)の中にスレッドを 3 本用意し、1本のスレッドに1件のリクエストを割り当てます。ローカルの rails s も、同じ Puma が 3 本のスレッドで動いています。ただし、Ruby では、1つのプロセスの中で Ruby のコードを同時に実行できるスレッドは1本だけです(GVL)。スレッドが同時に進められるのは、DB の応答を待つ時間など、Ruby のコードを実行していない部分です。そのため、スレッドを増やしても、その分だけ速くなるわけではありません。

worker と CPU:Puma は、worker(プロセス)を複数起動することもできます。worker はそれぞれ、自分のスレッドと接続プールを持ちます。そのため、worker が 2 つなら、スレッドも接続の上限も、インスタンス1台で2倍になります。worker の数は、CPU の数に合わせるのが一般的です。GVL があるので、1つの worker は CPU を1つしか使えないためです。CPU が複数あるサーバーでは、worker を CPU の数だけ起動して、すべての CPU を使います。

Cloud Run のサービス api のインスタンスは、CPU が 1 つです(設定の値は 1000m)。worker の数を決める環境変数 WEB_CONCURRENCY は設定していないので、worker は初めの値の 1 つです。結果として、CPU の数と worker の数がそろっています。処理できる量を増やすときは、worker を増やすのではなく、Cloud Run がインスタンスの台数を増やします。

インスタンス 1台(Cloud Run が起動する。CPU 1 つ)
└─ Puma の worker 1 つ(プロセス):WEB_CONCURRENCY。設定していないので 1
   ├─ スレッド 3 本:RAILS_MAX_THREADS
   └─ 接続プール(Rails)
      └─ 接続 最大 3 本:RAILS_MAX_THREADS。接続の先は Cloud SQL

接続プールと接続

  • 接続プール:Rails の中にある、DB への接続の置き場。接続を使い回して速くし、接続の本数に上限をかける。
  • 接続:Rails と Cloud SQL の間の通信路。一度作ると、閉じるまで何度でも SQL を送れる。Cloud SQL は、開いている接続を1本ずつ数える。

スレッドが DB にクエリを送るには、DB への接続が必要です。クエリのたびに接続を作ると、通信の確立とパスワードの認証を毎回行うので遅くなります。また、1本の接続を2本のスレッドが同時に使うことはできません。そこで Rails(Active Record)は、作った接続を閉じずに接続プールに置き、スレッドに貸し出します。

  1. スレッドが、接続プールから接続を1本借りる。空いている接続がなければ、上限までは新しく作る
  2. スレッドが、その接続で Cloud SQL にクエリを送る
  3. 処理が終わると、スレッドが接続を接続プールに返す。接続は閉じずに、次のスレッドが使い回す

スレッドは、1本につき接続を最大1本使います。そのため、2つの数はそろえます(図3)。

3全体の流れ

リクエストが届いてからインスタンスが止まるまでを、3つの場面に分けました。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。

場面 1:起動するインスタンスが 0 台のとき、または全台が満杯のとき

  1. Cloud Run が、リクエストを渡せるインスタンスがないとき、新しいインスタンスを起動し、Puma と Rails を動かす。最大インスタンス数(2)を超えては起動しない
  2. Puma が、スレッドを 3 本用意する。Rails の接続プールは、まだ空のまま(接続は、場面 2 の ⑤ で初めて作る)

場面 2:処理するリクエストのたび

  1. ブラウザ が、Firebase Hosting に、/api/articles のリクエストを送る
  2. Firebase Hosting が、Cloud Run のサービス api に、リクエストを転送する
  3. Cloud Run が、処理中のリクエストが同時実行数(3)より少ないインスタンスを選び、その Puma にリクエストを渡す
  4. Puma が、空いているスレッド1本にリクエストを割り当て、そのスレッドで Rails が処理する
  5. Rails が、接続プールから接続を1本借り、Cloud SQL にクエリを送る。接続がまだなければ、このときに作る
  6. Cloud SQL が、Rails に結果を返す。Rails は、処理を終えると、接続を接続プールに返す
  7. Rails が、Cloud Run にレスポンスを返す
  8. Cloud Run が、Firebase Hosting にレスポンスを返す
  9. Firebase Hosting が、ブラウザ にレスポンスを返す

Issue #35 で決めるのは、この場面の ③ の「同時実行数」、④ の「スレッド数」、⑤ の「接続プール」と、場面 1 の「最大インスタンス数」、場面 3 の「最小インスタンス数」です。どれもコードではなく、設定の値です。

場面 3:止めるリクエストがない状態が続いたとき

  1. Cloud Run が、リクエストのない状態が続いたインスタンスを停止する。Cloud Run の文書では、アイドル状態のインスタンスを残すのは最大15分。最小インスタンス数が 0 なので、全台が停止することもある
  2. Rails のプロセスが終了し、Cloud SQL との接続が閉じる

4リクエストの数と、DB の接続の数を追う

3章の流れのうち、Issue #35 で大事なのは「何件のリクエストを、どこで処理し、どこで待たせるか」と「DB の接続が、全体で何本になるか」です。この章では、この2つの数だけを追います。

同時に 7 件のリクエストが届いたとき

例として、同時に 7 件のリクエストが届いたときを、今の設定と変更後の設定で比べます。2つの設定の違いは、Cloud Run がインスタンスの空きを「Puma が処理できる数」で数えるかどうかです。

  • 同時実行数:Cloud Run が、1つのインスタンスに同時に送るリクエストの上限。リクエストの数であり、DB の接続の数ではない。

Issue #35 の設定では、次の3つの数がすべて 3 になります。数は同じですが、数えているものは別です。

数数えているもの決める側
同時実行数 3インスタンスに同時に送るリクエストCloud Run
スレッド 3 本インスタンスの中で同時に処理できるリクエストPuma
接続の上限 3 本Cloud SQL への接続Rails の接続プール

リクエストは、表の上から順に進みます。まず Cloud Run が、インスタンスにリクエストを 3 件まで送ります。次に、Puma が、1件ずつスレッドに割り当てます。最後に、スレッドが接続を1本ずつ借ります。図5 は、このうち上の2行(同時実行数とスレッド)がそろっていないと何が起きるかを描いたものです。

同時実行数をスレッド数にそろえる理由

結論から言うと、同時実行数をスレッド数と同じ 3 にすると、Cloud Run が数えるインスタンスの空きと、Puma が実際に処理できる数が一致するからです。理由は3つあります。

  1. 80 のままでは、Cloud Run が台数を増やす判断を誤る。4 件目以降は Puma の中で待ちますが、Cloud Run は待っているリクエストも「インスタンスが受け付けた数」として数えます。そのため、インスタンスはまだ満杯ではないと判断し、2 台目を起動しません(図5 の上段)。
  2. 3 にすると、処理できない分は別のインスタンスに回る。4 件目は、Cloud Run が別のインスタンスに送ります。すべてのインスタンスが満杯なら、Cloud Run がリクエストを待たせ、一定の時間内に空かなければ 429 を返します(図5 の下段)。
  3. 1 台で処理できる量は減らない。Puma が同時に処理できるのは、もともと 3 件です。同時実行数を 80 にしても、4 件目以降は処理されずに待っているだけなので、3 にして失うものはありません。

つまり、80 のままにする利点はなく、Cloud Run の判断がずれる欠点だけがあります。仕様書 035 の判断 A は、このことです。スレッド数は、Rails 8 の初めの値の 3 のままにします(判断 B)。

DB の接続を数える

次に、Cloud SQL の側から見て、接続が最も多くなるときを数えます。サービス api が最大の 2 台まで増え、同時にジョブ migrate が動いているときです。

使う側計算接続数
サービス api最大インスタンス数 2 × 接続の上限 3 本6
ジョブ migrate接続の上限 5 本(ジョブには RAILS_MAX_THREADS がないため、database.yml の初めの値)5
管理者用の予約PostgreSQL が管理者のために残しておく接続(初めの値)3
合計最大接続数 25 に収まる。余りの 11 は、Cloud SQL が内部で使う接続と、手で接続する作業のための余裕14

同じ式を逆に使うと、DB の側から決まる最大インスタンス数の上限が分かります。予約と余裕を合わせて 5 本残すと、(25 − 5(ジョブ)− 5(予約と余裕))÷ 3(1台あたり)= 5 なので、上限は 5 台です。

参考:CPU を 2 つにするときの増やし方

Issue #35 では設定しません。将来、インスタンスの CPU を増やすときのために、増やし方を残します。上の計算は、worker が 1 つである前提です。結論から言うと、増やすのは WEB_CONCURRENCY(worker の数)で、それに合わせて変えるのは同時実行数と、この章の計算です。RAILS_MAX_THREADS は変えません。

RAILS_MAX_THREADS は、worker 1つあたりの値です。worker はそれぞれ、自分のスレッドと接続プールを持ちます。RAILS_MAX_THREADS=3 は、「worker 1つあたり、スレッド 3 本、接続の上限 3 本」という意味です。worker を 2 にすると、3 本の組が2つになり、インスタンス1台の合計は自動で 6 本になります。

インスタンス 1台(CPU 2 つ)
├─ worker 1:スレッド 3 本、接続 最大 3 本
└─ worker 2:スレッド 3 本、接続 最大 3 本
   → 1台の合計:スレッド 6 本、接続 最大 6 本

もし RAILS_MAX_THREADS を 6 にすると、worker 1つあたりが 6 本になります。合計は、スレッド 12 本、接続 12 本になってしまいます。

設定今CPU 2 つにするとき理由
インスタンスの CPU12worker を増やす前提
WEB_CONCURRENCY(worker の数)なし(1)2CPU の数に合わせる。CPU を増やしても、worker は自動では増えない
RAILS_MAX_THREADS33 のままworker 1つあたりの値
リクエストの同時実行数(Cloud Run)36インスタンス1台で同時に処理できるリクエストが、2 × 3 = 6 件になる

Cloud SQL の計算もやり直します。インスタンス1台の接続は 6 本になります。

ただし、DB の側から決まる最大インスタンス数の上限は下がります。(25 − 5(ジョブ)− 5(予約と余裕))÷ 6(1台あたり)= 2.5 なので、上限は 5 台から 2 台になります。

最大インスタンス数を 2 にする理由

結論から言うと、DB の側から決まる上限 5 台の範囲で、今の利用に足りる最小の台数より1つ多い 2 台にするためです。

  1. 1 台のままでは、台数が増えたときの計算を設定で示せない。今の利用者はオーナーだけなので 1 台で足ります。しかし 1 台では、インスタンスが増えても接続数が上限に収まることを、実際の設定として確認できません。
  2. 5 台にすると、思わぬアクセスで費用が増えやすい。Cloud Run の費用は、インスタンスがリクエストを処理している時間で決まります。最大インスタンス数は、大量のアクセスを受けたときに、費用が増える速さの上限になります。2 台なら、1 台のときの2倍までに抑えられます。
  3. 2 台で困る場面は、今はない。2 台で同時に処理できるのは 6 件です。7 件以上が同時に届く利用は、今はありません。上げるときは、上の式の上限 5 台までは、DB の設定を変えずに上げられます。

つまり、2 台にすると、計算を設定で示せて、費用の上限も小さく保てます。仕様書 035 の判断 C は、このことです。

最小インスタンス数を 0 のままにする理由

結論から言うと、リクエストがない間の費用を 0 にし、その代わりに生じるコールドスタートの時間を、計測して記録するためです。最小インスタンス数を 1 にすると、リクエストがない間もインスタンスが動き続け、課金されます。0 のままにすると、場面 3 で全台が止まった後の最初のリクエストは、場面 1 の起動を待ちます。この待ち時間がどれくらいかを、AC-4 で計測します(仕様書 035 の判断 D)。計測の結果は、フェーズ3 以降の速度改善を考えるときの材料になります。

私たちが決めるのは、4つの値だけ

すること誰がするか
どのインスタンスに送るかを決める。インスタンスを起動・停止する。満杯のときに待たせ、429 を返すCloud Run
スレッドにリクエストを割り当てるPuma(gem)

同時実行数、最大インスタンス数、最小インスタンス数、スレッド数(接続の上限も同じ値)を決める私たち(Issue #35)

Rails のコードは変えません。puma.rb と database.yml は、どちらも環境変数 RAILS_MAX_THREADS を読むので、Cloud Run にこの環境変数を足すだけで、スレッド数と接続プールが同じ値になります。

簡略化したこと

  • 図5 では、インスタンスが満杯になってから 2 台目を起動するように描きました。Cloud Run の文書では、Cloud Run は同時実行数と CPU の使用率がそれぞれ上限の 60% ほどに達した時点で、台数を増やし始めます。
  • Cloud Run がリクエストを待たせる時間は、Cloud Run の文書では、コンテナの平均の起動時間の 3.5 倍か 10 秒の、長いほうです。

確認していないこと

  • 管理者用の予約の 3 は、PostgreSQL の初めの値です。Cloud SQL での実際の値と、Cloud SQL が内部で使う接続の数は確認していません。Issue #49 で DB を作り直した後に、SHOW max_connections と SHOW superuser_reserved_connections で確認します。
  • コールドスタートの時間は、まだ計測していません(AC-4)。
  • 上限を超えるリクエストが来たときの実際の振る舞い(待ち時間と 429)は、フェーズ5 の k6 による負荷試験で確認します。

私たちのコードの側の名前

名前何か図のどこか
WEB_CONCURRENCY環境変数。Puma の worker の数。設定していないので 1。Issue #35 では設定しない図2 の点線の枠(worker 1 つ)
RAILS_MAX_THREADS環境変数。Issue #35 で、Cloud Run のサービス api に 3 を足す図1 の「スレッド 3」と「接続の上限 3 本」の両方、図3 の右
threads threads_count, threads_count(api/config/puma.rb)Puma のスレッド数。RAILS_MAX_THREADS がなければ 3図2 のスレッド 1〜3、図4 場面 1 ②、場面 2 ④
max_connections:(api/config/database.yml)Rails の接続プールの上限。RAILS_MAX_THREADS がなければ 5図2 の接続 1〜3、図4 場面 2 ⑤、図6 の上の3行

max_connections という名前は、database.yml と Cloud SQL の両方に出てきますが、別のものです。database.yml の値は、Rails のプロセス1つが持つ接続の上限です。Cloud SQL の値は、DB 全体で受け付ける接続の上限です。前者を台数分足したものが、後者に収まる必要があります(図6)。
