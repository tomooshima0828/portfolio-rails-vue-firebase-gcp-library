置き場と、動かす場所と、鍵の金庫

Issue #30 で、Rails を本番の Google Cloud で動かします。そのために使う3つの部品(イメージの置き場、動かす場所、鍵の金庫)が何で、どうつながるかを図にしたノートです。作業の前に、Rails が本番で動き出すまでの流れを見渡します。

1出発点:なぜ3つの部品が要るのか

フェーズ1では、Rails はオーナーの Mac の上で、Docker を使って動いていました。Issue #29 では、本番用の箱(Google Cloud のプロジェクト)と、料金を払う財布を用意しました。箱の中は、まだ空です。

Issue #30 では、Mac で動いている Rails を、本番用の箱の中で動かし、インターネットから呼べるようにします。そのためには、3つの問題を解く必要があります。

  1. Rails をどうやって Google まで運ぶか。Rails は、コードだけでは動きません。Ruby と gem も要ります。そこで、全部を1つにまとめた「イメージ」を Mac で作り、Google の中のイメージの置き場(Artifact Registry)に送ります。
  2. 運んだ Rails を、誰が起動し、誰が URL で受け付けるか。自分でサーバーを借りて管理すると、OS の更新や台数の調整まで受け持つことになります。そこで、イメージを渡せば起動と受け付けを引き受けてくれる動かす場所(Cloud Run)を使います。
  3. Rails の起動に要る鍵を、どうやって安全に渡すか。Rails は、暗号化した設定(api/config/credentials.yml.enc)を、鍵で開いて読みます。鍵は、オーナーの Mac にある api/config/master.key の中身です。本番では、このファイルの代わりに、同じ値を環境変数 RAILS_MASTER_KEY で Rails に渡します。鍵をイメージや設定画面に書くと、見える人がみな鍵を手にできます。そこで、鍵を鍵の金庫(Secret Manager)にしまい、決めた相手にだけ渡してもらいます。

Issue #30 のゴールは、本番の URL の /up(Rails が起動しているかを答える入口)が 200 を返すことです。データベースは、まだ繋ぎません(Issue #31)。

3登場人物と、#30 が終わった時点の構成

登場人物は6つです。オーナーは手元の Mac に、ブラウザはインターネットのどこかに、残りの4つは Google の中(本番用の箱)にあります。色は、このページの図と本文で共通です。

オーナー手元の Mac · 人Mac の Docker でイメージを作り、置き場に送る。動かす場所に「この版を動かして」と頼む(デプロイ)。鍵の金庫に鍵を登録する。#30 では、オーナーの Mac で Claude がコマンドを実行する。Google から見ると、どちらもオーナーのアカウントの操作になる。

イメージの置き場(Artifact Registry)Google の中 · #30 で作るイメージを、版ごとに名前(タグ)を付けて保管する。動かす場所に頼まれたら、イメージを渡す。

動かす場所(Cloud Run)Google の中 · #30 で作るイメージから Rails を起動し、URL を付けて公開する。アクセスがなければ 0 台に戻す。金庫に鍵を頼むときは、Rails 専用の身分証(サービスアカウント。人ではなくプログラムに渡す身分)を名乗る。

Rails動かす場所の中 · 私たちが書いたフェーズ1で作った API。起動のときに鍵を受け取り、暗号化した設定を開く。#30 では /up にだけ正しく応答できる(データベースがまだないため)。

鍵の金庫(Secret Manager)Google の中 · #30 で作る鍵を暗号化してしまう。頼んできた相手の身分証を見て、読む権限がある相手にだけ鍵を渡す。

ブラウザインターネット · 誰でも本番の URL を開く。#30 では、オーナーが /up を開いて(または curl で)、200 が返るかを確かめる。

4Rails が動き出し、応答するまでの流れ

Rails が本番で応答するまでを、5つの場面に分けました。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。破線は、条件によって起きることです。

場面 1:準備する#30 で1回だけ

  1. オーナー が、鍵の金庫(Secret Manager) に鍵(config/master.key の中身)を登録する。この作業だけは Claude ではなくオーナーが行う
  2. オーナー が、鍵の金庫(Secret Manager) に「Rails 専用の身分証(サービスアカウント)には、この鍵を読ませてよい」と設定する。読める身分は、この1つだけ

簡略化:図では、部品を使えるようにする設定(API の有効化)、置き場を作る作業、身分証を作る作業を省いています。どれも準備の前に1回だけ行います。7章の表に入れています。

場面 2:デプロイする新しい版を出すたび。#33 から自動

  1. オーナー の Mac で、Docker が api/Dockerfile からイメージを作る
  2. オーナー が、イメージの置き場(Artifact Registry) にイメージを送る
  3. オーナー が、動かす場所(Cloud Run) に「置き場のこの版を、この身分証と、金庫のこの鍵で動かして」と頼む
  4. 動かす場所(Cloud Run) が、イメージの置き場(Artifact Registry) にイメージを頼む
  5. イメージの置き場(Artifact Registry) が、動かす場所(Cloud Run) にイメージを渡す

Issue #30 で手を動かすのは、場面 1 と 2 です。場面 2 は、#33 で GitHub Actions が受け持つようになります。そのときは、図3 の オーナー の縦の線が、GitHub Actions に置き換わります。

場面 3:起動するデプロイの直後と、0 台からアクセスが来たとき

  1. 動かす場所(Cloud Run) が、Rails 専用の身分証を名乗って、鍵の金庫(Secret Manager) に鍵を頼む
  2. 鍵の金庫(Secret Manager) が、その身分証に読む権限があるかを確かめる。なければ鍵を渡さず、デプロイは失敗し、その版は動かない(完了条件 AC-4)
  3. 鍵の金庫(Secret Manager) が、動かす場所(Cloud Run) に鍵を渡す
  4. 動かす場所(Cloud Run) が、鍵を環境変数 RAILS_MASTER_KEY に入れて、Rails を起動する。Rails は、その鍵で暗号化した設定を開く

確かめていないこと:0 台から起動するとき、動かす場所(Cloud Run) がイメージを置き場から読み直すのか、手元に持っているのかは確かめていません。図では、イメージを受け取るのはデプロイのとき(⑥⑦)だけに描きました。鍵は、起動のたびに金庫から受け取ります(⑧〜⑩)。

今の Rails は、起動するときにデータベースの準備(rails db:prepare)もしようとします。#30 ではデータベースがないので、ここで起動に失敗します。そのため、#30 で api/bin/docker-entrypoint からこの処理を外します(仕様書 030 の「判断したこと」)。

場面 4:応答するアクセスのたび

  1. ブラウザ が、本番の URL の /up を開く。リクエストは、まず 動かす場所(Cloud Run) の受付に届く
  2. 動かす場所(Cloud Run) が、動いている Rails にリクエストを渡す
  3. Rails が、動かす場所(Cloud Run) に 200(起動している)を返す
  4. 動かす場所(Cloud Run) が、ブラウザ に 200 を返す(完了条件 AC-1)

場面 5:0 台に戻るしばらくアクセスがないとき

  1. 動かす場所(Cloud Run) が、Rails を止める。0 台の間は、料金がかからない。次にアクセスが来たら、場面 3 からやり直す(そのぶん、最初の応答は遅くなる)

5鍵を追う

Issue #30 の設定のほとんどは、鍵(RAILS_MASTER_KEY)を誰に見せ、誰に見せないかのために決めています。鍵が、どこに生まれ、誰の手を通り、どこで消えるかを追います。

鍵の一生

右の列は、その時点で鍵がある場所です。番号は、図3 の番号とは別に振っています。

順誰が、何をするかある場所
①フェーズ1で rails new をしたとき、Rails が鍵を作り、api/config/master.key に保存した。.gitignore で除いているので、GitHub には上がっていないオーナーの Mac
②オーナー が、鍵を 鍵の金庫(Secret Manager) に登録する(図3 の ①)。金庫は、1つ目の版として暗号化してしまう。Mac の鍵は、そのまま残るオーナーの Mac鍵の金庫(Secret Manager)
③Docker がイメージを作るとき、api/.dockerignore が config/master.key を除く。イメージには鍵が入らない(図3 の ③)オーナーの Mac鍵の金庫(Secret Manager)
④オーナー がデプロイするとき、動かす場所(Cloud Run) に渡すのは「金庫の rails-master-key の 1 つ目の版」という指し示しだけ。鍵の値は渡さない(図3 の ⑤)オーナーの Mac鍵の金庫(Secret Manager)
⑤起動のとき、動かす場所(Cloud Run) が身分証を名乗って金庫に頼み、鍵を受け取る(図3 の ⑧〜⑩)鍵の金庫(Secret Manager)動かす場所(Cloud Run)。起動中だけ

表のとおり、鍵がずっと残っている場所は、オーナーの Mac と 鍵の金庫(Secret Manager) の2つだけです。イメージの置き場(Artifact Registry) と、動かす場所(Cloud Run) の設定には、一度も鍵が入りません。

私たちがするのは、「誰に読ませるか」と「どの版を使うか」を決めることだけです。鍵を運ぶ処理は書きません。

なぜ、鍵を金庫から渡すのか

結論から言うと、鍵の値を手にできるのが、金庫が認めた身分だけになるからです。

  1. イメージに入れると、イメージを取れる人がみな鍵を持てる。置き場からイメージを取り出せる人や仕組みは、中のファイルも読めます。古い版のイメージにも鍵が残り続けます。
  2. 動かす場所の設定に値を直接書くと、設定を見られる人に鍵が見える。Heroku の Config Vars と同じやり方です。設定画面や、デプロイのコマンドの記録に、鍵がそのまま残ります。
  3. 金庫を使っても、損は小さい。部品が1つ増え、権限を1つ設定する手間はかかります。料金は、無料枠(しまっておく版の数と、読み出しの回数に上限がある)の範囲に収まる見込みです。正確な枠は、作業のときに料金表で確かめます。

つまり、得は「鍵が見える範囲を、金庫と1つの身分証に絞れる」こと、損は「部品と設定が1つずつ増える」ことです。仕様書の完了条件 AC-3 が、このことを確かめます。

なぜ、Rails 専用の身分証(サービスアカウント)を作るのか

結論から言うと、Rails が乗っ取られたときに、できることを「鍵を1本読む」だけに抑えるためです。

  1. 身分証を指定しないと、既定の身分証で動く。動かす場所は、何も指定しないと、Google Cloud が最初から用意している身分証(Compute Engine の既定のサービスアカウント)で Rails を動かします。この身分証には、プロジェクトの作り方によって、箱の中のほとんどを変更できる強い権限(編集者)が付いていることがあります。本番用の箱でどうなっているかは、作業のときに確かめます。
  2. Rails の身分証の権限は、そのまま攻撃者の権限になる。Rails に穴があって乗っ取られると、攻撃者は Rails の身分証で Google Cloud を操作できます。強い権限の身分証なら、データベースの削除や、別の部品の作成までできてしまいます。
  3. 権限は、箱全体ではなく、鍵1本に付ける。「箱の中の鍵をすべて読める」権限にすると、#31 でデータベースのパスワードを金庫に足したとき、それも読めるようになります。必要になったら、そのときに1本ずつ足します。
  4. 専用の身分証を作る損は小さい。作るのは1回だけで、料金もかかりません。イメージを取りに行くこととログを出すことは、動かす場所が自分の身分で行うので、専用の身分証に権限を足す必要はありません。

つまり、手間は1回分で、得は「乗っ取られたときの被害が、鍵1本に限られる」ことです。仕様書の完了条件 AC-2 と AC-4 が、このことを確かめます。

なぜ、鍵の版の番号を指定するのか

結論から言うと、どの値で動いているかを、動かす場所の設定から1つに決められるからです。

  1. 「最新の版」を指定すると、値が混ざる。動かす場所は、起動のたびに金庫から鍵を受け取ります(⑤)。金庫の鍵を新しい版に変えると、その後に起動した Rails だけが新しい値を使い、前から動いている Rails は古い値のままになります。
  2. 番号を指定すれば、値を変えるにはデプロイが要る。鍵を変えたいときは、金庫に新しい版を足し、その番号でデプロイし直します。動いている Rails は、すべて同じ版になります。
  3. 損は、デプロイが1回増えること。鍵を変えるのはまれなので、手間は小さいです。

仕様書の「判断したこと」の「シークレットは版の番号を指定して渡す」が、このことです。

AWS と Heroku で近いもの

Google CloudAWS で近いものHeroku で近いもの
Cloud RunApp Runner(使い勝手が近い)、ECS on Fargate(実務でよく使われる)dyno
Artifact RegistryECR(Elastic Container Registry)Heroku Container Registry。git push で動かすときは、Heroku がビルドしたもの(slug)が置き場にあたる
Secret ManagerSecrets Manager、Systems Manager の Parameter Store近いものはない。Config Vars は、値を設定に直接書くやり方
サービスアカウントIAM ロール近いものはない

使い勝手は Heroku に近いです。サーバーを管理せず、イメージ(Heroku ならコード)を渡せば URL が付いて動きます。違うのは、次の2点です。

  1. 台数と料金。Heroku の dyno は、1台ごとの月額で、基本的には常に起動しています。Cloud Run は、使われていない間は 0 台になり、リクエストを処理した分だけ課金されます(図3 の場面 5)。
  2. 鍵の渡し方。Heroku の Config Vars は、設定画面に値がそのまま見えます。Issue #30 では、このやり方を選ばず、金庫から渡します(5章「なぜ、鍵を金庫から渡すのか」)。

AWS では、ECS on Fargate と比べられることが多いです。ECS on Fargate も、サーバーの管理は要りません。ただし、基本的に1台以上を常に動かす前提で、ロードバランサー(URL の受付)なども自分で組み合わせます。Cloud Run は、受付まで含めて1つの部品にまとまっています。
