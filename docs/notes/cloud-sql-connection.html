1出発点:なぜデータベースと、道と、表を作る係が要るのか

Issue #30 で、Rails は本番の 動かす場所(Cloud Run) で動き出しました。ただ、記事を覚えておく場所がありません。/up(Rails が起動しているかを答える入口)には答えられますが、記事の一覧を頼まれても、読む先がないのでエラーになります。

ローカルでは、Docker の中の PostgreSQL が記事を覚えていました。Issue #31 では、本番用の箱の中にデータベースを用意し、Rails から繋ぎます。そのためには、3つの問題を解く必要があります。

  1. データベースを、どこに用意するか。自分でサーバーを借りて PostgreSQL を入れると、OS の更新やバックアップまで受け持つことになります。そこで、Google が管理してくれる データベース(Cloud SQL for PostgreSQL) を借ります。
  2. Rails からデータベースまでの道を、どう安全にするか。データベースがインターネットから誰でも繋げる状態だと、パスワードが漏れただけで中身を読まれます。そこで、動かす場所(Cloud Run) が用意する 接続口(Cloud SQL 接続) を通り、2つの門(身分証を確かめる門と、パスワードを確かめる門)を抜けた相手だけが繋げるようにします。パスワードは、Issue #30 の鍵と同じく 鍵の金庫(Secret Manager) から渡します。
  3. データベースの中の表を、誰がいつ作るか。借りたばかりのデータベースは空で、記事を入れる表(members と articles)がありません。表を作る・変える作業(マイグレーション)を、表を作る係(Cloud Run のジョブ) が、デプロイのたびに1回だけ行います。

もう1つ、料金の問題があります。データベースは、このプロジェクトで初めて「使っていなくても料金がかかる」部品です。動かしたままで月約1,900円の見込みなので、使わない期間の扱いも決めました(4章の場面 6)。

Issue #31 のゴールは、本番の URL の /api/articles が 200 と記事の一覧を返すことです。記事はまだ入れないので、一覧は空です。記事の投稿にはログインが要るので、Issue #32 で行います。

3登場人物と、Issue #31 が終わった時点の構成

登場人物は6つです。オーナーは手元の Mac に、ブラウザはインターネットのどこかに、残りの4つは Google の中(本番用の箱)にあります。色は、このページの図と本文で共通です。Issue #30 のノートと同じ色にそろえ、このノートで使わない イメージの置き場(Artifact Registry) の色を、データベース(Cloud SQL) に回しました。

オーナー手元の Mac · 人コンソールで、データベースと、Rails が使う DB の利用者 api を作り、そのパスワードを決める。同じパスワードを鍵の金庫に登録する。Rails 専用の身分証に許可を足し、ジョブの実行とデプロイを頼む。

データベース(Cloud SQL)Google の中 · Issue #31 で作るGoogle が管理する PostgreSQL のサーバー1台(インスタンス db)。中に、Rails の表が入るデータベース api_production がある。繋いでくる相手を、2つの門で確かめる。

Rails動かす場所の中 · 私たちが書いたサービスの Rails は、記事の一覧を頼まれると、データベースから記事を読んで返す。ジョブの Rails は、rails db:migrate で表を作って終わる。どちらも同じイメージで、接続口に繋ぐだけで、その先のことは知らない。

鍵の金庫(Secret Manager)Google の中 · Issue #30 で作ったIssue #30 の鍵に加えて、DB のパスワード(db-password)をしまう。読む許可がある身分証にだけ渡す。

ブラウザインターネット · 誰でも本番の URL の /api/articles を開く。Issue #31 では、オーナーが curl で開いて、200 が返るかを確かめる。

4Rails が DB に繋ぎ、記事の一覧を返すまでの流れ

6つの場面に分けました。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。破線は、ときどきしか起きないことです。

場面 1:準備するIssue #31 で1回だけ。作り直すときも

  1. オーナー が、データベース(Cloud SQL) のインスタンス db を作り、その中にデータベース api_production と、Rails が使う利用者 api を作る。api のパスワードは、オーナー が決める。このとき、裏口の名簿(承認済みネットワーク)は空のままにする(5章の図4)
  2. オーナー が、同じパスワードを 鍵の金庫(Secret Manager) に db-password として登録する。この作業は Claude ではなくオーナーが行い、Claude はパスワードを見ない
  3. オーナー が、Rails 専用の身分証(api-runtime)に、2つの許可を足す。「db-password を読んでよい」と「データベースに繋いでよい」

簡略化:図では、部品を使えるようにする設定(Cloud SQL Admin API の有効化)と、データベースの作成を待つ時間(数分〜十数分)を省いています。7章の表に入れています。

場面 2:起動するサービスのデプロイ・0 台からの起動、ジョブの実行のたび

  1. 動かす場所(Cloud Run) が、Rails 専用の身分証を名乗って、鍵の金庫(Secret Manager) にパスワードを頼む
  2. 鍵の金庫(Secret Manager) が、その身分証に読む許可があるかを確かめる
  3. 鍵の金庫(Secret Manager) が、動かす場所(Cloud Run) にパスワードを渡す
  4. 動かす場所(Cloud Run) が、パスワードを環境変数 DB_PASSWORD に入れて、Rails を起動する。同時に、接続口(/cloudsql/…)をコンテナの中に用意する

Issue #30 の場面 3 と同じ流れです。Issue #30 では金庫から受け取るのが RAILS_MASTER_KEY だけでしたが、Issue #31 からは DB_PASSWORD も一緒に受け取ります。

場面 3:繋ぐRails が初めて DB を使うとき

  1. Rails が、接続口 に繋ぐ。Rails から見ると、接続口は /cloudsql/knowledge-library-prod:asia-northeast1:db という名前のファイルで、ここに繋ぐだけで、その先のことは知らない
  2. 動かす場所(Cloud Run) の中の運び役(Cloud SQL Auth Proxy)が、Rails 専用の身分証を名乗って、データベース(Cloud SQL) に繋ぐ。ここからの通信は暗号化される
  3. データベース(Cloud SQL) が、1つ目の門で、その身分証に「データベースに繋いでよい」許可があるかを確かめる。なければ、ここで断る
  4. Rails が、利用者名 api とパスワードを、接続口を通して見せる
  5. データベース(Cloud SQL) の中の PostgreSQL が、2つ目の門で、利用者とパスワードが合っているかを確かめる。合わなければ、ここで断る
  6. データベース(Cloud SQL) が、Rails との接続を開く。Rails は、この接続を手元に取っておき、次からは使い回す(場面 5 の ⑳ では、もう門を通り直さない)

簡略化:⑨⑩ は、実際には、運び役が身分証を使って Google から短い期限の証明書を受け取り、それをデータベースに見せる、という2段階です。図では「身分証を見せる」の1本にまとめました。

場面 4:表を作るデプロイのたび、サービスより先に。Issue #33 から自動

  1. オーナー が、動かす場所(Cloud Run) に「ジョブ migrate を実行して」と頼む。動かす場所(Cloud Run) は、サービスと同じイメージで、ジョブの Rails を起動する(場面 2・3 と同じ)
  2. ジョブの Rails が、rails db:migrate で、データベース(Cloud SQL) に members と articles の表を作る。表がもうあれば、まだ流していないマイグレーションだけを流す
  3. ジョブの Rails が、終わったことを 動かす場所(Cloud Run) に伝えて、止まる
  4. 動かす場所(Cloud Run) が、オーナー に「成功」を返す(コンソールのジョブの画面に出る)。成功したら、オーナー はサービス api をデプロイする(場面 2 へ)

Issue #31 で手を動かすのは、場面 1 と 4 と、サービスのデプロイ(場面 2 のきっかけ)です。場面 4 とデプロイは、Issue #33 で GitHub Actions が受け持つようになります。マイグレーションをジョブで流す理由は、ADR 0006 にあります。

マイグレーションが作るのは、表(入れ物の形)だけです。記事(中身)を入れるのは、会員が記事を投稿したときの Rails です。Issue #31 では記事を入れないので、表は空のままです。

場面 5:応答するアクセスのたび

  1. ブラウザ が、本番の URL の /api/articles を開く。リクエストは、まず 動かす場所(Cloud Run) の受付に届く
  2. 動かす場所(Cloud Run) が、サービスの Rails にリクエストを渡す
  3. Rails が、取っておいた接続を使って、データベース(Cloud SQL) に記事を新しい順に頼む
  4. データベース(Cloud SQL) が、Rails に記事を渡す(Issue #31 の時点では0件)
  5. Rails が、動かす場所(Cloud Run) に 200 と { "articles": [] } を返す
  6. 動かす場所(Cloud Run) が、ブラウザ に 200 と記事の一覧を返す(完了条件 AC-1)

場面 6:使わない期間ときどき

  1. 止める(応急処置):予算アラートのメールが来て、原因を調べる間に費用の増え方を抑えたいときだけ、オーナー がインスタンスを止める。止めている間も、Rails は動いていて /up には 200 を返すが、⑳ で記事を読めないので、/api/articles は 500(エラー)を返す見込み。作業で実際に確かめる(完了条件 AC-6)
  2. 削除する・作り直す:1か月以上使わない見込みのときは、オーナー がインスタンスを削除する。データとバックアップも消える。使うときは、手順書(docs/production-setup.md)で、場面 1 と 4 をやり直す

なぜ「止める」を普段使わないのか:止めている間も、ディスク(約330円)と公開 IP アドレス(約1,100円)の料金が月にかかり、動かしたまま(約1,900円)より月500円ほどしか下がらないからです。削除すれば0円になり、データはテスト用なので失っても困りません。金額は概算です。詳しくは ADR 0007 にあります。

5DB のパスワードを追う

Issue #31 で増える危険は、「データベースに誰が入れるか」です。DB のパスワードが、どこに生まれ、誰の手を通り、どこで使われるかを追うと、設定の理由が分かります。

2つの門

先に、パスワードが使われる場所を見ます。データベース(Cloud SQL) に入るには、門を2つ通る必要があります。

パスワードの一生

右の列は、その時点でパスワードがある場所です。番号は、図3 の番号とは別に振っています。

順誰が、何をするかある場所
①オーナー が、コンソールで利用者 api を作るときに、パスワードを決めて入れる(図3 の ①)。データベース(Cloud SQL) は、パスワードそのものではなく、照合するための形(ハッシュ)で覚えるオーナーの手元(画面)DB(照合用の形)
②オーナー が、同じパスワードを 鍵の金庫(Secret Manager) の db-password に、1つ目の版として登録する(図3 の ②)。その後、手元には残さない鍵の金庫(Secret Manager)DB(照合用の形)
③オーナー が、サービス api とジョブ migrate の設定に、「金庫の db-password の 1 つ目の版を、環境変数 DB_PASSWORD に入れる」という指し示しを書く。値は書かない鍵の金庫(Secret Manager)DB(照合用の形)
④起動のとき、動かす場所(Cloud Run) が身分証を名乗って金庫に頼み、パスワードを受け取って、環境変数に入れて Rails を起動する(図3 の ④〜⑦)鍵の金庫(Secret Manager)Rails(動いている間だけ)
⑤Rails が、api/config/database.yml の password: ENV["DB_PASSWORD"] でパスワードを読み、接続口を通して データベース(Cloud SQL) に見せる。データベース(Cloud SQL) が照合する(図3 の ⑪⑫)鍵の金庫(Secret Manager)Rails(動いている間だけ)
⑥サービスが 0 台に戻るとき、またはジョブが終わったとき、Rails と一緒に、受け取ったパスワードも消える。次の起動では ④ からやり直す鍵の金庫(Secret Manager)DB(照合用の形)
⑦データベースを削除して作り直すとき(図3 の ㉕)、オーナー が新しいパスワードを決め、金庫に2つ目の版として足し、③ の指し示しを2つ目の版に変える鍵の金庫(Secret Manager)。版 1 と 2新しい DB(照合用の形)

表のとおり、パスワードがずっと残っている場所は、鍵の金庫(Secret Manager) だけです。データベース(Cloud SQL) にあるのは照合用の形で、そこからパスワードを取り出すことはできません。イメージにも、動かす場所(Cloud Run) の設定にも、リポジトリにも、パスワードの値は一度も入りません(完了条件 AC-3)。

受け持ちの分け方

すること誰がするか
パスワードを決め、DB と金庫に登録する(①②)オーナー。秘密の値を扱うので、Claude は行わない
身分証に許可を足す、どの版を使うか・どの接続口を開くかを設定する(③)オーナー(コンソール)。Claude は手順を説明し、後から確かめる
身分証を確かめてパスワードを渡す(④)鍵の金庫(Secret Manager)(Google)
パスワードを環境変数に入れる、接続口を用意し暗号化して運ぶ(④⑤)動かす場所(Cloud Run)(Google)
1つ目の門(身分証の許可)、2つ目の門(パスワードの照合)データベース(Cloud SQL)(Google と PostgreSQL)
環境変数を読んで、接続口に繋ぐ(⑤)Rails。Rails が元から持つ仕組み(Active Record)で、私たちが書くのは database.yml の環境変数の名前だけ

私たちのコードで変えるのは、api/config/database.yml の本番の設定だけです。Rails が生成したままだと、本番だけパスワードを API_DATABASE_PASSWORD という名前で受け取るので、開発と同じ DB_PASSWORD にそろえます(仕様書 031 の「判断したこと」)。

なぜ、公開 IP のままで安全と言えるのか

結論から言うと、パスワードだけでは入れず、Rails 専用の身分証も要るからです。

  1. データベースには公開 IP アドレスが付くが、裏口の名簿は空。IP アドレスはインターネット上の住所です。住所があっても、承認済みネットワークが空なので、身分証を持たない相手は門の前に立てません(図4 の下の段)。
  2. 1つ目の門を通れるのは、このプロジェクトで許可を持つ身分だけ。Rails 専用の身分証のほかに、プロジェクトの「オーナー」や「編集者」の身分も通れます。オーナーの Google アカウントと、Issue #30 で見つけた既定の身分証(…-compute@developer.gserviceaccount.com。編集者が付いている)がこれにあたります。パスワードが漏れても、こうした身分がなければ1つ目の門で止まります。身分が乗っ取られても、パスワードがなければ2つ目の門で止まります。
  3. 内部 IP で繋ぐ方式は、もっと閉じられるが、部品が3つ増える。データベースを、インターネットから見えない Google の中の網(VPC)にだけ置く方式です。網、網とデータベースを繋ぐ設定(プライベート サービス アクセス)、Cloud Run から網への出口(Direct VPC egress)を作ることになり、作り直しの手順も長くなります。

つまり、得は「部品が一番少ないまま、門が2つになる」こと、損は「止めている間も公開 IP の料金がかかる」ことと「インターネットから見える住所が1つある」ことです。仕様書 031 の「判断したこと」の「公開 IP と、Cloud Run の Cloud SQL 接続で繋ぐ」が、このことです。完了条件 AC-2 が、名簿が空であることを確かめます。

オーナーの Google アカウントは、プロジェクトのオーナーなので、1つ目の門の許可を持っています。手元の Mac で運び役(Cloud SQL Auth Proxy)を動かせば、Mac からも繋げます。Issue #31 では使いません(マイグレーションはジョブで流すため)。

なぜ、身分証の「繋いでよい」許可を、プロジェクト全体に付けるのか

結論から言うと、データベースは1つだけなので、プロジェクトに付けても、繋げる範囲は変わらないからです。

  1. Cloud SQL には、1つのデータベースにだけ許可を付ける画面がない。Issue #30 では、鍵の金庫の画面から、鍵1本にだけ「読んでよい」を付けました。Cloud SQL には同じ画面がなく、許可はプロジェクトに付けます。
  2. この許可でできることは小さい。「データベースに繋いでよい」(Cloud SQL クライアント)でできるのは、インスタンスの情報を読むことと、1つ目の門を通ることだけです。中身を読むには、さらにパスワード(2つ目の門)が要ります。データベースを消したり設定を変えたりはできません。
  3. 条件で絞る方法もあるが、得がない。許可に「インスタンス db だけ」という条件を付ける方法もありますが、インスタンスは1つしかないので、範囲は同じまま、設定だけが増えます。

つまり、Issue #30 の完了条件 AC-2「プロジェクト全体への権限は持たない」は、この許可の分だけ変わります。仕様書 031 の完了条件 AC-4 が、身分証の許可がこの3つ(鍵2本を読む、データベースに繋ぐ)だけであることを確かめます。
