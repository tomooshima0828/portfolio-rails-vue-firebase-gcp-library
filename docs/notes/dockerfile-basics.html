Dockerfile の基礎

#5 で書く api/Dockerfile.dev と、rails new が作った本番用の api/Dockerfile を例に、Dockerfile の読み方と書き方の基礎をまとめる。

このページで答える問い Dockerfile とは何で、1行ずつ何をしていて、なぜ開発用と本番用で書き方が違うのか。

1.出発点:何に困っているのか

アプリを動かすには、コードだけでなく、OS、Ruby、gem、gem をビルドするための道具など、たくさんのものが必要になる。これを人の手で毎回そろえると、次のことが起きる。

  • 自分の Mac では動くのに、他の人のパソコンや本番のサーバーでは動かない(「手元では動くのに」問題)
  • 何を、どの順番で、どのバージョンで入れたのかが、どこにも残らない
  • 本番のサーバーを作り直すたびに、同じ作業を手でやり直す

そこで、環境の作り方を手順書として書いておき、その手順書から、毎回まったく同じ環境を機械に作らせる。この手順書が Dockerfile である。

2.前提の言葉

  • Dockerfile:イメージの作り方を、上から順に1行ずつ書いた手順書。ファイル名は普通 Dockerfile。このプロジェクトでは、開発用を Dockerfile.dev という名前にする。
  • イメージ:Dockerfile の手順どおりに組み上げ、保存した「環境の型」。中には OS の最小限、Ruby、gem などが入っている。一度作れば、何度でも同じものを使える。
  • コンテナ:イメージから起動した、実際に動いている環境。1つのイメージから、いくつでもコンテナを作れる。
  • ビルド:Dockerfile からイメージを作る作業。docker build や docker compose build で行う。
  • ベースイメージ:Dockerfile の最初に指定する、土台にする既製のイメージ。たとえば ruby:3.4.11-slim は、「Debian(Linux)に Ruby 3.4.11 を入れたもの」を Docker 公式が配っているもの。
  • レイヤー(層):Dockerfile の手順1つごとに作られる、変更分の記録。イメージは、このレイヤーを下から積み重ねたものになっている。
  • キャッシュ:前回のビルドで作ったレイヤーの保存。手順と材料が前回と同じなら、Docker はやり直さずにこれを再利用する。
  • レジストリ:イメージを置いておく倉庫。ベースイメージは Docker Hub から取ってくる。フェーズ2では、自分のイメージを Google Cloud の Artifact Registry に置く。

3.登場人物と全体の流れ

  1. Dockerfile:あなたが、環境の作り方を手順書として書く。
  2. ビルド → レジストリ:Docker が手順書の1行目(FROM)を読み、土台にするベースイメージを Docker Hub から取ってくる。
  3. ビルド:Docker が残りの手順を上から1つずつ実行し、手順ごとにレイヤーを積み重ねる。
  4. ビルド → イメージ:積み重ねたレイヤーが、イメージとして保存される。
  5. イメージ → コンテナ:docker compose up などで、Docker がイメージからコンテナを起動する。このとき、ポートの公開、バインドマウント、環境変数など「動かし方」を compose.yaml で渡す。

押さえておきたい区別:Dockerfile は「何を入れた環境か(型の作り方)」を書く。compose.yaml は「その型をどう動かすか(ポート、マウント、他のコンテナとのつながり)」を書く。

4.Dockerfile.dev を1行ずつ読む

# 開発用のイメージ。本番用は Dockerfile(フェーズ2で Cloud Run に使う)
ARG RUBY_VERSION=3.4.11
FROM docker.io/library/ruby:$RUBY_VERSION-slim

WORKDIR /rails

RUN apt-get update -qq && \
    apt-get install --no-install-recommends -y build-essential git libpq-dev libyaml-dev pkg-config && \
    rm -rf /var/lib/apt/lists /var/cache/apt/archives

ENV BUNDLE_PATH="/usr/local/bundle"

COPY Gemfile Gemfile.lock ./
RUN bundle install

EXPOSE 3000
CMD ["bin/rails", "server", "-b", "0.0.0.0"]
命令この行がすること知っておきたいこと
ARG ビルドのときだけ使う変数 RUBY_VERSION を決める Ruby のバージョンを1か所で変えられるようにするため。本番用の Dockerfile と同じ書き方にそろえている
FROM 土台にするベースイメージを決める。ここでは ruby:3.4.11-slim 必ず最初の命令(ARG を除く)。-slim は余計なものを省いた軽量版で、gem をビルドする道具は入っていない
WORKDIR 以降の命令を実行するフォルダを /rails にする フォルダがなければ作り、そこへ移動する(mkdir と cd を合わせたもの)。コンテナを起動したときも、このフォルダから始まる
RUN(1つ目) Linux のパッケージ管理(apt-get)で、gem のビルドに必要な道具を入れる build-essential は C のコンパイラなど、libpq-dev は pg gem が PostgreSQL につなぐためのライブラリ。最後の rm -rf は、もう要らないパッケージの一覧を消してイメージを小さくする
ENV 環境変数 BUNDLE_PATH を設定し、gem の入れ先を /usr/local/bundle にする イメージの中にずっと残る設定。コンテナの中で動くすべてのコマンドから見える
COPY Mac 側の Gemfile と Gemfile.lock を、イメージの /rails にコピーする コード全体ではなく、この2つだけをコピーする。理由は「5. レイヤーとキャッシュ」で説明する
RUN(2つ目) bundle install で gem を入れる 開発用なので、RSpec などの開発・テスト用の gem も入る
EXPOSE 「このイメージはポート 3000 を使う」と書いておく メモにすぎず、これだけではポートは公開されない。実際の公開は compose.yaml の ports で行う
CMD コンテナを起動したときに、標準で実行するコマンドを決める ここでは Rails のサーバーを起動する。docker compose run --rm api bundle exec rspec のように別のコマンドを指定すると、CMD の代わりにそちらが実行される

-b 0.0.0.0 がないとどうなるか:Rails は開発環境では、標準で localhost だけで待ち受ける。コンテナの中の localhost は「そのコンテナ自身」のことなので、Mac からポートの公開を通して届いたリクエストを受け取れない。0.0.0.0(すべての接続口)で待ち受けるように指定すると、Mac の localhost:3000 から届くようになる。

5.レイヤーとキャッシュ:なぜ Gemfile だけを先にコピーするのか

Docker は手順を1つ実行するたびに、その結果をレイヤーとして保存する。次にビルドしたとき、手順の文面も、コピーするファイルの中身も前回と同じなら、保存したレイヤーを再利用する(キャッシュ)。ただし、どこか1つの手順でやり直しが起きると、それより下の手順はすべてやり直しになる。

もし COPY . .(コード全体のコピー)を bundle install より上に置くと、コードを1文字変えただけで COPY がやり直しになり、続く bundle install も毎回やり直しになる。Gemfile だけを先にコピーするのは、gem が変わらない限り bundle install をやり直さないためである。本番用の Dockerfile も、同じ理由で Gemfile を先にコピーしている。

同じ RUN の中で片付ける理由:apt-get update と install と rm -rf を && でつないで1つの RUN にしているのは、レイヤーが「変更分の記録」だからである。別々の RUN にすると、ダウンロードした一覧が前のレイヤーに残ったままになり、後で消してもイメージは小さくならない。

6.本番用の Dockerfile:マルチステージビルド

rails new が作った本番用の Dockerfile は、FROM が3回出てくる。これはマルチステージビルドという書き方で、作業用の段階と、最終的に残す段階を分けている。

本番では、イメージが小さいほどダウンロードと起動が速く、余計な道具が入っていないほど攻撃されたときの被害が小さい。そのため、作業用の段階で使った道具は最終段階に持っていかない。開発用の Dockerfile.dev は、小ささより分かりやすさを優先して、1段階で書く。

7.開発用と本番用の違い

観点開発用 Dockerfile.dev本番用 Dockerfile
使う場所手元の Docker Compose(#5〜)Cloud Run(フェーズ2〜)
Rails の環境development(指定しない)RAILS_ENV=production
gem開発・テスト用も入れる開発用は入れない(BUNDLE_WITHOUT=development)
コード入れない。バインドマウントで渡すイメージの中にコピーする(COPY . .)
段階1段階3段階(マルチステージ)
実行するユーザーroot専用ユーザー rails
起動時の処理なし(db:prepare は自分で実行)bin/docker-entrypoint が db:prepare を実行してからサーバーを起動

本番のコンテナは、作ったら中身を変えずにそのまま動かす。コードを変えたら、イメージを作り直して入れ替える。開発のコンテナは、コードを何度も書き換えるので、コードはイメージに入れずマウントで渡す。この使い方の違いが、書き方の違いになっている。

8.ビルドコンテキストと .dockerignore

  • ビルドコンテキスト:ビルドのときに Docker に渡すフォルダ。COPY でコピーできるのは、このフォルダの中のファイルだけ。このプロジェクトでは api/ になる(compose.yaml で指定する)。
  • .dockerignore:ビルドコンテキストから外すファイルの一覧。.gitignore の Docker 版。rails new が作った api/.dockerignore は、master.key、.env*、ログ、一時ファイルなどを外している。鍵や秘密情報がイメージに入るのを防ぐ、大事な安全装置である。

9.例え話:レンタルキッチン

前回のメモ(local-dev-docker.html)と同じく、レンタルキッチンに例える。

例え実際
台所の設備の一覧表(何を、どの順番で設置するか)Dockerfile
一覧表どおりに設備を設置する作業ビルド
設置し終えた台所の「型」(何度でも同じ台所を用意できる)イメージ
型から用意された、実際に料理している台所コンテナ
設置作業の1工程ずつの記録レイヤー
前回と同じ工程は、記録を使ってやり直さないことキャッシュ
設備の一覧表に「コンロは3口」と書いておくだけのメモEXPOSE(実際に使えるようにするのは compose.yaml)

一覧表の上のほうには、めったに変えないもの(床、水道、コンロ)を書き、下のほうには、よく入れ替えるもの(調味料 = gem)を書く。調味料を入れ替えるときは、床から作り直さずに済む。これが「変わりにくい手順を上に、変わりやすい手順を下に」の意味である。
