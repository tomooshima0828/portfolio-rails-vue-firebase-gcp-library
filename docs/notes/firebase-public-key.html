Rails が公開鍵で ID トークンを確かめるしくみ

このページでは、Rails が Google の公開鍵を取りに行き、その鍵で Firebase の ID トークンが本物かを確かめるしくみを説明します。Issue #8(仕様書)で作る、ID トークンの検証の土台になる考え方です。

先に結論を書きます。誰かが Rails に公開鍵を渡すのではありません。Rails が自分で、誰でも見られる Google の URL に公開鍵を取りに行きます。そのとき Rails は、ID トークンを Google に送りません。Rails が Google から借りるのは「見分けるための道具」だけで、本物かどうかの判断は Rails が自分で行います。

  • Vue アプリ
  • Firebase Authentication
  • Rails API
  • Google の公開鍵配布元

01何のためにあるのか

ログインは、Vue アプリと Firebase Authentication の間で行われます。ログインに成功すると、Firebase Authentication が ID トークンを発行し、Vue アプリに渡します。この時点で、Rails は何も知りません。

そのあと、Vue アプリが ID トークンを Authorization: Bearer <ID トークン> の形で Rails に送ります。ここで Rails には困りごとがあります。届いた文字列は、誰でも作れるからです。悪い人が、中身に "sub": "他人の uid" と書いた偽物を送ってくるかもしれません。

そこで Rails は、「この ID トークンは、本当に Firebase が発行したものか。発行のあとで書き換えられていないか」を確かめる必要があります。確かめ方には2つの考え方があります。

A. 毎回、発行した人に聞く

Rails が Firebase に問い合わせる

Rails API ↓ 「このトークンは本物ですか?」(毎回) Firebase Authentication

リクエストのたびに通信が発生するので、遅くなります。Firebase が止まると、Rails も止まります。

B. このプロジェクトのやり方

Rails が手元で見分ける

Rails API ↓ 「公開鍵をください」(ときどき) Google の公開鍵配布元

Rails は公開鍵という道具だけを取ってきて、本物かどうかを自分で計算して確かめます。取ってきた鍵はしばらく保存するので、通信はたまにしか起きません。

B を実現しているのが、電子署名と公開鍵のしくみです。このページは特に、Rails が公開鍵をどう手に入れ、いつ取り直すのかに焦点を当てます。

02前提の言葉

署名
ID トークンの中身と秘密鍵から計算した値です。ID トークンの3つ目の部分(最後のドットのあと)に付いています。中身を1文字でも変えると、署名と合わなくなります。 入館証に押された公印にあたります。
秘密鍵
署名を「作る」ための鍵です。Google だけが持っていて、外には出しません。
公開鍵
秘密鍵と対になる鍵です。署名が本物かを「確かめる」ことしかできず、署名を「作る」ことはできません。だから、誰に見られても困りません。Google は公開鍵を、誰でも見られる URL で配っています。 公印の印影の見本にあたります。
JWKS
JSON Web Key Set の略で、公開鍵を JSON で並べたものです。Firebase の ID トークン用の JWKS は、次の URL で配られています。 https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com
kid
Key ID の略で、鍵の番号です。Google は鍵を複数持っていて、定期的に入れ替えます。ID トークンのヘッダー(1つ目の部分)には、「どの鍵で署名したか」が kid で書かれています。JWKS の中の鍵にも、それぞれ kid が付いています。
max-age
Google が JWKS を返すときに、HTTP のレスポンスヘッダー Cache-Control: max-age=秒数 で示す値です。「この鍵のセットは、この秒数のあいだ保存して使い回してよい」という意味です。

03登場人物

鍵に注目すると、それぞれの登場人物が持っているものは次のとおりです。図と手順でも同じ色を使います。

Firebase Authentication

持っているもの:秘密鍵

ログインに成功した人の ID トークンを作り、秘密鍵で署名してから Vue アプリに渡します。

Google の公開鍵配布元

www.googleapis.com/service_accounts/v1/jwk/securetoken@…

秘密鍵と対になる公開鍵(JWKS)を、誰にでも配ります。誰が何のために取りに来たのかは知りません。

Vue アプリ

持っているもの:ID トークン

ID トークンを受け取り、Rails の API を呼ぶときに付けて送るだけです。鍵には関わりません。

Rails API

持っているもの:取ってきた公開鍵(メモリに保存)

公開鍵を取りに行き、しばらく保存します。届いた ID トークンの署名を、保存した公開鍵で確かめます。

04全体の流れ

矢印の色は、送る側の色です。番号は次の章の手順番号と対応しています。⓪ は、Vue がログインするより前に、Google の中で済んでいる準備です。

④⑤ は毎回は起きません。Rails は取ってきた公開鍵を保存し、保存がないとき、保存の期限が切れたとき、知らない kid のトークンが届いたときだけ取り直します(06 章)。

図の中で、Rails から Firebase への矢印が1本もないことに注目してください。また、④ で Rails が 公開鍵の配布元に送るのは「公開鍵をください」だけで、ID トークンは送りません。Google は、Rails がどのトークンを確かめようとしているのかを知りません。

05流れを手順で追う

図の番号に沿って、誰が誰に何をするのかを見ていきます。

  1. 前もって:Google が、鍵のペアを用意する

    Firebase Authと公開鍵の配布元Vue がログインするより前

    Google が、秘密鍵と公開鍵の1組を作ります。秘密鍵は Firebase Authentication の中にしまい、外には出しません。公開鍵は 公開鍵の配布元の URL に貼り出し、誰でも見られるようにします。

    Firebase Authentication と公開鍵の配布元は、同じ Google が運営する別の窓口です。Vue アプリが話しかけるのは Firebase Authentication だけで、Rails が見に行くのは公開鍵の配布元だけです。2つの窓口をつないでいるのは、この1組の鍵です。ID トークンを1枚発行するたびに、2つの窓口がやり取りするわけではありません。

    Google が鍵を入れ替えるときは、Firebase Authentication の秘密鍵と、配布元に貼り出す公開鍵の両方を、Google が新しくします(06 章)。

  2. Firebase が、ID トークンに秘密鍵で署名する

    Firebase Auth内部の処理

    ログインが成功すると、Firebase Authentication が ID トークンの中身(uid、有効期限、宛先など)を作ります。次に、中身と秘密鍵から署名を計算し、トークンの末尾に付けます。ヘッダーには、どの鍵で署名したかを kid で書きます。

    ID トークンのヘッダー(1つ目の部分を JSON に戻したもの)
    {
  "alg": "RS256",
  "kid": "Google の鍵の番号",
  "typ": "JWT"
}

  3. Firebase が、ID トークンを Vue アプリに渡す

    Firebase Auth→Vue アプリ

    この時点でログインは完了しています。Rails はまだ何も知りません。

  4. Vue アプリが、ID トークンを付けて Rails の API を呼ぶ

    Vue アプリ→Rails API

    Vue アプリが、Authorization: Bearer <ID トークン> を付けて GET /api/me を送ります。Rails から見ると、これは「本物かどうか分からない文字列」です。

  5. Rails が、Google に公開鍵を取りに行く(必要なときだけ)

    Rails API→公開鍵の配布元

    Rails が、JWKS の URL に HTTP の GET を送ります。送るのは「公開鍵をください」というリクエストだけで、ID トークンは送りません。

    ただし、保存してある鍵がまだ使える場合、Rails はこの手順を飛ばします。いつ取りに行くかは 06 章で説明します。

  6. Google が、公開鍵のセットを返す

    公開鍵の配布元→Rails API

    公開鍵の配布元が、公開鍵を並べた JSON(JWKS)を返します。レスポンスヘッダーの Cache-Control: max-age で、保存してよい秒数も伝えます。Rails は、鍵のセットと期限をメモリに保存します。

    JWKS の形(値は省略)
    {
  "keys": [
    { "kid": "鍵の番号A", "kty": "RSA", "alg": "RS256", "use": "sig", "n": "…", "e": "AQAB" },
    { "kid": "鍵の番号B", "kty": "RSA", "alg": "RS256", "use": "sig", "n": "…", "e": "AQAB" }
  ]
}

    n と e が、公開鍵の本体の数値です。鍵が複数並んでいるのは、Google が鍵を入れ替える途中で、古い鍵で署名したトークンと新しい鍵で署名したトークンの両方が出回るためです。

    JWKS の URL は、ブラウザでも開けます。Rails がこの手順でしていることを、人が手で試すのと同じです。2026年11月1日に開いたときは、次の JSON が返りました(n は途中を省略しています)。

    ブラウザで JWKS の URL を開いた結果(2026-11-01)
    {
  "keys": [
    { "alg": "RS256", "kid": "81805e76fd5fa2fd91c2bb39e4b7ef05469bddce", "e": "AQAB", "kty": "RSA", "n": "7E01XMLvsyIH…0tVZw", "use": "sig" },
    { "e": "AQAB", "kty": "RSA", "n": "22q04PsB_qjo…KY7wxw", "use": "sig", "alg": "RS256", "kid": "904b0f91be6eb0867dabbaab587dfc2e33f00a24" }
  ]
}

    この一覧には、次の3つの性質があります。

    性質意味Rails がしていること
    誰が開いても同じログインも API キーも要らない。世界中の誰が開いても、同じ JSON が返る一度取ってきたら、すべてのリクエストで使い回す(06 章)
    ときどき入れ替わるGoogle が鍵を入れ替えると、並ぶ kid が変わる。しばらくたってから開くと、上とは違う kid になっている期限(max-age)が来たら取り直す。知らない kid のトークンが届いたら取り直す(06 章)
    すべてのプロジェクトで共通このアプリ専用の鍵ではない。Firebase Authentication を使うすべてのプロジェクトが、同じ鍵で署名している署名が合うだけでは、他人のプロジェクトのトークンも通ってしまう。そのため、宛先(aud)と発行元(iss)が自分のプロジェクトかも確かめる

  7. Rails が、kid に合う鍵を選び、署名を自分で確かめる

    Rails API内部の処理

    Rails(の中の jwt gem)が、ID トークンのヘッダーの kid を読み、JWKS の中から同じ kid の公開鍵を選びます。そして、その公開鍵を使って、署名がトークンの中身と合うかを計算します。この計算は Rails の中だけで終わり、どこにも問い合わせません。

    • 合った場合:秘密鍵を持つ Google が作ったトークンで、署名のあとで書き換えられていない、と分かります。続けて、有効期限や宛先などの中身を確かめます(仕様書の「検証で確かめること」の表)。
    • 合わなかった場合:偽物か、書き換えられたトークンです。Rails は 401 を返します。

  8. Rails が、結果を Vue アプリに返す

    Rails API→Vue アプリ

    本物なら、Rails は uid で会員を探して(いなければ作って)200 を返します。偽物なら 401 を返します。

06鍵を保存して使い回す

公開鍵はめったに変わりません。そのため Rails は、一度取ってきた鍵のセットをメモリに保存し、次のリクエストからは保存した鍵で手順6だけを行います。Rails が鍵を取り直すのは、次の3つの場面だけです。

場面Rails の動き理由
起動して最初のリクエスト取りに行くまだ何も保存していない
保存の期限(max-age)が過ぎた取り直すGoogle が「この時間までは使ってよい」と示した期限が過ぎた
保存した鍵の中に、トークンの kid がない取り直すGoogle が鍵を入れ替えた直後かもしれない
それ以外取りに行かない保存した鍵で確かめられる

時間の流れで見る

Google は、鍵のペアを同時に何組か持っていて、それぞれに番号(kid)を付けています。Firebase は、そのうちの1組の秘密鍵で ID トークンに署名し、使った鍵の kid をトークンのヘッダーに書きます。下の表の A、B、C は、kid を仮に呼んだ名前です。本物の kid は、長い英数字の文字列です。

max-age が 6 時間だった場合の例です(実際の秒数と、鍵を入れ替える時期は Google が決めます)。

時刻Google 側届いたトークンの kidRails の手元の鍵Rails の動き
前もって鍵のペア A と B を持ち、公開鍵 A と B を配布元に貼り出している。いまは B で署名している—なし—
9:00秘密鍵 B で署名したトークンを発行するBなし取りに行く。A と B を保存し、期限を 15:00 にする。B で確かめる
9:05秘密鍵 B で署名したトークンを発行するBA、B(15:00 まで)取りに行かない。保存した B で確かめる
12:00新しい鍵のペア C を作り、配布元に公開鍵 C を貼り出す(A は外す)。ここから C で署名する—A、B(15:00 まで)何も知らない
13:00秘密鍵 C で署名したトークンを発行するCA、B(15:00 まで)C がないので取り直す。B と C を保存し、期限を 19:00 にする。C で確かめる
13:30秘密鍵 C で署名したトークンを発行するCB、C(19:00 まで)取りに行かない。保存した C で確かめる
19:30秘密鍵 C で署名したトークンを発行するCB、C(期限切れ)期限が切れたので取り直す

12:00 に Google が鍵を入れ替えても、Google は Rails に知らせません。そのため 13:00 には、Rails の手元の鍵が古いまま、新しい鍵 C で署名したトークンが届きます。Rails は「鍵が入れ替わったのかもしれない」と考え、期限の前でも自分で取り直します。

取り直しても kid が見つからなければ、そのトークンは偽物です。悪い人が、適当な kid を書いて作ったトークンだからです。Rails は 401 を返します。

配布元に古い公開鍵 B が残っているのは、ID トークンの有効期限が1時間だからです。鍵を入れ替えた直後は、古い鍵 B で署名したトークンがまだ有効なまま出回っています。そのため Google は、入れ替えのあともしばらく、古い公開鍵も貼り出しておきます。

取り直すかどうかを決めるのは誰か

jwt gem の JWT.decode に、「鍵のセットを返す処理」を jwks: として渡します。jwt gem は、この処理を次のように呼び分けます。

  1. まず、{ kid: "トークンの kid" } を付けて呼びます。Rails 側の処理は、保存した鍵が期限内ならそれを返し、期限切れなら取り直して返します。
  2. 返ってきたセットに kid がなければ、jwt gem はもう一度、{ invalidate: true, kid_not_found: true, kid: … } を付けて呼びます。Rails 側の処理は、invalidate を見て、期限内でも取り直します。

つまり、「kid が見つからない」と気づくのは jwt gem で、「期限が切れたかどうか」と「実際に取りに行くこと」を受け持つのは Rails 側のコードです。

07例え話:入館証と印影の見本

会社のビルに入る場面に置き換えると、次のように対応します。

ビルでの役割このプロジェクト補足

入館証に押された印署名入館証の中身ごとに形が変わる。書き換えると合わなくなる

08なぜこの形なのか

公開鍵を誰でも見られる場所に置いて大丈夫なのはなぜか

公開鍵でできるのは、署名を確かめることだけです。署名を作るには秘密鍵が必要です。悪い人が公開鍵を手に入れても、本物の ID トークンは作れません。

引き換えに守るべきもの:確かめる側は「どの方式で確かめるか」を自分で決めておく必要があります。公開鍵を共通の鍵として使う HS256 や、署名なしの none を受け付けると、公開鍵を知っている人が偽物を作れてしまいます。そのため Rails は RS256 だけを受け付けます。

Rails が ID トークンを Google に送らないのはなぜか

送る必要がないからです。公開鍵さえあれば、本物かどうかは Rails の手元の計算で分かります。問い合わせがない分、速く、Google が一時的に応答しなくても、保存した鍵の期限内なら Rails は動き続けます。

引き換えに失うもの:Firebase 側でユーザーを無効にしても、Rails は気づきません。発行済みの ID トークンは期限(1時間)まで通ります。

鍵を毎回取りに行かないのはなぜか

公開鍵はめったに変わらないので、毎回取りに行くのは無駄です。毎回取りに行くと、リクエストのたびに通信が増えて遅くなり、A の方式(毎回問い合わせる)と同じ弱さを抱えます。

引き換えに必要になるもの:保存した鍵が古くなったときに気づく仕組みです。それが max-age と、知らない kid での取り直しです。

保存の期限を Google の max-age に合わせるのはなぜか

鍵をいつ入れ替えるかを知っているのは Google だけだからです。Rails が勝手に「1日保存する」と決めると、Google が鍵を入れ替えたあとも古いセットを使い続けるおそれがあります。

知らない kid で取り直すのはなぜか

Google が新しい鍵で署名し始めた直後は、Rails の保存したセットに新しい鍵がまだありません。取り直さないと、本物のトークンを偽物として 401 にしてしまいます。期限を待たずに取り直すことで、鍵の入れ替えの直後でも正しく確かめられます。

10似たものとの違い

公開鍵を設定ファイルで持つ方式

発行者と確かめる側が同じ会社なら、公開鍵をファイルや環境変数で Rails に持たせることもできます。この場合は「誰かが Rails に公開鍵を渡す」形になります。Firebase では、鍵を入れ替えるのが Google なので、その都度だれかが Rails の設定を書き換えるわけにはいきません。そのため、Rails が URL から取りに行く形になります。

共通の鍵(HS256)で確かめる方式

HS256 では、署名を作る側と確かめる側が同じ秘密の鍵を共有します。Google が Firebase の秘密の鍵を Rails に渡すことはできないので、Firebase の ID トークンは RS256(秘密鍵と公開鍵)です。

Firebase に失効を問い合わせる方式

Firebase の Admin SDK には、トークンが取り消されていないかを Firebase に問い合わせる checkRevoked があります。これは 01 章の A の方式です。ログアウトやアカウントの停止がすぐ反映される代わりに、毎回の通信が増えます。Issue #8 では作りません。
