ローカル開発の構成:Rails を手元で動かすか、すべて Docker か

#5「Rails API プロジェクトを作る」と ADR 0002 の判断材料。2つの構成を、同じ図の描き方で比べる。

このページで答える問い ARails は Mac で直接動かし、PostgreSQL だけ Docker で動かす構成と、BRails も PostgreSQL もすべて Docker で動かす構成は、何がどう違うのか。

1.出発点:何に困っているのか

開発者(オーナー)は、自分の Mac で Rails API と PostgreSQL を動かし、コードを書いては動作を確かめたい。ところが、Mac に入っているものと、作りたい環境が合っていない。

Mac に今入っているものこのプロジェクトで使うもの本番(フェーズ2)
Ruby3.2.2(rbenv)3.4 系3.4 系(Cloud Run のコンテナ)
PostgreSQL14(Homebrew)1717(Cloud SQL)

この差をどこで埋めるかが、2つの構成の違いになる。Aは Ruby を Mac に入れて埋め、PostgreSQL だけをコンテナに任せる。Bは両方をコンテナに任せ、Mac には Docker 以外を入れない。

2.前提の言葉

  • イメージ:アプリを動かすのに必要なもの(OS の最小限、Ruby、gem など)を1つにまとめた「型」。Dockerfile という手順書から作る。
  • コンテナ:イメージから起動した、実際に動いている実行環境。1つのイメージから、何度でも同じコンテナを作れる。
  • Docker Desktop:Mac でコンテナを動かすためのアプリ。コンテナは Linux 用の仕組みなので、Docker Desktop は Mac の中に Linux の仮想マシンを1台動かし、コンテナはその中で動く。
  • Docker Compose:複数のコンテナ(ここでは api と db)の起動方法を compose.yaml に書いておき、まとめて起動・停止する道具。
  • ポートの公開:コンテナの中で待ち受けているポートを、Mac 側の localhost のポートにつなぐ設定。公開しないポートは、Mac からは見えない。
  • バインドマウント:Mac 上のフォルダ(./api)を、コンテナの中のフォルダ(/rails)として見せる設定。Mac で保存したファイルが、すぐコンテナの中でも見える。
  • rbenv:Mac に複数の Ruby を入れ、フォルダごとに使い分ける道具。今の Mac にも入っている。
  • gem / bundle install:gem は Ruby のライブラリ。bundle install は、Gemfile に書いた gem をまとめて入れるコマンド。
  • Ruby LSP:VS Code で Ruby の補完や定義ジャンプを行う拡張機能。Mac に Ruby と gem があることを前提に動く。

5.日々の作業の流れ

同じ作業を、2つの構成でどう行うかを並べる。Bでは、Rails に関わるコマンドの前に docker compose run --rm api が付く。

場面ARails は MacBすべて Docker
最初の準備ruby-build を更新 → rbenv install 3.4.x(数分かかる)→ bundle installdocker compose build(イメージを作る)
起動docker compose up -d db → bin/rails sdocker compose up
コードを直して確かめる保存してリクエストすれば反映保存してリクエストすれば反映(バインドマウント経由)
テストbundle exec rspecdocker compose run --rm api bundle exec rspec
gem を追加Gemfile を編集 → bundle installGemfile を編集 → docker compose build api(イメージを作り直す)
DB の中を見るpsql -h localhost(Mac の psql)docker compose exec db psql -U postgres
Ruby のバージョンの決め方.ruby-version と rbenvDockerfile.dev の FROM ruby:3.4.x

流れの詳細:GET /up が返るまで

ARails は Mac

  1. ブラウザ → Rails:Mac の localhost:3000/up にリクエストを送る。
  2. Rails:Mac の上で動く Ruby が、Mac のファイルをそのまま読んで応答を作る。
  3. Rails → PostgreSQL:DB を使う場合は localhost:5432 に接続する。Docker が、それを db コンテナへ転送する。

Bすべて Docker

  1. ブラウザ → Docker:Mac の localhost:3000/up にリクエストを送る。Docker が、それを api コンテナのポート 3000 へ転送する。
  2. Rails:コンテナの中の Ruby が、バインドマウントされた /rails(中身は Mac の ./api)を読んで応答を作る。
  3. Rails → PostgreSQL:DB を使う場合は、ホスト名 db のポート 5432 に接続する。compose のネットワークの中だけで完結し、Mac は通らない。

6.例え話:料理と台所

例え実際
自宅の台所Mac
レンタルキッチン(設備の一覧表どおりに毎回同じものが用意される)コンテナ(設備の一覧表が Dockerfile)
調理器具(包丁、コンロ)Ruby と gem
冷蔵庫PostgreSQL
レシピと食材あなたが書くコード(./api)
レンタルキッチンへの受け渡し窓口バインドマウント

Aは、自宅の台所で料理し、冷蔵庫だけレンタルする形。使い慣れた包丁がすぐ手に取れて速い。ただ、自宅の包丁は自分で研いで(Ruby を入れて)管理する必要がある。前から置いてある古い冷蔵庫(Homebrew の PostgreSQL 14)と置き場所(ポート)を取り合うこともある。

Bは、台所ごとレンタルする形。設備の一覧表(Dockerfile)どおりの台所が毎回用意されるので、誰がいつ借りても同じ環境になる。その代わり、器具を1つ足すたびに一覧表を書き換えて台所を用意し直す(イメージを作り直す)必要がある。レシピと食材は窓口(バインドマウント)から受け渡す。

7.比べたときの違い

観点ARails は MacBすべて Docker
Mac の状態に左右されるか左右される(rbenv、Homebrew の PostgreSQL)左右されにくい(Docker だけあればよい)
環境が文書として残るか手順は README などに書く必要があるDockerfile.dev と compose.yaml がそのまま構成の記録になる
本番との近さRuby は Mac 版、本番は Linux 版本番(Cloud Run)と同じく Linux のコンテナで動く
コマンドの手軽さbin/rails ... だけ毎回 docker compose run --rm api が付く
速さファイルを直接読むので速いバインドマウント越しにファイルを読むので、やや遅い(Rails の起動、テストの実行)
gem の追加bundle install だけイメージの作り直しが要る
エディタの補完Ruby LSP がそのまま動くMac に Ruby がないので弱くなる(Dev Containers を使えば補える)
トラブルの切り分け登場人物が少ないDocker の層が1枚増える(ネットワーク、マウント、イメージ)
Docker の理解が深まるかDB のコンテナだけイメージ、マウント、ネットワークまで、フェーズ2の前に手で触れる

緑の太字が、その観点で有利な側。どちらが正解というより、「日々の手軽さ」をとるか、「環境の再現性と本番への近さ」をとるかの違い。

8.押さえておきたい仕組み(B を選んだ場合)

  • 開発用と本番用で Dockerfile を分ける理由:rails new が作る Dockerfile は本番向けで、開発・テスト用の gem(RSpec など)を入れない設定になっている。開発には Dockerfile.dev を別に用意し、本番用はフェーズ2の Cloud Run 用に残す。
  • gem はイメージの中、コードはマウント:gem は bundle install でイメージの中(/usr/local/bundle)に入る。コードは Mac の ./api を /rails にマウントする。置き場所が別なので、マウントしても gem は消えない。gem を変えたときだけイメージを作り直せばよいのは、このため。
  • db のポートを公開しない理由:api と db は、Compose が作るネットワークの中で、サービス名(db)を使って直接話せる。Mac から DB に直接つなぐ必要がないので、公開しない。公開しなければ、Homebrew の PostgreSQL 14 とポートがぶつかることもない。
  • コードの変更がすぐ反映される理由:Rails は開発環境では、リクエストのたびにファイルが変わったかを確かめ、変わっていれば読み直す。バインドマウントで Mac の変更がすぐコンテナに見えるので、A と同じ感覚で開発できる。

9.実務での位置づけと、隣の選択肢

  • 実務では両方ある:チームに新しい人が入ったとき、すぐに同じ環境を作れるように、B(Docker Compose)を採るチームは多い。一方で、速さを重視して A を採るチームや、DB だけ Docker の A を採るチームもある。
  • Dev Containers(3つ目の選択肢):VS Code が、エディタごとコンテナの中で動く仕組み。B の弱点である「エディタの補完が弱い」を解消できる。Rails 8 は rails new --devcontainer で、その設定を生成できる。その代わり、VS Code に強く依存し、設定ファイルも増える。
  • 本番(フェーズ2)との関係:本番の Cloud Run も、イメージからコンテナを起動して動かす。B で「イメージを作る」「コンテナにポートを公開する」「環境変数で接続先を渡す」に慣れておくと、フェーズ2で同じ考え方をそのまま使える。

10.どちらを選ぶかの問い

次の問いに、自分の言葉で答えられる側を選ぶとよい。ADR 0002 の「理由」には、その答えを書く。

  • 毎回 docker compose run --rm api を打つ手間と、Mac の環境に左右されない安心感の、どちらが自分にとって大きいか。
  • フェーズ2(Cloud Run)の前に、イメージやコンテナの仕組みを手で触っておきたいか。
  • エディタの補完が弱くなることを、許容できるか(または、Dev Containers で補う手間をかけるか)。
  • 面接で「なぜこの構成にしたのか」と聞かれたら、何と答えたいか。
