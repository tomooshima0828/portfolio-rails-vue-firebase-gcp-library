トークンを断る場所

GET /api/me に届いたトークンは、Rails の中の3つの場所のどこかで「だめだ」と判断されると、401 になります。このページでは、その3つの場所と、そこから 401 にたどり着くまでの道を整理します。

1断る場所は3つある

3つの場所は、確かめる項目で分担しています。どの場所で断っても、Vue が受け取る返事は同じ 401 と { "error": "unauthorized" } です。iss や aud などの名前は、7章の用語にまとめています。

A

concern

authenticate_member! の 9〜10行目

ヘッダーの形を見る。Authorization: Bearer … の形でなければ断る。

断るときは例外を使わず、その場で 401 を返して return する。

B

jwt gem

verify! の中の JWT.decode(55〜64行目)

6項目を見る。署名(kid〈key ID、鍵の番号〉に合う鍵で確かめる)、alg(algorithm、署名の方式)、exp(expiration time、有効期限)、iat(issued at、発行時刻)、aud(audience、宛先)、iss(issuer、発行者)。

断るときは、jwt gem 自身の例外(JWT::ExpiredSignature など)を投げる。

C

verify!

verify! の 65〜66行目

jwt gem が見ない2項目を見る。sub(subject、誰についてのトークンか。Firebase の uid)が空でないこと、auth_time(authentication time、ログインした時刻)が未来でないこと。

断るときは、最初から InvalidToken を投げる。

2401 にたどり着くまでの道

図の縦の帯は、コードの入れ子です。左の concern が verify! を呼び、verify! が jwt gem を呼びます。処理は上から下へ進みます。緑の矢印は確かめが通った道、赤の矢印は断られた道です。

A で断る道:例外を使わない

  1. concern が、ヘッダーからトークンを取り出せなかった(token が nil)
  2. concern が、render_unauthorized で 401 の返事を作り、return でメソッドを抜ける

verify! を呼ぶ前なので、例外は登場しません。

B で断る道:例外を2回受け渡す

  1. jwt gem が、6項目のどれかで断り、jwt gem 自身の例外(例:期限切れなら JWT::ExpiredSignature)を投げる
  2. verify! の rescue JWT::DecodeError が受け止める。jwt gem の例外は、どれも JWT::DecodeError の子孫だから
  3. verify! が、InvalidToken に変えて投げ直す
  4. concern の rescue InvalidToken が受け止め、401 を返す

C で断る道:verify! の rescue を素通りする

  1. verify! が、sub(subject、uid)か auth_time(authentication time、ログインした時刻)で断り、最初から InvalidToken を投げる
  2. verify! の rescue JWT::DecodeError は、これを受け止めない。InvalidToken は JWT::DecodeError の子孫ではないから
  3. concern の rescue InvalidToken が受け止め、401 を返す

3確かめる項目ごとの一覧

だめなトークンを1種類ずつ、実際に verify! に通して、どの例外が投げられるかを確かめた結果です(jwt 3.3.0)。concern に届くときは、どれも InvalidToken になっています。

4コードの中の位置

図の箱が、コードのどの行にあたるかを示します。

concern(firebase_authenticatable.rb)

def authenticate_member!
  token = request.authorization.to_s[/\ABearer (.+)\z/, 1]
  A return render_unauthorized("…") if token.nil?   # 例外を使わず、その場で 401

  payload = FirebaseIdTokenVerifier.new.verify!(token)   # ここで B と C が起きる
  @current_member = Member.create_or_find_by!(firebase_uid: payload["sub"])
rescue FirebaseIdTokenVerifier::InvalidToken => e      # B と C は、どちらもここに届く
  render_unauthorized(e.message)
end

verify!(firebase_id_token_verifier.rb)

def verify!(token)
  B payload, _header = JWT.decode(token, nil, true, …)   # jwt gem が6項目を確かめる
  C raise InvalidToken, "sub が空です" if payload["sub"].blank?
  C raise InvalidToken, "auth_time が未来です" if payload["auth_time"].to_i > Time.current.to_i

  payload
rescue JWT::DecodeError => e      # B の例外だけを受け止める。C の InvalidToken は素通り
  raise InvalidToken, e.message
end

A、B、C の文字は説明のために付けた印で、実際のコードには書かれていません。

5なぜこの形なのか

  • concern は InvalidToken だけを知っていればよい:jwt gem の例外の種類は10以上あります。それを concern が全部知っていると、あとでライブラリを替えたときに concern まで直すことになります。verify! の中で InvalidToken にそろえているので、concern は jwt gem のことを知らずに済みます。
  • C を verify! に置く理由:sub(subject、uid)と auth_time(authentication time、ログインした時刻)は、jwt gem が確かめてくれない項目です。でも Firebase の公式の手順では確かめることになっています。「Firebase のトークンとして正しいか」を確かめるのは verify! の役目なので、jwt gem のあとに verify! が自分で確かめます。
  • A だけ例外を使わない理由:ヘッダーの形を見るのは concern 自身で、呼び出した先から結果を受け取る必要がありません。その場で返事を作って抜ければ済みます。
  • 本文はいつも同じ:どこで断っても、返事の本文は { "error": "unauthorized" } です。偽物を作ろうとする人に、どの確認で落ちたかの手がかりを与えないためです。理由(e.message)は Rails のログにだけ残します。

6確認用の問い

  1. 期限切れのトークンが届きました。図の上で、どの箱をどの順に通って 401 になりますか。2章の「B で断る道」です。
  2. sub(subject、uid)が空のトークンで投げられた InvalidToken を、verify! の rescue が受け止めないのはなぜですか。2章の「C で断る道」の2番目です。
  3. Google の鍵の配布元が止まっていたら、Vue が受け取るのは 401 と 500 のどちらですか。3章の一覧の、灰色の行です。

7用語

トークンの中の項目の名前は、JWT の標準(RFC 7519)が決めた英語の略です。トークンはリクエストのたびにヘッダーに載せて送るので、名前を短くしてトークンを小さくしています。

トークンの header の項目

名前元の英語意味Firebase の ID トークンでの中身確かめる場所

kidkey ID署名に使った鍵の番号Google の公開鍵のどれか1つの番号B この番号で公開鍵を選ぶ

トークンの payload の項目

名前元の英語意味Firebase の ID トークンでの中身確かめる場所
ississuer発行者。誰がこのトークンを作ったかhttps://securetoken.google.com/<プロジェクト ID>B 自分のプロジェクトの URL か
audaudience宛先。誰に向けたトークンかプロジェクト IDB 自分のプロジェクト ID か
subsubject主体。誰についてのトークンかFirebase の uid(会員を見分ける番号)C 空でないか
iatissued at発行時刻このトークンが作られた時刻B 過去か
expexpiration time有効期限発行時刻の1時間後B 未来か
auth_timeauthentication time(名前は略さない)ログインした時刻利用者が実際にログインした時刻C 過去か

時刻の項目(iat、exp、auth_time)には、Unix 時間が入っています。1970年1月1日 0時(UTC)からの秒数で、たとえば 1793600000 のような数です。

iat と auth_time の違い:Vue 側の Firebase SDK は、ID トークンの期限(1時間)が近づくと、トークンを自動で発行し直します。発行し直すと iat は新しい時刻に変わります。でも、利用者はログインし直していないので、auth_time は最初にログインした時刻のままです。

iss と aud の違い:iss は「Firebase のどのプロジェクトが作ったか」、aud は「どのプロジェクトのアプリが受け取るべきか」です。Firebase ではどちらにも同じプロジェクト ID が入りますが、Rails は、別のプロジェクト用のトークンを流用されないように、両方を確かめます。
