Vitest を RSpec と比べて読む

PR #27 で、Vue の画面と関数のテストを6つ書きました。どれも Vitest というテストの道具で書いています。このページは、RSpec は知っているがフロントエンドのテストは初めて、という人が、そのテストを読めるようになるためのものです。中心にあるのは「偽物」という考え方です。

このページで分かること

  • Vue のテストで、何を確かめたいのか(1章)
  • テストに登場する道具と、それぞれの役割(2章)
  • 1つのテストが、どんな順で動くのか(3章)
  • 偽物とは何か、なぜ要るのか、Rails のテストとどう違うのか(4章)
  • Vitest の名前が、RSpec の何にあたるのか(5章)
  • 実際のテストを1つ、行ごとに読む(6章)
  • PR #27 のテストの一覧と、動かし方(7章)
  • RSpec を知っている人が、つまずきやすいところ(8章)

1出発点:何を確かめたいのか

記事の投稿画面を例にします。確かめたいことの1つは、「Rails が『タイトルが空です』と返したとき、投稿画面はエラーを表示し、一覧画面に移らない」です。確かめたいのは、投稿画面という部品が、受け取った返事に正しく応じるかだけです。

ところが、投稿画面は自分だけでは動きません。送るボタンを押すと、記事を頼む関数、ID トークンを付ける関数、Firebase、ブラウザの通信、Rails、データベースと、次々に先の部品が呼ばれます。全部を本物のまま動かそうとすると、Rails とデータベースを起動し、本物の Google アカウントでログインしておく必要があります。CI では Google のログインができないので、テストが動きません。「Rails がエラーを返す」場面を、狙って起こすのも難しくなります。

そこで、確かめたい部品のすぐ先にいる相手を、テストのときだけ代役(偽物)に入れ替えます。代役は、テストが決めたとおりの返事を返し、どう呼ばれたかを覚えています。こうすると、Rails もログインも本物のブラウザもなしで、部品1つの振る舞いを、何度でも速く確かめられます。これが、このページの中心の考え方です。

2登場人物

テストは、web のコンテナの中の Node(JavaScript を動かす実行環境)で動きます。本物のブラウザも、本物の Rails も使いません。色は、このページの図と本文で共通です。

テストのファイルweb/src の __tests__ の中 · 私たちが書く何を確かめるかを書いたファイル。偽物を用意し、部品を動かし、結果を比べるよう頼む。RSpec の spec ファイルにあたる。

Vitestライブラリテストのファイルを読み込んで動かし、期待どおりかを比べ、結果を出す。偽物を作る道具も持っている。RSpec 本体と rspec-mocks にあたる。

Vue Test Utils と jsdomライブラリVue の画面を1つだけ描き、入力やクリックを起こし、表示を読む。jsdom は、Node の中で動く偽物のブラウザ。Capybara の rack_test にあたる。

テストされる部品web/src · 私たちが書いた本物投稿画面、一覧画面、記事を頼む関数など。テストの主役で、偽物にはしない。

偽物テストの間だけ · Vitest が作る本物の相手の代わりに置く代役。テストが決めた返事を返し、どう呼ばれたかを覚えている。4章で詳しく見る。

本物の相手ネットワークの先などRails、Firebase、本物のブラウザ。テストでは呼ばない。全部をつないだ流れは、手動確認で確かめる。

3全体の流れ:1つのテストが動く順番

1つのテストは、4つの場面で進みます。例は、1章の「Rails が『タイトルが空です』と返したとき」のテストです。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。

場面 0:読み込みテストのファイルを読み込むとき、1回だけ

  1. テストのファイル が、Vitest に「記事を頼む関数を、偽物に差し替えて」と頼む
  2. Vitest が、偽物 を作る。偽物は、本物と同じ名前で、同じように呼べる
  3. Vitest が、投稿画面 を読み込むときに、本物の代わりに 偽物 を渡す。投稿画面 は、偽物だと気づかない

この場面は、テストのファイルの中のどこに書いても、ほかの読み込み(import)より先に動きます。投稿画面が読み込まれる前に、差し替えを済ませておく必要があるためです(8章の 3)。

場面 1:準備テストごと

  1. テストのファイル が、偽物 に「呼ばれたら、『タイトルが空です(422)』と返して」と決める

偽物を使うテストの中心は、この場面です。4章で、偽物の中で何が起きているかを拡大します。

場面 2:実行テストごと

  1. テストのファイル が、Vue Test Utils に、投稿画面を描いて、タイトルと本文を入れて、送るよう頼む
  2. Vue Test Utils が、投稿画面 のフォームに、送信を起こす
  3. 投稿画面 が、記事を頼む関数(本当は 偽物)を呼ぶ
  4. 偽物 が、場面 1 で決めた返事を 投稿画面 に渡す。あわせて、何を渡されて呼ばれたかを記録する
  5. 投稿画面 が、返事を見てエラーを表示する(jsdom の中の画面に描く)

場面 3:確認テストごと

  1. テストのファイル が、Vue Test Utils に、画面に出ている文字を聞く
  2. Vue Test Utils が、テストのファイル に文字を渡す
  3. テストのファイル が、偽物(画面を移す頼みの偽物)に、どう呼ばれたかを聞く
  4. 偽物 が、テストのファイル に記録を渡す(今回は「一度も呼ばれていない」)
  5. テストのファイル が、受け取った文字と記録を、Vitest の expect で期待と比べる。違っていれば、Vitest がテストを失敗にする

簡略化したところ:図2 では、偽物を1つにまとめています。実際のテストには、記事を頼む関数の偽物と、画面を移す頼み(router)の偽物の2つがあります。場面 2 で記録されるのは前者、場面 3 で確かめているのは主に後者です。

4偽物を追う

3章の場面のうち、いちばん大事なのは偽物です。この章では、偽物だけに注目して、生まれてから記録が消されるまでを追います。そのあとで、なぜ偽物が要るのか、Rails のテストとどう違うのかを見ます。

たとえ話:映画の代役

テストの「偽物」は、英語では test double と言います。double は「そっくりな代役」という意味で、映画のスタントの代役(stunt double)が名前の由来です。

映画テストでは
主役の俳優本物の相手(記事を頼む本物の関数。その先に Rails がいる)
代役偽物
監督が、代役に演技を指示するテストのファイル が、偽物に返事を決める
共演者は、相手が代役だと気づかない投稿画面 は、偽物を本物だと思って呼ぶ
撮影の記録を、後で見返す偽物が覚えている「呼ばれ方」を、後で確かめる

偽物の中で起きていること

偽物は、2つのものを持っています。テストが入れる「返事」と、呼ばれるたびに増える「記録」です。

偽物の一生

右の列は、その時点で偽物が持っているものです。例は、1章のテストです。

順誰が、何をするか偽物が持っているもの
生まれるVitest が、ファイルを読み込むときに偽物を作り、投稿画面 に本物の代わりに渡す(図2 場面 0)返事:なし記録:0件
①テストのファイル が、返事を「422、タイトルが空」に決める返事:422記録:0件
② ③投稿画面 が偽物を呼ぶ。偽物は、何を渡されたかを記録し、決められた返事を渡す返事:422記録:1件
④テストのファイル が、記録を見て「正しいものを渡されて呼ばれたか」を確かめる返事:422記録:1件
⑤次のテストの前に、テストのファイル が記録を消す。続けて、返事を「成功」に決め直す返事:成功記録:0件

⑤ で記録を消すのは、偽物がファイルの中で1回しか作られず、テストの間で使い回されるためです。消さないと、前のテストで呼ばれた記録が残り、「一度も呼ばれていない」を確かめるテストが落ちます。RSpec は、この後片付けをテストごとに自動でしますが、Vitest は、このプロジェクトの設定ではしません(8章の 4)。記録を消しても、決めた返事は消えません。なので、⑤ では返事も決め直しています。

なぜ偽物を使うのか

結論から言うと、確かめたい部品の振る舞いだけを、ほかの部品に振り回されずに確かめるためです。理由は3つあります。

  1. 本物の相手は、テストの中でそろえられない。Rails は別のサーバーで動いていて、Vitest の中では起動できません。本物の Google のログインは、CI ではできません。
  2. 本物の相手では、確かめたい場面を起こしにくい。「Rails が 422 を返す」「通信に失敗する」を狙って起こすのは大変です。偽物なら、返事を1行で決められます。
  3. 偽物の方が、確かめたいことがよく見える。「一覧画面に移るよう頼んでいない」のような、何も起きなかったことは、外から見えにくいです。偽物は呼ばれ方を記録しているので、「一度も呼ばれていない」をそのまま確かめられます。

まとめると、得は「速い、何度でも同じ結果になる、どんな場面でも作れる」ことです。損は「偽物を置いたところから先は、本物が動かない」ことです(下の「偽物の限界」)。仕様書 012-articles-ui.md の完了条件で、画面と関数の振る舞いはテスト、全部をつないだ流れ(AC-20)は手動確認、と分けているのはこのためです。

Rails のテストとの違い

偽物にするかどうかの決まりは、Rails でも Vue でも同じです。テストが自分で用意できないもの(自分の外にあるもの)を、偽物にします。違うのは、「自分の外」にあるものの量です。

Rails のテストVue のテスト
いちばん大事な相手データベースRails
その相手を手元で用意できるかできる。Rails がテスト用のデータベースを持ち、テストごとに中身を元に戻せるできない。別のサーバーで動いている
偽物にするもの外のサービスだけ(Google の公開鍵の取得)Rails への頼み、Firebase、ブラウザ(jsdom)、場合によって router

フロントエンドのテストで偽物が多くなるのは、フロントエンドが特別だからではありません。大事なデータが、ネットワークの向こうにあるからです。

偽物の限界

偽物を置いたところから先は、テストでは本物が一度も動きません。その例が、PR #24 で見つかった require "net/http" の抜けです。Rails のテストでは、公開鍵を取る処理を偽物にしていたので、本物の通信の行は一度も動かず、テストはすべて通っていました。手動確認で初めて 500 が出ました。

なので、このプロジェクトでは次のように分けています。

  • 部品ごとの振る舞い:偽物を使ったテストで確かめる。偽物にした先の部品は、その部品自身のテストで確かめる(記事を頼む関数は articles.spec.ts で)
  • 全部を本物でつないだ流れ:手動確認で確かめる(PR #27 の AC-20「ログインして投稿し、一覧に出る」)

本物のブラウザで本物の Rails とつないで操作するテスト(E2E テスト。Rails の system spec にあたる)もありますが、このプロジェクトではまだ書いていません。

偽物と factory の違い

どちらもテストの準備で使いますが、用意するものが違います。

factory(FactoryBot)偽物
用意するものデータ(会員、記事のレコード)呼ばれる相手(関数、通信)
本物か本物。本物のモデルで、本物のデータベースに保存される偽物。本物の代わりに置く
Vitest のテストではファイルの上に書いたデータ(const article = { ... })vi.fn() で作る関数

テストでは、この2つを組み合わせます。PR #27 のテストでも、「偽物が、用意したデータ(article)を返す」形になっています。

8RSpec を知っている人がつまずくところ

  1. describe や it も、ファイルの先頭で読み込む。このプロジェクトの設定では、自動では使えません。
  2. オブジェクトや配列は toEqual、文字や数は toBe。toBe は「同じもの」を比べるので、中身が同じでも、別々に作った配列どうしは落ちます。
  3. vi.mock は、どこに書いても読み込みより先に動く。そのため、vi.mock の中では、ファイルの途中で作った変数を使えません(まだ作られていない)。中で使う偽物は vi.hoisted で作ります(6章の「ファイルの中で、実際に動く順番」)。
  4. 偽物の記録は、自動では消えない。RSpec は、テストごとに偽物を作り直します。このプロジェクトの Vitest の設定では、偽物はファイルで1回だけ作られて使い回されるので、beforeEach で vi.clearAllMocks() を呼びます(図3 ⑤)。
  5. 画面のテストは、待ってくれない。Capybara は、要素が出てくるまで少し待ってくれます。Vue Test Utils は待たないので、操作の後に await flushPromises() を書き、偽物の返事を画面に反映させてから確かめます。
  6. 失敗を確かめるときは、expect の前に await。await expect(…).rejects.toThrow() の await を忘れると、確かめる前にテストが終わり、間違っていても通ります。
  7. jsdom は本物のブラウザではない。たとえば trigger('submit') は送信の出来事を直接起こすので、ブラウザが送る前にする required の確認を通りません。PR #27 では、入力欄に required の属性があるかを確かめ、本物のブラウザでの動きは手動で見ています。

9確認用の問い

  1. 投稿画面のテストで確かめたいのは、誰の振る舞いですか。そのとき、Rails には何か届きますか。1章と図1、図2 です。
  2. 偽物が持っている2つのものは何ですか。それぞれ、誰が入れて、誰が見ますか。4章の図3 と「偽物の一生」です。
  3. Vue のテストで、Rails のテストより偽物が多くなるのはなぜですか。4章の「Rails のテストとの違い」と図4 です。
  4. beforeEach の vi.clearAllMocks() を消すと、どのテストが、なぜ落ちる可能性がありますか。図3 ⑤ と、8章の 4 です。
  5. 偽物を使ったテストがすべて通っても、手動確認が要るのはなぜですか。4章の「偽物の限界」です。
