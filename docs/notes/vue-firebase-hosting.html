1出発点:なぜ Firebase Hosting と、3つのつなぎが要るのか

Issue #31 までで、本番の Rails はデータベースに繋がり、本番の URL の /api/articles に記事の一覧(今は空)を返せるようになりました。ただ、利用者が開く画面がありません。利用者は、記事を読むのも投稿するのも、Vue の画面を通して行います。

ローカルでは、Vite の開発サーバーが Vue の画面を配り、/api へのリクエストを Rails に回していました。本番には、その役をする係がいません。そこで、2つの問題を解きます。

  1. Vue の画面を、どこから配るか。Vue はビルドすると、ただのファイル(HTML、JavaScript、CSS)になります。このファイルを、世界中のブラウザに速く配るサービス Firebase Hosting に置きます。
  2. 置いた画面を、ログインと Rails にどうつなぐか。画面を置くだけでは、ログインも投稿もできません。次の3つをつなぎます。
    • つなぎ1:Firebase Hosting が、/api へのリクエストを Rails に取り次ぐ
    • つなぎ2:本番の Firebase Auth の設定値を、Vue のファイルに埋め込む
    • つなぎ3:Rails に、本番の Firebase Auth のログインだけを信じるよう教える

Issue #32 のゴールは、本番の URL(https://knowledge-library-prod.web.app)を開き、Google でログインし、記事を投稿すると、その記事が一覧に出ることです。Vue と Rails のコードは変えません。足すのは、Firebase Hosting の設定(firebase.json)と、Google の画面での設定だけです。

3Rails を本番に置いたときと、何が同じで何が違うか

「Rails を本番に置いたのと同じことを、Vue でも行う」という見方は、半分合っています。手元で作って本番に送るところは同じです。違うのは、送った後に どこで動くか です。

api(Rails)web(Vue)
手元で作るものイメージ(Rails と、動かすのに要るものを固めた箱)ビルドしたファイル(HTML、JavaScript、CSS)
送る先Artifact RegistryFirebase Hosting
本番で動く場所Google の中の Cloud Run利用者のブラウザの中
設定値を受け取るとき動き始めるとき(Cloud Run の環境変数、Secret Manager)ビルドするとき(ファイルの中に埋め込む)
使っていない間の料金0台まで減るので、ほぼかからないファイルを置くだけなので、無料枠に収まる

4行目の違いが、このノートでいちばん大事な点です。Rails は、動き始めるたびに設定値を受け取るので、設定を変えればデプロイし直すだけで済みます。Vue は、設定値をビルドのときにファイルへ書き込んでしまうので、設定を変えたらビルドからやり直します(6章の「つなぎ2」)。

Rails のコードは訳さずにそのまま箱に入り、本番で Ruby が読んで動かします。Vue のコードは本番の前に訳され、ブラウザには訳した結果だけが届きます。これが2つの一番の違いです。

混ざりやすい点:Issue #32 でも Docker を使う。仕様書 032 では、Vue のビルドを次のコマンドで行います。

docker run --rm -v "$PWD/web":/app -w /app node:24.22.0-slim npm run build

ここの Docker は、箱を作るためではなく、作業台 として使っています。docker build は新しいイメージ(箱)を 作る コマンドで、docker run は、すでにある Node のイメージを 借りて、その中でコマンドを動かすコマンドです。借りるのは、手元の Mac の Node が web/ の求める版より少し古く、web/node_modules も Linux 向けに入れたものだからです。npm run build の結果は、箱ではなく web/dist のファイルとして Mac に残り、作業台(コンテナ)は終わると消えます(--rm)。

Rails: docker build → イメージ(箱)→ Artifact Registry → Cloud Run が動かす
Vue:   docker run(作業台を借りる)の中で npm run build
       → web/dist(ファイル)→ Firebase Hosting → ブラウザが動かす

Rails の経験でいうと、npm run build は rails assets:precompile に近い作業です。CSS や JavaScript をブラウザ向けにまとめて小さくし、public/assets に出力する作業でした。このプロジェクトでは画面がすべて Vue なので、訳す対象が画面全体になります。

5準備から、ログインして投稿するまでの流れ

5つの場面に分けました。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。Vue の線は、ブラウザの中で動く Vue を表します。

場面 1:準備するIssue #32 で手で1回。設定値を変えたら③からやり直す

  1. オーナー が、Firebase Auth のコンソールで、ログインの方法に Google を足し、ウェブアプリを登録する。
  2. Firebase Auth が、オーナー に、このウェブアプリの設定値(プロジェクト ID、API キーなど4つ)を見せる。
  3. オーナー が、設定値を手元のファイルに書き、Vue をビルドする。設定値はビルドしたファイルの中に埋め込まれる。
  4. オーナー が、ビルドしたファイルを Firebase Hosting に送る(デプロイ)。
  5. オーナー が、Rails の設定に、本番のプロジェクト ID を足してデプロイし直す。

場面 2:画面を開く利用者が URL を開くたび

  1. ブラウザ が、Firebase Hosting に、https://knowledge-library-prod.web.app/ の画面を頼む。
  2. Firebase Hosting が、ブラウザ に、画面のファイル(index.html と JavaScript)を渡す。利用者が /articles/new のような画面の URL を直接開いたときも、同じ index.html を渡す。
  3. ブラウザ が JavaScript を読み込み、Vue が動き出す。Vue は URL を見て、出す画面を決める。

場面 3:一覧を見る一覧の画面を出すたび

  1. Vue が、Firebase Hosting に、/api/articles(記事の一覧)を頼む。Vue から見ると、画面をもらったのと同じ相手に頼んでいる。
  2. Firebase Hosting は自分では答えず、Rails に取り次ぐ。
  3. Rails が、データベースから記事を読む。
  4. Rails が、Firebase Hosting に記事の一覧を返す。
  5. Firebase Hosting が、その答えを Vue にそのまま渡す。Vue が一覧を画面に出す。

場面 4:ログインするログインのボタンを押したとき

  1. Vue が、本番の Firebase Auth に、Google でのログインを頼む。小さな窓(ポップアップ)が開き、利用者が Google アカウントを選ぶ。
  2. Firebase Auth が、Vue に、ID トークンを渡す。ID トークンには「本番の Firebase Auth が発行した」という印(プロジェクト ID)が入っている。

場面 5:投稿する投稿のボタンを押したとき

  1. Vue が、Firebase Hosting に、記事と ID トークンを送る(POST /api/articles)。
  2. Firebase Hosting が、Rails に取り次ぐ。ID トークンも、そのまま一緒に届く。
  3. Rails が、ID トークンを確かめる。署名が本物か、期限内か、そして 本番の Firebase Auth が発行したものか(⑤ で教わったプロジェクト ID と同じか)を見る。
  4. Rails が、その会員の記事としてデータベースに保存する。
  5. Rails が、Firebase Hosting に「保存した」と返す。
  6. Firebase Hosting が、Vue に渡す。Vue は一覧の画面に戻り、場面 3 がもう一度起きて、投稿した記事が一覧に出る。

今ここ:Issue #32 で手で行うのは、場面 1 です。場面 2〜5 は、場面 1 が終われば、利用者の操作で自然に起きます。完了条件は、場面 2〜5 が本当に起きるかを確かめるものです(8章)。

63つのつなぎ

図4 の矢印のうち、Issue #32 で初めて通るようになるのは、Firebase Hosting を通る矢印(⑥⑦、⑨⑩⑫⑬、⑯⑰⑳㉑)と、本番の Firebase Auth との矢印(⑭⑮)です。これらを通すのが、次の3つのつなぎです。

つなぎ1:Firebase Hosting が、/api を Rails に取り次ぐ

Firebase Hosting には、「どのパスに来たリクエストを、どう扱うか」を設定に書きます。書くのは2行だけです。

来たリクエストのパスFirebase Hosting がすること図4
/api/ で始まる自分では答えず、東京の Rails(Cloud Run のサービス api)に取り次ぎ、その答えを返す⑨〜⑬、⑯〜㉑
それ以外で、ファイルがある(/assets/…js など)そのファイルを返す⑦
それ以外で、ファイルがない(/articles/new など)index.html を返す。Vue が起動して URL を見て、画面を出す⑦

3行目が要るのは、/articles/new のような画面は、ブラウザの中で Vue が切り替えて作るもので、ファイルとしては存在しないからです。この設定がないと、画面の URL をブックマークから直接開いたときに「ページが見つからない」(404)になります。

なぜ、ブラウザに Rails の URL を直接呼ばせず、Firebase Hosting に取り次がせるのか

結論:Vue から見た API の相手を、画面をくれた相手と同じ1つにそろえると、Vue のコードを変えずに済み、別の相手を呼ぶための許可の設定も要らないからです。

  1. 直接呼ぶ案では、2つの手間が増える。ブラウザが web.app から画面をもらい、run.app(Rails の URL)を直接呼ぶと、ブラウザから見て相手が2つになります。ブラウザは、画面をくれた相手と違う相手への呼び出しを、相手が許可したときだけ通します(CORS という仕組み)。そのため Rails に許可の設定が要り、Vue にも Rails の URL を教える必要があります。
  2. 取り次がせると、ローカルと同じ形になる。ローカルでは、Vite の開発サーバーが /api を Rails に取り次いでいます。本番では、Firebase Hosting が同じことをします。Vue は今も /api/articles のように同じ相手の /api を呼んでいるので、コードを変えずに済みます。
  3. 取り次がせる損は、このアプリでは小さい。損は2つあります。1つは、取り次ぎが60秒で打ち切られること。このアプリの API は1秒もかかりません。もう1つは、Firebase Hosting が答えを手元に保存して(キャッシュ)、ほかの人に同じ答えを返してしまうおそれです。Firebase Hosting は、答えに「保存してよい」(Cache-Control: public)と書かれたときだけ保存します。Rails の答えには「この人専用、保存しない」(Cache-Control: private)と書かれていることを、2026-11-13 に本番で確かめました。

まとめ:取り次がせると、許可の設定と URL の受け渡しがいらず、Vue のコードもローカルと同じまま動きます。損は60秒の上限と保存のおそれで、どちらもこのアプリでは困りません。判断は ADR 0008 に、設定は firebase.json に書きます。

つなぎ2:本番の Firebase Auth の設定値を、Vue のファイルに埋め込む

Vue が Firebase Auth にログインを頼むには、「どの Firebase Auth か」を知っている必要があります。それを表すのが、Firebase Auth がウェブアプリごとに発行する4つの設定値(プロジェクト ID、API キー、ログインの窓のドメイン、アプリ ID)です。今の Vue のファイルには、開発用の Firebase Auth の設定値しか入っていません。

順誰が、何をするか設定値がある場所
①Firebase Auth が、ウェブアプリを登録したオーナーに設定値を見せる。オーナー が、手元の設定値のファイルに書くFirebase Auth のコンソールMac のファイル
②オーナー が Vue をビルドする。ビルドの道具が、設定値のファイルを読み、JavaScript のファイルの中に値をそのまま書き込むビルドしたファイル
③オーナー が、ビルドしたファイルを Firebase Hosting に送るFirebase Hosting
④利用者が画面を開くたびに、Firebase Hosting がファイルを ブラウザ に配る(図4 の ⑦)ブラウザ
⑤Vue が、ログインのたびに、この設定値で本番の Firebase Auth を呼ぶ(図4 の ⑭)ブラウザ

なぜ、Rails のように動き始めるときに受け取らないのか

結論:Vue が動くのは利用者のブラウザの中で、そこには設定値を後から渡す係がいないからです。

  1. ブラウザには、設定を渡す仕組みがない。Rails は、Google の中の Cloud Run が、動き始めるたびに環境変数を渡してくれます。ブラウザは利用者の持ち物で、Google はそこに環境変数を渡せません。Vue が手にできるのは、配られたファイルの中身だけです。
  2. ファイルに埋め込めば、追加の通信がいらない。設定値を別のファイルにして、画面を開くたびに取りに行く方法もありますが、その分だけ通信が増え、取りに行く仕組みを Vue に書く必要があります。ビルドのときに埋め込むのは、Vite の標準のやり方です。
  3. 埋め込んでも、秘密は漏れない。この4つの値は、ブラウザに配る JavaScript に入るので、誰でも読めます。もともと秘密ではありません。Firebase Auth は、値を知っているだけでは使わせず、許可したドメイン(web.app など)からのログインだけを受け付けます。

まとめ:埋め込む損は、設定値を変えたらビルドからやり直すことだけです。設定値はめったに変わらないので、困りません。

落とし穴:いつもの Vue のコンテナ(docker compose run web)でビルドすると、開発用の設定値が埋め込まれます。このコンテナには、ローカル開発のために、開発用の設定値が環境変数で渡されているからです。ビルドの道具(Vite)は、ファイルに書いた値より、環境変数の値を優先します。そのため本番のビルドは、開発用の設定値を渡さない別のコマンドで行います(仕様書 032)。間違えても画面は開きますが、ログインが開発用の Firebase Auth に行き、Rails が ID トークンを断ります(つなぎ3)。

つなぎ3:Rails に、本番の Firebase Auth の札だけを信じるよう教える

ID トークンには、「どの Firebase Auth が発行したか」を表す印として、プロジェクト ID が入っています。Rails は、図4 の ⑱ で、この印が「自分が信じる Firebase Auth」と同じかを確かめます。違えば、署名が本物でも断ります(401)。開発用の Firebase Auth の札を、本番の Rails で使わせないためです。

Rails が信じる Firebase Auth は、環境変数 FIREBASE_PROJECT_ID で教えます。ローカルでは開発用のプロジェクト ID が入っていますが、本番の Rails にはまだ入っていません。図4 の ⑤ で、knowledge-library-prod を入れます。

本番の Rails の設定ログインが要らない一覧(場面 3)ログインした投稿(場面 5)
今(FIREBASE_PROJECT_ID がない)200(ID トークンを見ないので動く)500。トークンを確かめようとして、信じる相手が決まっていないため止まる
⑤ の後(knowledge-library-prod)200本番の Firebase Auth の札なら 201。開発用の札なら 401

この値は、ブラウザに配るファイル(つなぎ2)にも入る公開の値で、秘密ではありません。そのため、Secret Manager には入れず、Cloud Run の普通の環境変数で渡します。

ログインせずに投稿を送った場合(完了条件の AC-5)は、Rails は ID トークンを確かめる前に「札がない」として 401 を返します。この振る舞いは、⑤ の前でも後でも同じです。
