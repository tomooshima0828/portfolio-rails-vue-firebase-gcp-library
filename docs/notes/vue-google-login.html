Vue の Google ログインの全体像

Issue #11 では、会員が Vue の画面から Google アカウントでログインし、Rails がその会員を知るところまでを作ります。このページでは、細かい仕組みに入る前に、全体で何が起きるのかを見渡します。

このページで分かること

  • 誰が登場するか(2章)
  • ページを開いてから、ログインして Rails を呼ぶまでに、何が起きるか(3章)
  • ID トークンを、誰が、どこに持ち、どう Rails まで届けるか(4章)
  • コードに出てくる名前が、図のどこにあたるか(5章)
  • 今書いている手順 11 の firebase.ts が何をするか(6章)と、全体のどこにあたるか(7章)

1出発点:なぜこういう形になるのか

このアプリでは、Rails は会員のパスワードを持ちません。ログインそのものは Google に任せます。

ただ、そうすると Rails は「今リクエストしてきたのは誰か」を自分では分かりません。そこで、Google がログインした人に ID トークン(ログインした証明書)を発行し、Vue がそれを Rails に見せます。Rails は、ID トークンが本物かを確かめて、会員を特定します。この「確かめる」部分は、Issue #8 で作りました。

Issue #11 で作るのは、残りの Vue の部分です。ログインのボタンを出し、Google でログインさせ、受け取った ID トークンを Rails に見せるところまでです。

登場人物は6人です。3人はブラウザの中にいて、2人はインターネットの先にいます。色は、このページの図と本文で共通です。

会員(あなた)人ブラウザで画面を見て、ボタンを押す人

Vue のコードブラウザの中 · 私たちが書く画面を出すプログラム。Issue #11 では4つのファイルに分けて書く(4章)

ブラウザの保存領域ブラウザの中 · ブラウザが持つタブを閉じても消えない場所。Firebase の SDK が、ここにログイン状態(ID トークンなど)を保存する。私たちのコードは直接触らない

3全体の流れ

Issue #11 で起きることを、6つの場面に分けました。縦の点線が登場人物で、上から下へ時間が進みます。矢印の色は、矢印を出した側の色です。

場面 0:準備ページを開くたび、最初に

  1. Vue のコード が、Firebase の SDK に、どの Firebase のプロジェクトとやりとりするかを伝える。Firebase の SDK は、そのプロジェクトとやりとりするための窓口を作る

今書こうとしている手順 11 の firebase.ts は、この1行だけを受け持ちます。場面 1〜5 で Vue のコード が Firebase の SDK に何かを頼むときは、必ずこの窓口を通します。

場面 1:初めて開く未ログイン

  1. Firebase の SDK が、ブラウザの保存領域 に、前回のログイン状態があるか探す。初めてなので、ない
  2. Firebase の SDK が、Vue のコード に「未ログイン」と知らせる
  3. Vue のコード が、画面にログインのボタンを出す

完成したアプリでは、未ログインでも記事の一覧が見られます(記事の一覧の API はログインが要りません)。ただ、記事の画面は Issue #12 で作ります。Issue #11 の画面にあるのは、ログインのボタンと会員の id だけです。

場面 2:ログインする

  1. 会員 が、ログインのボタンを押す
  2. Vue のコード が、Firebase の SDK にログインを頼む
  3. Firebase の SDK が、ポップアップ(小さな別ウィンドウ)を開き、Google のログイン画面を出す
  4. 会員 が、ポップアップの中で Google アカウントを選び、ログインする
  5. Google が、ID トークンを発行して、Firebase の SDK に渡す。ポップアップは閉じる
  6. Firebase の SDK が、ID トークンを手元に持っておく。同じものを、ブラウザの保存領域 にも保存する
  7. Firebase の SDK が、Vue のコード に「ログイン中」と知らせる

Firebase の SDK は、ID トークンを2か所に持ちます。

置き場所性質何に使うか
SDK の手元(メモリ)ページを閉じると消える場面 3 で、Vue のコード に渡す
ブラウザの保存領域ページを閉じても残る場面 5 で、ページを開き直したときに手元へ読み戻す

Vue のコード は、保存領域を直接読みません。ID トークンが欲しいときは、いつも Firebase の SDK に頼みます(場面 3)。

場面 3:Rails を呼ぶ「ログイン中」と知らされたら

  1. Vue のコード が、Firebase の SDK に ID トークンを頼む
  2. Firebase の SDK が、手元に持っている ID トークンを、Vue のコード に渡す。ID トークンの期限(1時間)が近いときは、先に Google から新しい ID トークンを取り直してから渡す
  3. Vue のコード が、ID トークンを付けて、Rails の GET /api/me を呼ぶ
  4. Rails が、ID トークンが本物かを確かめ、会員を特定する。初めての会員なら、会員を作る(Issue #8)
  5. Rails が、Vue のコード に会員の id を返す
  6. Vue のコード が、画面に「会員 ID:1」とログアウトのボタンを出す

場面 4:ログアウトする

  1. 会員 が、ログアウトのボタンを押す
  2. Vue のコード が、Firebase の SDK にログアウトを頼む
  3. Firebase の SDK が、手元と ブラウザの保存領域 の両方から、ID トークンなどのログイン状態を消す
  4. Firebase の SDK が、Vue のコード に「未ログイン」と知らせる。Vue のコード は、画面をログインのボタンに戻す

場面 5:開き直すログインしたまま、再読み込みする・開き直す

  1. Firebase の SDK が、ブラウザの保存領域 に、前回のログイン状態があるか探す。場面 2 で保存したので、ある。SDK は、見つけた ID トークンなどを手元に読み戻す
  2. Firebase の SDK が、Vue のコード に「ログイン中」と知らせる
  3. このあと、場面 3 と同じことが起きる

場面 1 と場面 5 は、同じ仕組みです。違うのは、ブラウザの保存領域 にログイン状態があるかどうかだけです。

4ID トークンを追う

3章の場面のうち、いちばん大事なのは「ID トークンを、誰が、どこに持ち、どう Rails まで届けるか」です。この章では、ID トークンだけに注目して、生まれてから消えるまでを追います。

たとえ話:入館証

ID トークンを、会社の入館証にたとえます。入館証には、発行所の印鑑が押してあり、「この人は誰か」と「有効期限(1時間)」が書いてあります。

たとえ話このアプリでは
入館証(印鑑つき、期限1時間)ID トークン
入館証の発行所Google
入館証の管理係。あなたの代わりに入館証を預かるFirebase の SDK
管理係の机の上。すぐ取り出せるが、退勤すると片付けられるSDK の手元(ページを閉じると消える)
管理係のロッカー。退勤しても中身が残るブラウザの保存領域
届け係。窓口に用事を頼みに行くとき、管理係から入館証を借りて見せるVue のコード
用事を受け付ける窓口。入館証の印鑑が本物かを確かめてから受け付けるRails

ID トークンの一生

右の列は、その時点で ID トークンがどこにあるかです。

順誰が、何をするかID トークンがある場所
①会員 がポップアップの中で Google にログインすると、Google が ID トークンを作り、Firebase の SDK に渡す。ID トークンには、Google の印鑑(署名)、会員が誰か、期限(1時間後)が書いてあるSDK の手元
②Firebase の SDK が、ID トークンを手元に置いたまま、写しを 保存領域 にしまう。ID トークンを取り直すための情報も、いっしょにしまうSDK の手元保存領域
③Vue のコード が、Rails に用事を頼む前に、Firebase の SDK に「ID トークンをください」と頼む。Firebase の SDK は、手元の ID トークンを渡すSDK の手元保存領域Vue のコード
④Vue のコード が、Rails への依頼(リクエスト)の決まった欄(Authorization という欄)に ID トークンを書き込み、Rails に送る。Vue のコード は、送ったら ID トークンを手放すSDK の手元保存領域Rails に届いた依頼の中
⑤Rails が、ID トークンの印鑑が Google の本物か、期限が切れていないかを確かめ、会員を特定する(Issue #8)。Rails は ID トークンを保存しない。依頼が来るたびに、届いたものを確かめるSDK の手元保存領域
⑥期限が近づいたあとに ③ で頼まれると、Firebase の SDK は、② でしまった「取り直すための情報」を Google に見せて、新しい ID トークンをもらう。手元と保存領域の ID トークンを、新しいものに入れ替えてから、Vue のコード に渡すSDK の手元保存領域(どちらも新しいもの)
⑦会員 がページを閉じると、SDK の手元にあった ID トークンは消える保存領域
⑧会員 がページを開き直すと、Firebase の SDK が、保存領域の写しを手元に読み戻す。このあとは ③ からと同じSDK の手元保存領域
⑨会員 がログアウトのボタンを押すと、Vue のコード が Firebase の SDK にログアウトを頼み、Firebase の SDK が手元と保存領域の両方から ID トークンを消すどこにもない

Vue のコードが、ID トークンを自分で持っておかない理由

結論から言うと、期限内の新しい ID トークンを持っているのは、いつも Firebase の SDK の手元だけだからです。Vue のコード が取っておいた写しは、すぐに古くなります。理由は3つあります。

  1. 取り直すのは SDK なので、Vue のコードの写しは取り残される。ID トークンの期限は1時間です。期限が近づくと、Firebase の SDK が Google から新しい ID トークンを取り直し、自分の手元と保存領域を入れ替えます(⑥)。このとき、Vue のコード が取っておいた写しは入れ替わりません。その古い写しを Rails に送ると、期限が切れていれば Rails は 401 を返します。 入館証で言うと、管理係は期限の前に新しい入館証に取り替えますが、届け係がコピーを持っていると、そのコピーは古いままです。
  2. Vue のコードには、取り直す手段がない。取り直すための情報(② でいっしょにしまったもの)を持っているのも、Google とやりとりするのも、Firebase の SDK です。Vue のコード で期限を見張って取り直す仕組みを作ると、SDK がすでに持っている仕組みを、もう1つ作ることになります。
  3. 毎回頼んでも、手間はほとんどかからない。期限内なら、Firebase の SDK は手元の ID トークンをすぐに返し、Google とは通信しません。Google と通信するのは、期限が近いときだけです。

つまり、Vue のコード が ID トークンを持っておいても得はなく、古くなる損だけがあります。そこで、Vue のコード は、Rails に用事を頼むたびに ③ から始め、そのとき SDK の手元にある ID トークンを使います。仕様書の「ID トークンは、API を呼ぶたびに getIdToken() で取り出す」は、このことです。

Issue #11 で私たちが書くのは、③ と ④ だけ

①②⑥⑦⑧⑨ は、Firebase の SDK(とブラウザ)が行います。⑤ は Issue #8 で書いた Rails のコードです。Issue #11 で ID トークンに触るのは ③ と ④ だけで、手順 13 の api/client.ts にまとめて書きます。手順 9 のテスト(client.spec.ts)は、この ③ と ④ を確かめています。

6場面 0 の詳細:firebase.ts

ここからが、今書こうとしている手順 11 の話です。firebase.ts が受け持つのは、図2 の場面 0「窓口を作る」の1か所だけです。

書くコード

import { initializeApp } from 'firebase/app'
import { getAuth } from 'firebase/auth'

// 設定値を渡して、どのプロジェクトとやりとりするかを覚えた app を作る
const app = initializeApp({
  apiKey: import.meta.env.VITE_FIREBASE_API_KEY,
  authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
  projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
  appId: import.meta.env.VITE_FIREBASE_APP_ID,
})

// app から窓口の auth を作り、ストアと apiFetch が使えるように書き出す
export const auth = getAuth(app)

流れ

  1. firebase.ts が、import.meta.env で、オーナーが .env に書いた4つの設定値を読む
  2. firebase.ts が、Firebase の SDK の initializeApp に設定値を渡す。SDK は、設定値を覚えた app を返す
  3. firebase.ts が、Firebase の SDK の getAuth に app を渡す。SDK は、窓口の auth を返す。このとき auth.currentUser は null(SDK の手元は、まだ空)
  4. firebase.ts が、auth を書き出す(export)。firebase.ts の仕事はここで終わり
  5. このあと、Firebase の SDK が、自分で保存領域を探し始める(図2 場面 1・5)。ここから先は、firebase.ts は関わらない

2 と 3 では、まだ Google と通信しません。ブラウザの中でオブジェクトを作るだけです。

auth の中身の移り変わり

図3 の「SDK の手元」は、コードの中では auth.currentUser です。中身を簡単にすると、次のように移り変わります。

いつauth.currentUser
firebase.ts が作った直後null
図3 ① ログインしたあと、または ⑧ 読み戻したあと会員(uid と、ID トークンを返す getIdToken を持つ)
図3 ⑦ ページを閉じたときauth ごと消える(次に開いたら、また firebase.ts が作る)
図3 ⑨ ログアウトしたあとnull

窓口を1か所で作る理由

auth は、ストア(手順 12)と apiFetch(手順 13)の2か所で使います。

  • ストアが signInWithPopup(auth, …) でログインすると、Firebase の SDK が、その auth の currentUser に会員を入れる(図3 ①)
  • apiFetch は、auth.currentUser.getIdToken() で ID トークンをもらう(図3 ③)

2か所が別々の auth を見ていると、ログインした結果を apiFetch が見つけられません。同じ1つの auth を見るように、firebase.ts で作って、両方から import します。JavaScript のファイル(モジュール)は、何か所から import されても、中身は最初の1回しか実行されないので、auth は1つだけになります。

テストでの扱い

手順 8〜10 のテストは、どれも vi.mock('@/firebase', …) で、このファイルを偽物の auth に差し替えています。テストでは本物の Firebase に通信しないためです。firebase.ts 自体にはテストを付けず、型チェック(vue-tsc)が通ることと、最後の手動確認(AC-9:本物の Google アカウントでログインできる)で確かめます。
