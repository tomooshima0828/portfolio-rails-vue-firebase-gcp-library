コードで追うログイン

全体のノート(vue-google-login.html)で、ログインの流れを見ました。ファイルのノート(vue-login-files.html)で、ファイルどうしのつながりを見ました。このページでは、実際のコードを、ものが渡る順番に6か所読みます。どの行が、ノートの図のどの矢印にあたるかを、1行ずつ対応させます。

このページで分かること

  • なぜこの順番で読むのか(1章)
  • 6か所の道順と、それぞれで受け取るもの・渡すもの(2章)
  • 6つの場所のコードの1行ずつの意味と、ノートの図との対応(3〜8章)

1なぜこの順番で読むのか

コードは、ファイルごとに分かれています。1つのファイルを上から読んでも、ファイルとファイルの間で何が渡っているかは書いてありません。ノートの図で流れが分かっていても、「その矢印は、コードのどの行か」が分からないと、Issue #12 で記事の画面を書き足すときに、どこを手本にすればよいかが分かりません。

そこで、このページでは、ものが渡る順番にコードを読みます。

この順番にする理由

結論:読む順番を「ものが渡る順番」にそろえると、どのファイルも、入ってくるものと出ていくものが分かった状態で読めます。

  1. 画面から読む方法だと、中身を知らない名前が先に出てくる。画面の App.vue から読む方法もよく使われます。ただ、App.vue の最初の数行で useAuthStore と apiFetch が出てきて、その中で何が起きるかを知らないまま読み進めることになります。
  2. フォルダーや名前の順だと、つながりを自分で組み直すことになる。ファイルの並びは流れと関係がないからです。
  3. ものが渡る順番なら、前の順の出口が、次の順の入口になる。各章の最後で「次に渡すもの」を確かめれば、それがそのまま次の章の入口です。損は、最初の順1 ではまだ画面が出てこないことくらいで、全体のノートの場面 0 に戻れば位置が分かります。

この順番は、全体のノートの図2・図3 と、ファイルのノートの図1・図3 の流れと同じです。

ログインのボタンを押したとき、このファイルの中で起きる順番

  1. 順3 の App.vue が、signIn(27行目)を呼ぶ
  2. 28行目で、SDK がポップアップを開く。会員が Google でログインし終えるまで、ここで待つ
  3. ログインが終わると、SDK が、21行目で登録しておいた関数を、会員を渡して呼ぶ(28行目の待ちが終わるのと、どちらが先かは気にしなくてよい作りにしてある。理由は下の 3)
  4. 22行目で user に会員が入り、23行目で authStateReady が true になる(すでに true なら、そのまま)
  5. user が入れ替わったので、順3 の App.vue の画面と watch が動く

なぜこう書くか

結論:user を書き換えるのは、知らせの中(22行目)の1か所だけにします。

  1. ログイン中になるきっかけは2つある。ボタンでログインしたとき(場面 2)と、ページを開き直したとき(場面 5)です。signIn の中で user に入れる書き方だと、開き直したときは signIn を通らないので、user が入りません。
  2. 知らせの中なら、どのきっかけでも同じ1か所を通る。ログイン、ログアウト、開き直しのどれでも、22行目を通ります。
  3. 1か所にまとめても損はない。画面は user の変化を見張っているので、user がいつ入っても同じように動きます。

そのほかの書き方の理由です。

  • shallowRef にする理由:user の中身は SDK のオブジェクトで、中を書き換えるのは SDK です。知りたいのは入れ替わったかどうかだけなので、入れ替わりだけを見張れば足ります。
  • authStateReady を持つ理由:開いた直後の user の null は、「未ログイン」か「まだ分からない」かを区別できません。区別しないと、ログイン中の会員にも、ログインのボタンが一瞬見えてしまいます。

確かめ方

  • 画面の下の中央にある Vue DevTools のボタンを押し、Pinia の欄で auth のストアを選ぶと、user と authStateReady の今の値が見えます。ログインとログアウトで変わるのを見られます(10章)。
  • テスト:web/src/stores/__tests__/auth.spec.ts の5件。偽物の SDK から知らせを送り、user と authStateReady が変わるかを確かめています。

なぜこう書くか

結論:ID トークンは取っておかず、送るたびに SDK からもらいます(9行目)。

  1. 取っておいた写しは、古いまま残る。ID トークンの期限は1時間で、期限が近づくと SDK が新しいものに取り直します。取り直されても、私たちのコードが取っておいた写しは変わりません。
  2. 私たちのコードには、取り直す手段がない。取り直すための情報も、Google とのやりとりも、SDK が持っています。
  3. 毎回もらっても、損はない。期限内なら、SDK は通信せずにすぐ返します。

まとめると、取っておく得はなく、古くなる損だけがあります。詳しくは全体のノートの4章にあります。

もう1つ、未ログインのときも、Authorization を付けずに送ります(7行目の if を通らない)。記事の一覧(GET /api/articles)のように、ログインしなくても呼べる API があるためです(完了条件 AC-7)。

なぜこう書くか

結論:ブラウザから見た相手を、localhost:5173 の1つにします。

  1. Rails を直接呼ぶと、相手が2つになる。ブラウザから localhost:3000 の Rails を直接呼ぶと、ブラウザから見た相手が2つ(画面は 5173、API は 3000)になります。すると、ブラウザの安全のための決まり(CORS)によって、Rails 側に「5173 からの呼び出しを許す」設定が要ります。
  2. 転送なら、その設定が要らない。ブラウザから見た相手は1つです。本番で、Firebase Hosting が /api を Cloud Run の Rails へ転送する形とも同じになります。
  3. changeOrigin は false にする。true だと、宛先の欄(Host ヘッダー)が api:3000 に書き換わり、Rails の開発環境が「知らない宛先」として断ります。false なら宛先は localhost:5173 のままで、Rails が初めから許している localhost に当たります。

確かめ方

  • Network タブで me を選ぶと、Request URL は http://localhost:5173/api/me です。3000 ではないことが、転送されている証拠です。
  • Rails のログ(docker compose logs -f api)に、Started GET "/api/me" for 192.168.… と出ます。この 192.168.… は Docker のネットワークの中のアドレスです(手元の確認では 192.168.97.2 でした)。ブラウザではなく、web コンテナの Vite が Rails を呼んでいることが分かります。
