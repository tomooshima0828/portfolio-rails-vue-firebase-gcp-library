Vue の本番配信と Firebase Hosting

roadmap.md のフェーズ2(本番デプロイ)に Firebase Hosting を入れるかどうかの判断材料。Knowledge Library(Rails API + Vue 3 SPA)の構成を例に説明する。

このページで答える問い Firebase Hosting は README で優先度 B になっている。一方、principles.md には「A を先に完成させ、B は後回し」とある。それでもフェーズ2に入れるべきか。

1.出発点:何に困っているのか

フェーズ2で本番にデプロイするとき、Vue の画面を利用者のブラウザまで届ける場所が必要になる。

Rails API は Cloud Run で動く。しかし Vue は、vite build でビルドすると HTML・JavaScript・CSS のファイル(静的ファイル)になる。これは Rails のようにサーバーとして動き続けるものではない。そのため、「このファイルを HTTPS で配る係」を別に決める必要がある。

つまり本当の問いは「Firebase Hosting を使うかどうか」ではない。「本番で Vue をどこから配り、ブラウザから Rails API をどう呼ぶか」である。

2.前提の言葉

  • オリジン:URL のうち「プロトコル + ドメイン + ポート」の組み合わせ。たとえば https://xxx.web.app と https://api-xxxx.a.run.app は別のオリジンになる。
  • CORS(Cross-Origin Resource Sharing):ブラウザは、画面を読み込んだオリジンとは別のオリジンへ JavaScript から送ったリクエストについて、相手のサーバーが許可した場合しか結果を渡さない。この許可の仕組みが CORS。Rails 側では rack-cors で許可を出す。
  • rewrite(転送):配信サーバーが、特定のパスへ来たリクエストを別のサーバーへ回す設定。
  • SPA のフォールバック:利用者が /articles/3 のような URL を直接開いたときにも、配信サーバーが index.html を返す設定。SPA(Single Page Application)では画面の切り替えを Vue Router がブラウザの中で行うので、サーバー側に /articles/3 というファイルは存在しない。
  • CDN(Content Delivery Network):静的ファイルの複製を世界中のサーバーに置き、利用者に近い場所から返す仕組み。

4.全体の流れ(Firebase Hosting で /api を転送する場合)

手順の詳細

  1. ブラウザ → Firebase Hosting:利用者のブラウザが https://xxx.web.app/ を要求する。Firebase Hosting は CDN から index.html と JavaScript を返す。
  2. ブラウザ ⇄ Firebase Auth:ブラウザで動き始めた Vue が Firebase Auth で Google ログインを行い、ID トークンを受け取る。
  3. ブラウザ → Firebase Hosting:Vue が、同じオリジンの https://xxx.web.app/api/articles へ、ID トークンを付けてリクエストを送る。
  4. Firebase Hosting → Rails:Firebase Hosting が、/api/** に来たリクエストを rewrite 設定に従って Cloud Run の Rails へ転送する。
  5. Rails → Firebase Hosting → ブラウザ:Rails が ID トークンを検証して記事を返す。応答は Firebase Hosting を通ってブラウザへ戻る。

ブラウザから見ると、API の相手は最初から最後まで xxx.web.app だけになる。オリジンが1つなので、CORS は発生しない。

5.例え話

Firebase Hosting を、建物の受付カウンターに例える。

例え実際
来訪者ブラウザ
受付カウンターFirebase Hosting
受付に置いてあるパンフレットVue の静的ファイル
奥の部屋にいる担当者Rails API
受付が担当者へ用件を取り次ぐことrewrite(/api の転送)
別の建物に入るときの入館許可CORS

A の構成では、来訪者は受付にだけ話しかければよい。パンフレットはその場でもらえ、込み入った用件は受付が奥の担当者へ取り次いでくれる。D の構成では、来訪者はパンフレットを受付でもらった後、担当者のいる別の建物へ自分で出向く。その建物では入館許可(CORS)の確認を受ける。

6.選択肢と、それぞれの困る点

案構成よい点困る点
A. Firebase Hosting + /api 転送 Vue は Hosting、/api は Hosting が Cloud Run へ転送 無料枠で収まる。CDN と HTTPS が自動。SPA のフォールバックは設定1行。同じオリジンなので CORS 不要 Hosting 経由の Cloud Run 呼び出しは60秒で打ち切られる。API の応答に Cache-Control を付け間違えると CDN にキャッシュされる
B. Cloud Storage の静的サイト Vue はバケット、/api の振り分けはロードバランサ Google Cloud だけで完結する HTTPS と /api の振り分けにロードバランサが必要で、常時課金(月に数千円規模)。SPA のフォールバックが不自然(404 ページに index.html を指定する)
C. Rails が Vue も配る Vue のビルド結果を Rails の public/ に入れ、Cloud Run 1つで動かす 構成が一番単純。同じオリジン 画面を直すだけでも Rails のデプロイが必要。CDN がない。README の「api/ と web/ を分ける」構成と合わない
D. Firebase Hosting + 別オリジン Vue は Hosting、ブラウザは Cloud Run の URL を直接呼ぶ 転送の制約(60秒など)がない CORS の設定が必要。オリジンが2つになり、設定ミスの入り口が増える

B は principles.md の非目標「無料枠・低額枠を超える常時稼働の構成」に当たるので外れる。C は、フロントとバックエンドを分けて見せるというポートフォリオの意図とずれる。現実的なのは A か D で、どちらにしても Firebase Hosting は使う。

7.このプロジェクトでの位置づけ

  • Firebase と Cloud Run を組み合わせる構成では、A は公式ドキュメントでも紹介されている定番の形。求人の「Firebase / Google Cloud を使った開発経験」を説明する材料にもなる。
  • A を選ぶと、README で優先度 A になっている rack-cors の意味が変わる。本番は同じオリジンになるので、CORS が必要なのはローカル開発(Vite の 5173 番ポート → Rails の 3000 番ポート)だけになる。しかも Vite の proxy 機能を使えば、ローカルでも不要にできる。D を選んだ場合は、本番でも rack-cors が必要。
  • つまり A と D のどちらを選ぶかは、rack-cors の扱いにも関わる設計上の分かれ道になる。

8.推奨

roadmap.md には「フェーズ2で Vue の本番配信を Firebase Hosting で行う。方式(A か D か)はフェーズ2のタスクで ADR に残して決める」と書く。あわせて、「優先度は B だが、本番で Vue を配る場所が必要なので、例外としてフェーズ2に入れる」と1行添える。

今の時点で A か D かまで決めないのは、architecture.md の「決まっていないことは書かない」方針に合わせるため。実際にデプロイするタスクで60秒の制約やキャッシュの挙動を確かめてから ADR に残すほうが、根拠のある判断になる。
