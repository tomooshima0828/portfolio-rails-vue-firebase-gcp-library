# 方針(Principles)

このプロジェクトの「変えない前提」を置く。タスクごとの仕様書は `docs/specs/`、技術選定の理由は `docs/adr/` に書く。

## 目的

リベシティ「Railsエンジニア」求人(業務委託・フルリモート)の要件を、動くもので示すポートフォリオを作る。
要件と、このリポジトリでの示し方の対応表は [README.md](../README.md) にある。

題材は、会員がノウハウ記事を投稿・検索・ブックマークできる「ノウハウ図書館」風の Web サービス。
機能の豊富さが目的ではない。**求人要件を満たしていることが、コードと記録から読み取れること**が目的。

## 優先順位

迷ったら上から順に判断する。

1. **理解できていること**。オーナーが説明できないコードは入れない。面接で「なぜこうしたか」に答えられることが成果物の価値になる。
2. **求人の必須要件に直結すること**。優先度 A の技術を先に完成させ、B、C は後回しにする。
3. **小さく動くこと**。機能を広げる前に、ログインから記事の一覧表示まで通して動かす。
4. **記録が残ること**。判断と計測は、後から読める形で `docs/` に残す。

## 進め方

- 仕様駆動開発(SDD)。全体を決める → タスクに分解する → タスクごとに仕様書を書いてから実装する、の順に進める。
- Claude Code との対話とコミットは 1ファイル(1実装箇所)単位。書く前に説明し、承認後に書き、差分を確認してからコミットする。
- PR はタスク単位(1タスク = 1 Issue = 1 ブランチ = 1 PR)。GitHub での具体的な流れは [development-flow.md](development-flow.md) に書く。
- AI への作業ルールは [CLAUDE.md](../CLAUDE.md) に書く。

## 非目標(やらないこと)

- 本物のサービス並みの機能やデザイン。UI は最低限でよい。
- 優先度 C の技術を、A・B が終わる前に入れること。
- 理解していない技術を、見栄えのために入れること。
- 無料枠・低額枠を超える常時稼働の構成。Cloud SQL は予算アラートを設定し、使わない期間は停止または削除する。

## 品質の基準

- 変更は必ず PR 経由。CI(RSpec、RuboCop、Brakeman、Vitest、vue-tsc、ルールテスト)が通ること。
- 認証・認可に関わる箇所は、テストで保証する(Rails のトークン検証、Firestore セキュリティルール)。
- 性能の改善は、改善前後の数値を残す。
- 機密情報(鍵、`.env`、本番データ、個人情報)は、リポジトリにも AI にも渡さない。

## 記録のルール

| 内容 | 置き場所 |
|---|---|
| 今の全体像(機能一覧、画面と API の一覧、データモデル、インフラ構成) | `docs/architecture.md` |
| フェーズと、その順番・目標 | `docs/roadmap.md`、GitHub Milestone |
| タスクごとの仕様書(目的、やること、やらないこと、完了条件、設計) | `docs/specs/Issue番号-名前.md` |
| タスクと進み具合(仕様書へのリンク) | GitHub Issue |
| 変更内容と、その理由・動作確認の結果 | GitHub PR |
| 技術選定・設計判断(背景、選択肢、決定、理由) | `docs/adr/NNNN-名前.md` |
| 検討メモ(ADR を書く前の判断材料、技術の解説) | `docs/notes/` |
| AI に渡さない情報の線引き | `docs/ai-guideline.md` |
| 構成図、runbook、スプリントの記録 | `docs/` 配下 |

## 最初の到達点

最初のマイルストーンは、次の縦一本が動くこと。

> Google ログイン(Firebase Auth)→ ID トークンを Rails が検証 → 記事を1件投稿 → 一覧で表示

これを roadmap のフェーズ1にする。
