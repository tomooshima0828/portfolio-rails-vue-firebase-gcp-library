# CI を作る

Issue: #7

## 目的

PR ごとにテストと静的解析を自動で実行し、通らない変更を main に入れられないようにする。

## やること

- `.github/workflows/ci.yml` を作り、PR を作成・更新したときと、main に push(マージ)したときに動かす
- ジョブを4つに分ける。ジョブごとに成否が分かれるので、何が失敗したかがすぐ分かる
  - `api-lint`:RuboCop
  - `api-security`:Brakeman、bundler-audit
  - `api-test`:RSpec。PostgreSQL 17 を services で起動する
  - `web`:vue-tsc、Vitest
- ワークフローの権限は、リポジトリを読むだけ(`contents: read`)にする
- main の Ruleset に、4つのジョブの成功を必須として足す

## やらないこと

- CD(デプロイ、フェーズ2)
- Firestore セキュリティルールのテスト(フェーズ4)
- Dependabot(フェーズ5)
- Vue のビルド(`npm run build`)。Issue の範囲外で、型チェックは vue-tsc で別に行う

## 完了条件

<!-- AC-3、AC-4 は、わざと問題を入れた確認用のブランチと下書きの PR で確かめ、確認後に PR を閉じてブランチを消す -->

- AC-1:PR を作成・更新したとき、CI は4つのジョブを実行し、すべて成功する
- AC-2:main に push したとき、CI は同じ4つのジョブを実行する
- AC-3:チェックで問題が見つかった場合(RuboCop の違反、型エラー)、CI はそのジョブを失敗にし、ほかのジョブは成功にする
- AC-4:いずれかのジョブが失敗している場合、main の Ruleset は PR のマージを止める

## 設計

### 変更するファイル

セットアップのタスクなので、テストを先に書く順番の対象外。

1. `docs/specs/007-ci.md`:この仕様書
2. `docs/adr/0003-ci-environment.md`:CI は Docker Compose を使わず、Actions の標準の仕組み(setup-ruby、setup-node、services)で動かす判断
3. `.github/workflows/ci.yml`:CI の本体
4. (ファイルではない操作)main の Ruleset に、4つのジョブを必須のチェックとして足す。CI が一度動いて、チェックの名前が GitHub に登録されてから `gh api` で行う
5. `docs/development-flow.md`:「ブランチ保護」の「CI 導入後に追加する」を、実際の設定に書き換える
6. `docs/architecture.md`:構成に CI を足す

### 判断したこと

- **ワークフローで使う Action(checkout などの部品)のバージョンは、タグではなく、その Action のリポジトリのコミットの SHA で指定する**(例:`actions/checkout@<SHA> # v7.0.1`)。Gemfile.lock で gem のバージョンを固定するのと同じ考え方で、テストする PR のコミットとは別のもの。タグは後から別のコミットに付け替えられるため、Action の作者のアカウントが乗っ取られると、差し替えられたコードを CI が実行してしまう。SHA は中身と一対一なので、差し替えの影響を受けない。読みにくさは、横のバージョンのコメントで補う。更新は手で行い、フェーズ5からは Dependabot に任せる
- **バージョンはローカルとそろえる**。Ruby は `api/.ruby-version` を setup-ruby が読む。Node は `web/Dockerfile.dev` と同じ `24.22.0` を書き、そろえることをコメントに残す。PostgreSQL は compose.yaml と同じ `postgres:17`
- **DB の接続先は環境変数で渡す**(`DB_HOST=localhost` など)。`api/config/database.yml` は #5 のまま変えない
- **パスで絞り込まない**(`api/` が変わったときだけ api のジョブを動かす、など)。Ruleset で必須にしたチェックが動かないと、PR が「待ち」のままマージできなくなるため
