# 記事の投稿・一覧画面を作る

Issue: #12

## 目的

ログインした会員が Vue の画面から記事を投稿し、一覧で見られるようにする。これで、フェーズ1の縦一本(Google ログイン → Rails が ID トークンを検証 → 記事を投稿 → 一覧で表示)が画面からつながる。

## やること

- Vue Router に、記事の一覧画面(`/`)と投稿画面(`/articles/new`)を登録する
- 記事の一覧画面を作る。ログインしていなくても見られる。`GET /api/articles` の記事を、返ってきた順(新しい順)に出す
- 記事の投稿画面を作る。ログインが必要。`POST /api/articles` で保存し、成功したら一覧画面に移る
- ログインが必要な画面を守るガードを作る。未ログインなら一覧画面に移す
- 記事の API を呼ぶ関数を `src/api/articles.ts` にまとめる。中では #11 の `apiFetch` を使う
- `App.vue` を、ログイン・ログアウトのボタンを持つヘッダーと、画面を差し込む場所(`<RouterView>`)にする。#11 の仮の画面の「会員 ID」の表示と `GET /api/me` の呼び出しは消す

## やらないこと

- 記事の詳細・編集・削除、ページネーション(フェーズ3)
- 一覧に書いた人を出すこと。API が会員の名前を返さないため(会員の名前は、必要になった Issue で足す)
- エラーの文の日本語化(rails-i18n)。見た目を整えるときに一緒に決める
- 見た目を整えること(principles.md の非目標)
- 存在しないパスを開いたときの画面(404)
- 本番の Firebase Hosting で `/articles/new` を直接開けるようにする設定(フェーズ2)
- rack-cors。#11 の仕様書で決めたとおり、ローカルは Vite の proxy を使うので要らない

記事の API を呼ぶ関数

- AC-4:`GET /api/articles` または `POST /api/articles` が 422 以外の失敗(401、500 など)を返した場合、記事の API を呼ぶ関数は、エラーを投げる

- AC-6:記事が1件もない場合、一覧画面は「記事はまだありません」と表示する

### 入出力

画面

| パス | ログイン | 表示 |
|---|---|---|
| `/` | 不要 | 記事ごとに、タイトル、本文、投稿日時。記事がなければ「記事はまだありません」。ログイン中は「記事を書く」のリンク |
| `/articles/new` | 必要 | タイトルの入力欄(必須、100文字まで)、本文の入力欄(必須)、送るボタン。エラーがあれば、その文 |

ヘッダー(全画面で共通)

| 状態 | 表示 |
|---|---|
| ログイン状態の確認中 | 何も出さない |
| 未ログイン | 「Google でログイン」のボタン |
| ログイン中 | 「ログアウト」のボタン |

422 のエラーの表示は、Rails が返した項目ごとの文を、項目の日本語名と並べて出す(例:「タイトル:can't be blank」)。

記事の API を呼ぶ関数(`src/api/articles.ts`)

| 関数 | 受け取るもの | 返すもの |
|---|---|---|
| `fetchArticles()` | なし | 記事の配列。失敗したらエラーを投げる |
| `createArticle(input)` | `{ title, body }` | 成功なら `{ ok: true, article }`。422 なら `{ ok: false, errors }`(`errors` は `{ title: ["can't be blank"] }` の形)。それ以外の失敗はエラーを投げる |

記事の型は、`GET /api/articles` が返す項目に合わせる(`id`、`title`、`body`、`member_id`、`created_at`、`updated_at`)。

### 判断したこと

- **一覧と投稿を、別の画面にする**。#11 の仕様書で、画面の遷移とガードを、この Issue で記事の画面と一緒に作ると決めた。1画面に一覧とフォームを並べるとガードを作る場面がなくなり、ログインが必要な画面の守り方が、後の編集・削除の Issue に持ち越しになる
- **記事の API を呼ぶ処理は、`src/api/articles.ts` にまとめる**。API のパスと JSON の形を知っているのを、このファイルだけにする。画面は「記事の配列」や「項目ごとのエラー」だけを受け取る。画面のテストでは、この関数を偽物に差し替えればよく、`Response` を組み立てなくて済む
- **`createArticle` は、422 だけを戻り値で返し、ほかの失敗はエラーを投げる**。422 は会員が直せる失敗なので、画面が項目ごとに出す。401 や 500 は会員には直せないので、画面は一律にエラーの文を出す。扱いの違う2種類を、戻り値と例外で分けておく
- **ガードは、Firebase の SDK の `auth.authStateReady()` を待ってから `auth.currentUser` を見る**。ページを開き直した直後は、SDK が保存したログイン状態をまだ読み込んでいない。待たずに判断すると、ログインしている会員も一覧画面に移されてしまう。`authStateReady()` は、最初の判定が終わると解決する Promise で、判定が終わった後に呼べばすぐ解決する。ログイン状態の本体は SDK にあるので、ガードはストアの写しではなく SDK を直接見る
- **未ログインの会員を移す先は、一覧画面(`/`)にする**。ログインのボタンはヘッダーにあるので、ログイン専用の画面は作らない
- **ログアウトしたら、一覧画面に移す**。ガードは画面を開くときにしか働かないので、投稿画面にいる間にログアウトすると、ログインが必要な画面に残ってしまうため
- **入力欄の `required` と `maxlength="100"` で、送る前に止める**。Rails のバリデーション(タイトルは必須で100文字まで、本文は必須)と同じ決まりを、ブラウザでも確かめる。決まりの本体は Rails にあるので、それでも 422 が返ったときは、Rails の文をそのまま出す。日本語化は rails-i18n を入れるときに一緒に決める
- **送ってから応答が返るまで、送るボタンを押せなくする**。ボタンを2回押すと、同じ記事が2件保存されるため
- **#11 の「会員 ID」の表示と `GET /api/me` の呼び出しを消す**。ログインが Rails までつながっていることは、記事の投稿(ID トークン付きの `POST /api/articles` が 201 になる)で確かめられる。`GET /api/me` の API 自体は残す
