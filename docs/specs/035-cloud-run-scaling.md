# Cloud Run のスケール設定と、Cloud SQL の最大接続数を決める

Issue: #35

## 目的

アクセスが増えて Cloud Run のインスタンスが増えても、Cloud SQL の接続数が上限を超えないようにする。そのために、次の4つの値の関係を計算して決め、計算の過程を docs に残す。

- Cloud Run の最大インスタンス数と同時実行数(1つのインスタンスに同時に送るリクエストの数)
- Puma のスレッド数
- Rails の DB の接続プール(1つのインスタンスが持つ DB の接続の上限)
- Cloud SQL の最大接続数

2026-11-26 の時点の設定は、次のとおり。

| 対象 | 項目 | 値 | 決まり方 |
|---|---|---|---|
| Cloud Run のサービス `api` | 最大インスタンス数 | 1(サービス全体の値。版ごとの値は 20) | Issue #30 で決めた |
| Cloud Run のサービス `api` | 最小インスタンス数 | 0 | 初めの値のまま |
| Cloud Run のサービス `api` | 同時実行数 | 80 | 初めの値のまま |
| Puma | スレッド数 | 3 | `RAILS_MAX_THREADS` がないため、`api/config/puma.rb` の初めの値 |
| Rails | DB の接続プール | 5 | `RAILS_MAX_THREADS` がないため、`api/config/database.yml` の初めの値 |
| Cloud SQL のインスタンス `db` | マシン | 無料お試し(Enterprise Plus、8 vCPU) | Issue #31 で決めた |

問題は2つある。

- **同時実行数とスレッド数がそろっていない**。Cloud Run は1つのインスタンスに、同時に80件までリクエストを送る。Puma が同時に処理できるのは3件で、残りは Puma の中で待つ。Cloud Run からは、インスタンスに空きがあるように見える
- **接続プールの値に根拠がない**。スレッド数と同じ値にする設定(`RAILS_MAX_THREADS`)がないため、Puma と接続プールが、それぞれの初めの値になっている

計算の相手は、今の無料お試しの DB ではなく、2026-12-11 までに作り直す `db-f1-micro` にする(Issue #49)。作り直すと、最大接続数が下がるため。

## やること

- 4つの値を計算して決める(「設計」の「計算」)
- Cloud Run のサービス `api` の設定を変更する(オーナーがコンソールで行う)
  - 同時実行数を、Puma のスレッド数と同じ値にする
  - サービス全体の最大インスタンス数を変更する
  - 環境変数 `RAILS_MAX_THREADS` を足し、Puma のスレッド数と接続プールを同じ値にする
- 最小インスタンス数を 0 のままにしたときの、コールドスタート(インスタンスが0台の状態から、最初のリクエストに応答するまで)の時間を計測する
- `docs/production-setup.md` に「6. スケールの設定」の章を書く。計算、設定の手順、計測の結果を記録する。「本番の値」の表に、スケールの設定を足す

Cloud Run の画面の操作は、オーナーが行う。Claude は、操作の前に手順と理由を説明し、操作の後に gcloud・curl の読み取りだけのコマンドで結果を確認する。

## やらないこと

- 負荷試験。上限を超えるリクエストが来たときの振る舞いは、Cloud Run の文書では、待たせた後に 429 を返す。この実際の動きの確認は、フェーズ5の k6 で行う
- Cloud SQL の作り直しと、新しい DB の最大接続数の確認(Issue #49)
- 最小インスタンス数を1以上にすること。インスタンスが常に動作し、リクエストがなくても課金されるため
- Cloud SQL の最大接続数(`max_connections`)を、初めの値から変更すること
- Cloud Run のジョブ `migrate` の設定の変更
- Cloud Run の設定を `deploy.yml` で管理すること(仕様書 033 と同じく、`deploy.yml` はイメージだけを替える)

### 本番の値

| 項目 | 値 |
|---|---|
| Puma のスレッド数、接続の上限 | 3(環境変数 `RAILS_MAX_THREADS=3`) |
| 同時実行数 | 3 |
| 最大インスタンス数 | 2(サービス全体の値) |
| 最小インスタンス数 | 0 |
| Cloud SQL の最大接続数 | 25(`db-f1-micro` の初めの値。Issue #49 で実際の値を確認する) |

### 計算

DB の接続を使うのは、サービス `api` のインスタンスと、ジョブ `migrate` の2つ。どちらも、接続プールの値を、使う接続の上限として数える。

| 使う側 | 計算 | 接続数 |
|---|---|---|
| サービス `api` | 最大インスタンス数 2 × 接続の上限 3 本 | 6 |
| ジョブ `migrate` | 接続の上限 5 本(ジョブには `RAILS_MAX_THREADS` がないため、`database.yml` の初めの値) | 5 |
| Cloud SQL の管理用 | PostgreSQL が管理者のために予約する接続(`superuser_reserved_connections` の初めの値) | 3 |
| 合計 | | 14 |

この計算は、Puma の worker(プロセス)が 1 つである前提。環境変数 `WEB_CONCURRENCY` を設定していないため、worker は初めの値の 1 になる。

合計 14 は、最大接続数 25 に収まる。残りの 11 は、Cloud SQL が内部で使う接続と、作業のために手で接続するときの余裕にする。

同じ式で、DB の側から決まる最大インスタンス数の上限を求める。予約と余裕を少なめに見積もって 5 とすると、(25 − 5(ジョブ)− 5(予約と余裕))÷ 3 = 5 なので、上限は 5 台。

サービス全体の最大インスタンス数は、版をまたいだ合計の台数に効く(Cloud Run の文書「最大インスタンス数」)。デプロイ中に新旧の版が同時に動作しても、台数の合計は最大インスタンス数を超えない。

### 判断したこと

- **A. 同時実行数は、Puma のスレッド数と同じ 3 にする**。Cloud Run が送るリクエストの数と、Puma が同時に処理できる数をそろえる。そろえると、4件目のリクエストは、インスタンスの中で待たずに、Cloud Run が別のインスタンスに送る(またはインスタンスが増える)。Cloud Run の文書「同時実行」も、Python の例で、スレッド数を同時実行数に合わせるよう勧めている
- **B. スレッド数は、今の 3 のままにする**。Rails 8 の初めの値。Ruby は、1つのプロセスの中で同時に Ruby のコードを実行できるスレッドが1つだけ(GVL)なので、スレッドを増やしても、速くなるのは DB の応答を待つ時間だけになる。値を変えるかどうかは、フェーズ5の負荷試験の結果で判断する
- **C. 最大インスタンス数は 2 にする**。DB の側から決まる上限は 5 台だが、今の利用者はオーナーだけで、1台で足りる。2 にするのは、インスタンスが増えても接続数が上限を超えないことを、実際の設定で示すため。大量のアクセスを受けたときに、費用の増え方を1台の2倍までに抑える
- **D. 最小インスタンス数は 0 のままにする**。1 にすると、リクエストがない間もインスタンスが動作し、課金される。代わりに、コールドスタートの時間を計測して記録し(AC-4)、改善が必要かを判断する材料にする
- **E. ジョブ `migrate` には `RAILS_MAX_THREADS` を足さない**。ジョブは1回ずつ実行して終了するので、接続プールの 5 は、上の計算に収まる。ジョブの設定を変えるときは、サービスと同じ値にそろえる

### 注意すること

- **設定の変更で、新しい版ができる**。環境変数と同時実行数は版の設定なので、変更すると、今のイメージのまま新しい版が作られる。最大インスタンス数(サービス全体の値)は、版を作らずにすぐ効く(`docs/production-setup.md` の 2.8)
- **`deploy.yml` は、この設定を上書きしない**。`gcloud run services update` に `--image` だけを渡しているので、それ以外の設定は前の版から引き継がれる。AC-5 で確認する
- **CPU を増やして worker を増やすときは、計算をやり直す**。`RAILS_MAX_THREADS` は worker 1つあたりの値なので、インスタンス1台の接続の上限は「worker の数 × 接続の上限」になる。同時実行数も、「worker の数 × スレッド数」にそろえる。この Issue では、CPU は 1 つ、worker は 1 つのまま変えない。詳細は `docs/notes/035-cloud-run-scaling.html` の「参考」の節
- **Issue #49 で DB を作り直した後に、最大接続数を確認する**。25 でなかった場合は、この計算をやり直し、`docs/production-setup.md` を直す
